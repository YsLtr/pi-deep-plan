# pi-deep-plan — 设计文档索引

本目录是 **pi-deep-plan 的权威设计文档**。代码是实现,文档是契约:实现与文档冲突时,先改文档,再改代码(见 §6 维护约定)。

- 产品:pi 编码代理的「先写文档、再改代码」扩展。
- 机制:两阶段门禁 —— 文档阶段只允许写 `docs/`,执行阶段冻结 `docs/`。
- 工程底线:TypeScript,运行时依赖只有命令解析用的 `shell-quote`,扩展只经 pi 的公开接口接入。

## 1. 总目录

每个部分是**一个文件夹**。文件夹内的 `README.md` 同时是**二级描述**(本部分讲什么、边界在哪)与**二级索引**(下辖文件 + 何时读)。按下表先找到部分,再进该文件夹看细分主题。

| 文件夹 | 主题 | 什么时候读 |
| --- | --- | --- |
| [`00-总览/`](00-总览/README.md) | 定位与范围、两阶段模型、架构与文件职责、工程基线与验收 | 第一次接触本项目;改动跨模块边界时 |
| [`01-写入门禁/`](01-写入门禁/README.md) | 文件写入门禁、只读命令门禁、锚点解析、状态与持久化 | 改门禁;排查「某个写操作为什么被挡」 |
| [`02-文档规范/`](02-文档规范/README.md) | 话题文件夹布局、总纲与计划条目、决策归属与提交边界 | 改文档放哪、叫什么、提交怎么切 |
| [`03-规划流程/`](03-规划流程/README.md) | 提问式规划、子代理查证、成文与收尾、冲突回退 | 改 agent 在文档阶段被要求做什么 |
| [`04-扩展接口/`](04-扩展接口/README.md) | 命令与工具清单、上下文注入、状态栏与任务面板 | 加命令/工具;改注入文案;改状态显示 |
| [`05-测试与验收/`](05-测试与验收/README.md) | 测试分层、必测清单、手工验收清单、回归风险点 | 提交前;做回归 |

**建议阅读顺序**:`00 → 01 → 02 → 03 →（04）→ 05`。`03` 讲的是给模型的纪律(文案层),`01` 讲的是强制层(代码层);两者可以分别改,但改纪律前先确认强制层不会把它推翻。

## 2. 证据标注约定

文档里每个机制性论断后必须带证据,**只允许两类**:

| 写法 | 含义 |
| --- | --- |
| `src/state.ts:330` | 相对**本仓库**根目录的路径 + 行号 |
| `https://nodejs.org/api/path.html` | 外部规范、官方文档、平台官方说明 |

【规则】禁止在正文中引用第三方实现的文件路径、行号或代码。需要比对别的实现来定取值时,比对过程留在别处,不进本目录。

## 3. 内容标记

文档只写**本项目自己最终选定的实现方式**,不出现任何第三方扩展或产品的名称。三种标记:

| 标记 | 含义 | 写法要求 |
| --- | --- | --- |
| **【规则】** | 本文档规定本项目必须怎么做 | 直接给取值与验收标准 |
| **【依据】** | 该规则的来源与理由 | 只能是上表两类证据;必须写清「为什么这样定」 |
| **【不采纳】** | 明确放弃的做法 | 写清理由,防止后续有人补回来;只描述做法,不点名出处 |

## 4. 术语表

| 术语 | 含义 | 详见 |
| --- | --- | --- |
| **文档阶段 (writing)** | 只允许写 `docs/` 的阶段;执行阶段的文档冻结由它反向定义 | `00` |
| **执行阶段 (executing)** | `docs/` 冻结、仓库其余部分可写的阶段 | `00` |
| **门禁 (gate)** | 工具调用发生前的强制拦截点,不依赖模型自觉 | `01` |
| **话题 (topic)** | 一个长期维护的文档集合,对应一个文件夹 | `02` |
| **总纲 (overview)** | 话题文件夹内的主文档,`docs/<topic>/<topic>.md` | `02` |
| **条目 (entry)** | 计划拆分出的单个可独立验收项,一个文件 | `02` |
| **可变决策** | 已生效但用户可能想改的默认值,收尾时逐条过目 | `02` |
| **锚点 (anchor)** | 编辑器返回的 4 字符行引用,用于在不知道路径时定位文件 | `01` |
| **fail closed** | 目标形态可识别、但无法归属到唯一文件时判为不允许 | `01` |
| **scratch** | `.pi/tmp/`,子代理报告的落脚点,门禁放行 | `01` |
| **冲突回退** | 执行中发现文档与事实矛盾时中止执行、回到文档阶段 | `03` |

更细的字段级术语在各文档内就近定义。

## 5. 已知限制

- 本目录只描述**本项目自身**。它依赖 pi 宿主提供的钩子与工具接口,但不描述 pi 的实现。
- 门禁是**尽力而为**的静态检查,不是沙箱。判定基于工具名与参数文本,能拦住的用法在 `01-写入门禁/` 逐条列出,拦不住的同样列出。
- 本目录不含面向使用者的上手教程、发布说明或 API 参考(本扩展没有可生成文档的公共 API)。

## 6. 维护约定

1. 改门禁判定(放行/阻断的规则、清单成员):先改 `01-写入门禁/` 对应文件,再改代码。
2. 改文档放哪、文件怎么命名:先改 `02-文档规范/01-话题文件夹布局.md`。
3. 改给模型的纪律(阶段注入、收尾呈现、反模式):先改 `03-规划流程/`,并同步改动 `../skills/deep-plan/SKILL.md` —— 两者必须一致。
4. 加命令或工具:先改 `04-扩展接口/01-命令与工具清单.md`。
5. 改任何取值(条数上下限、补零位数、深度上限):先改对应文档,并在该处保留【依据】;**不得**只改代码。
6. 新增主题:在对应文件夹下加编号文件,并同步更新该文件夹 `README.md` 的文件索引与本文件的 §1 总目录。
7. 任何「做不到」的结论写进对应文档的**已知限制**一节,不写进设计正文当承诺。
8. 本目录只放**长期有效的设计**;修复过程、排查记录、A/B 结论、按日期排布的变化记录都不入文档(历史由 git 记录)。

## 已知限制

- 文档描述的是**设计契约**,与代码同步维护。`01`–`05` 的文件级论断都带 `src/*.ts:行号` 证据,行号会随代码改动漂移;改代码时按下表反向核对。
- 取值类条目(条数上下限、补零位数、命令深度上限)多数是本项目**首次规定**,没有外部权威可引;这类条目的【依据】写的是推导过程或约束来源,不是出处。
- 术语表刻意保持在 12 条;扩容前先考虑是否应放入对应文档的局部术语小节。
