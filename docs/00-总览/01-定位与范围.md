# 00 总览 / 01 · 定位与范围

## 1. 定位总览

pi-deep-plan 是一个编码代理扩展,该扩展把一次改动**强制划分为两个阶段**:先把「目标、依据、验收方式」写进 `docs/` 并交用户过目,用户批准后才允许动代码;动代码期间 `docs/` 被冻结。

本扩展的定位不是「辅助构思」的工具,而是**固定顺序**的工具:先文档后代码,顺序由门禁强制,不能依赖模型自觉。

## 2. 能力范围

| # | 能力 | 说明 | 详见 |
| --- | --- | --- | --- |
| S1 | **两阶段门禁** | 文档阶段只允许写 `docs/`;执行阶段冻结 `docs/`、放行仓库其余部分 | `02` |
| S2 | **写作阶段只读 shell** | 文档阶段连命令都只允许只读用法,防止以 shell 绕开文件门禁 | `../01-写入门禁/02` |
| S3 | **锚点解析** | 模型用行锚点编辑文档时,门禁仍能判定改的是哪个文件 | `../01-写入门禁/03` |
| S4 | **话题文件夹布局** | 一个话题一个文件夹,计划拆分出的条目各自成文件 | `../02-文档规范/01` |
| S5 | **收尾审查** | 文档写完先向用户呈现「可变决策(用户可能希望修改的默认值)」再请求批准 | `../02-文档规范/03` |
| S6 | **冲突回退** | 执行中发现文档与事实矛盾时中止执行并回到文档阶段,不得绕过 | `../03-规划流程/04` |
| S7 | **拦截记录与一次性放行** | 被拒命令写入 `.pi/deep-plan-blocked.log`;模型可为**实际只读**的单条命令申请一次性放行,用户批准后该命令执行一次 | `../01-写入门禁/05` |

## 3. 非目标范围

| # | 不做的 | 依据 |
| --- | --- | --- |
| N1 | **不代用户执行 git** | 扩展只声明提交边界与归属,不执行 `git commit`。若由扩展执行 git,「用户批准后才继续」这一约束将失去意义 —— 提交动作必须留在人可干预的位置 |
| N2 | **不做沙箱** | 门禁是工具调用前的静态判定,不是运行环境隔离。拦不住的用法逐条写在 `../01-写入门禁/` 的已知限制里 |
| N3 | **不禁止执行阶段的任何操作** | 执行阶段只冻结 `docs/`,不额外限制命令。此时用户已经批准过方案,追加限制将增加执行开销 |
| N4 | **不向用户提问** | 规划阶段的提问是 agent **自问自答**;用户只在收尾审查一次(见 S5)。依据是用户的时间只用于「决策」,不用于「供料」 |
| N5 | **不解析第三方 YAML 库** | frontmatter 用手写解析,只认 `---` 包裹的 `key: value` | 
| N6 | **不做增量的文档版本管理** | 文档是长期维护的完整文件,不是按日期排布的变更记录。历史由 git 承担 |
| N7 | **不做文档归档/回收** | 没有「旧方案归档到某个子目录」的机制。话题长期存在,过期结论由人改写 |
| N8 | **不生成公共 API 文档** | 本扩展没有对外暴露的公共 API |

N5 的【依据】:引入 YAML 解析库将新增一个只为 frontmatter 服务的依赖,而 frontmatter 只用到「字符串键值对」这一子集,`src/archive.ts:24` 的正则已足够覆盖。【规则】新增 frontmatter 字段时,必须确保值里不出现需要复杂转义的 YAML 结构。

## 4. 与「只写文档」「只写代码」两种做法的区别

| 做法 | 问题 |
| --- | --- |
| 直接改代码,改完补一段说明 | 说明是**事后叙述**,无法在动手前挡住错误方向;用户看到说明时实现成本已经付出 |
| 先写一份详细方案,再照着写代码 | 方案与代码之间没有强制关系,方案写完照样可以偏离方案;偏离时也没有回退动作 |
| **本项目** | 方案写完**必须经用户批准**才解锁代码(N2 之外的写操作此前被挡);执行中若发现方案与事实矛盾,**强制回退**到文档阶段(S6),不得在代码里打补丁 |

关键区别在偏离发生时产生的后果。前两种做法中,偏离的代价为零,故偏离成为常态;本项目的偏离有确定的代价(门禁挡住,或退回文档阶段),故两段顺序可持续。

## 5. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **门禁只覆盖已登记的工具名** | `tool_call` 先按工具名筛(`src/index.ts:177`)。名字不在 `FILE_MUTATION_TOOLS`(`src/state.ts:94`)里的写工具**不参与判定**,直接放行。新增写工具时必须同步登记,这是一处纯人工契约 |
| L2 | **无法验证文档是否「真的对」** | 门禁只能验证文档**存在且非空**(`src/index.ts:575`),不能判断内容是否自洽。质量仍靠纪律(`../03-规划流程/`)与用户审查 |
| L3 | **不检查计划条目编号连续** | 条目文件只要非空即通过。完整性由 `deep_plan_task` 承担,两者不互为真相 |
| L4 | **执行阶段的冻结是单向的** | 要改文档只能通过 `deep_plan_revise` 显式退出执行阶段;没有「临时改一行」的通道。这是刻意的,见 S6 |
| L5 | **依赖 pi 宿主的钩子接口** | 门禁挂在 `tool_call` 上(`src/index.ts:172`)。宿主不触发该钩子时,门禁整体失效 |
