# 01 写入门禁 / 05 · 拦截记录与临时放行

## 1. 定位

只读命令门禁的判定结果只有「放行」与「拒绝」两种(`02` §1)。本文件规定拒绝路径上的两项附加设施:

| 设施 | 触发方 | 产物 | 生命周期 |
| --- | --- | --- | --- |
| 拦截记录 | 门禁自动执行 | `.pi/deep-plan-blocked.log` | 跨会话累积 |
| 临时放行 | 模型经 `deep_plan_request_allow` 申请,用户批准 | 一条待用放行凭据 | 用掉、会话结束或下一轮 run 开始时失效 |

```
命令 → 只读判定 ──放行──→ 执行
           │
          拒绝 ──→ 有待用凭据且命令逐字相同? ──是──→ 用掉凭据,放行
                       │否
                       ↓
                 写入拦截记录 → 阻断
```

**【规则】** 两项设施仅在文档阶段生效。执行阶段不限制命令(`../00-总览/01` 的 N3),门禁在该阶段不读取本文件规定的任何状态(`src/index.ts:215`)。

## 2. 拦截记录

### 2.1 位置与形状

**【规则】** 每次拒绝向项目根目录下的 `.pi/deep-plan-blocked.log` 追加一行 JSON(`src/intercept.ts:18`、`src/intercept.ts:44-48`)。

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| `at` | string | ISO 8601 时间戳 |
| `phase` | string | 触发拒绝的阶段;只读墙仅存在于文档阶段 |
| `tool` | string | 承载命令的工具,`bash` 或 `powershell` |
| `command` | string | 提交的命令原文 |
| `reason` | string | 只读判定给出的拒绝原因 |

**【规则】** 一行一条记录。`JSON.stringify` 把命令里的换行写为 `\n` 转义,故多行命令仍然占一行(`src/intercept.ts:37-39`)。

**【依据】** 一行一条使记录可直接送入 `grep`、`wc -l`、`sort | uniq -c`。调白名单所需的统计是「哪些命令被拒了多少次」,JSONL 无需解析器即可给出该统计。

**【规则】** 记录文件位于 `.pi/` 下。本仓库根目录的 `.gitignore` 以 `*.log` 规则排除该文件(`.gitignore:2`)。

**【依据】** 记录是某台机器上某次运行的使用痕迹,不是项目设计的一部分;提交该文件会把本地调试数据混进版本历史。记录位置由扩展决定,是否提交由被使用项目自己的 `.gitignore` 决定。

### 2.2 写入时机

**【规则】** 写入发生在阻断之前,且不改变判定结果:先写记录,再返回阻断(`src/index.ts:228-246`)。

**【规则】** 记录写入失败时向用户发一条 `warning` 通知,命令仍被阻断(`src/index.ts:236-239`)。

**【依据】** 记录是判定之外的旁路。写入失败若导致放行,一条日志错误即构成绕过只读墙的通道;写入失败若导致不阻断,同样的错误也使约束失效。两种后果都源于把「记录」与「强制」合并,故记录失败只产生通知。

**【规则】** 记录只覆盖被拒绝的命令。文件写入门禁(`01`)的阻断不写入该文件。

**【依据】** 该文件的用途是调整只读白名单与逐命令参数规则(`02` §3–§5)。文件写入门禁做的是路径归属比较,其中不含可调的名单,不需要使用记录。

## 3. 临时放行

### 3.1 申请的前提

**【规则】** 申请只适用于**实际只读**的命令:该命令不写文件、不删除文件、不执行任意代码,只是未被只读墙的白名单或参数规则识别。典型情形是查看类命令因不在白名单而被拒(见 `02` §7 的 L3)。

**【规则】** 该前提由模型自行确认,并作为 `readOnly` 参数随申请一并提交(`src/index.ts:827-829`)。`readOnly` 为假时不发起申请,直接返回「未确认为实际只读的命令,不予申请」(`src/index.ts:840-850`)。

**【依据】** 只读墙无法判定的正是「这条命令是否只读」中依赖语义的那一部分,扩展因此不能验证该前提。把确认写成必需参数,使该判断成为申请流程里的一个显式动作,而不是被默认假设的一步。写类命令的申请因此必须经过一次显式声明与用户过目,不能静默通过。

### 3.2 申请与展示

**【规则】** 模型用 `deep_plan_request_allow command readOnly reason` 发起申请,用户在 UI 上从「放行一次」「拒绝」两项中选择(`src/index.ts:817-893`;参数表见 `../04-扩展接口/01` §2.1)。

**【规则】** 申请须携带理由,说明该命令实际只读的依据,以及该命令在文档阶段为何必要(`src/index.ts:830`)。UI 同时展示命令原文、模型自述与理由(`src/index.ts:869-872`)。

**【依据】** 用户批准的内容是「这条具体命令可以执行这一次」。命令原文使批准范围明确,理由与自述使用户具备判断依据;缺少任一项时,批准退化为对未知操作的授权。

### 3.3 不发起申请的情形

| 情形 | 返回 | 行 |
| --- | --- | --- |
| 当前是执行阶段 | 「没有只读墙,直接执行即可」 | `src/index.ts:834-839` |
| 未确认实际只读 | 「未确认为实际只读的命令,不予申请」 | `src/index.ts:840-850` |
| 命令为空 | 「命令为空,无法申请放行」 | `src/index.ts:852-854` |
| 命令本就通过只读判定 | 「本来就通过只读墙,无需申请」 | `src/index.ts:855-860` |
| 无 UI | 「取不到用户同意」并保持阻断 | `src/index.ts:861-868` |

**【规则】** 无 UI 环境下不发起申请,返回文案不得写成已批准(`src/index.ts:861-868`)。

**【依据】** 无 UI 时不存在取得批准的可能性。把「无法取得同意」当作同意,将使只读墙在无人值守的运行中失效。

### 3.4 凭据的生效与失效

**【规则】** 批准后把命令原文与所在 run 的 `startedAt` 写入内存(`src/index.ts:879-880`)。门禁放行该凭据与命令原文逐字相同的一次调用,并在放行时删除凭据(`src/index.ts:221-227`)。

**【规则】** 凭据比较在去除命令首尾空白后进行(`src/intercept.ts:50-52`)。其余差异均为不同命令:更长的命令、大小写不同、追加一段管道都不匹配。

**【依据】** 逐字比较使批准范围等于用户看到的命令。前缀匹配或子串匹配会让「批准 `rm x`」同时放行 `rm x && rm -rf src`,用户看到的与被执行的不再是同一件事。

**【规则】** 凭据只在与批准时相同的那一轮 run 内有效:`grantedRun` 与当前 `state.startedAt` 不同时,门禁不认该凭据(`src/index.ts:223`)。

**【依据】** 用户批准的是当前这轮规划里的一条命令。若凭据跨 run 生效,同一会话内开始下一轮规划时,一次批准即凭空放行一条未经批准的命令。

**【规则】** 凭据只存在于内存,不写入会话状态 —— `PlanState` 不含该字段(`04` §1)—— 并在 `session_shutdown` 时清除(`src/index.ts:124-125`)。

**【依据】** 批准是当次用户在场时作出的授权。持久化将使新会话凭空继承上一次的放行。凭据失效的途径有三种:被用掉、会话结束、开始新一轮 run。

## 4. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **「实际只读」不可由扩展验证** | `readOnly` 是模型的自述(`src/index.ts:827-829`)。门禁只检查该参数是否为真,不检查命令本身;判断由用户在看到命令与理由后作出 |
| L2 | **待用凭据只有一份** | 新的批准覆盖尚未使用的上一条批准(`src/index.ts:879`)。连续申请两条命令时,先批准的那条被后批准的覆盖 |
| L3 | **凭据不与承载工具绑定** | 凭据只记录命令文本(`src/index.ts:223`)。批准 `bash` 的某条命令后,`powershell` 提交同一文本同样被放行 |
| L4 | **记录不含被放行的命令** | 只有拒绝进入记录。批准与被放行的命令留在会话记录中,不写入该文件 |
| L5 | **记录文件不轮转** | 记录只追加,没有大小上限与轮转机制;持续被拒的运行会使其持续增长 |
| L6 | **记录保存命令原文** | 命令文本按原样写入,其中可能含本地路径等环境信息。该文件只在本机、且被 `.gitignore` 排除,读取记录时须注意内容 |
| L7 | **凭据在放行时即被删除** | 被放行的命令若执行失败(非零退出码),凭据同样已失效,需要重新申请 |
