# 项目文档格式

文档写在 `docs/` 下。**本次目标文档**由 `/deep-plan <目标> [--doc <路径>]` 决定;
阶段一期间 `docs/` 下**任意**文档与 `.pi/tmp/`(子代理报告)可写。

**范围是 harness 层的硬拦截。** 阶段一只放行 `docs/` 内的写入,`edit`/`write`/`replace`/
`replace_match`/`insert`/`copy`/`move`/`undo_last_change` 对 `docs/` 之外的写入会被直接阻断,
`bash`/`powershell` 只放行只读命令;被拦时不要用重定向或别的工具绕。
改已有文档要带 `path`(或整篇 `write` 覆盖),否则门禁无法判定目标而一律拦下。

## docs/ 是开发文档 (development)

`docs/` 就是本项目的**开发文档**,取代传统的根目录 `development.md`:
构建方式、测试命令、目录约定、各话题的设计**结论**都住在这里。

- **入口是 `docs/INDEX.md`**:一行一个话题并指向该话题的入口文件。新人从该文件开始读。
- 要写"项目怎么开发"这类内容时,写进 `docs/` 下的对应话题,**不要**在仓库根新建 `development.md`。

## 布局:话题是文件夹,计划条目是文件

`docs/` 下每**一个话题**是一个文件夹,话题内部的**每个计划条目**是一个文件:

```
docs/
  INDEX.md                     话题索引 / 开发文档入口
  <topic>/
    <topic>.md                 总纲:概览 / 目标与非目标 / 术语 / 风险 / 开放问题
    plan/NNNN-<slug>.md        一个计划条目一个文件
```

- 话题文件夹只在需要时建。旧的单文件话题 `docs/<slug>.md` 仍然合法(没有条目可分的文档
  不值得拆),但**别为同一话题再建一份平行文档** —— 就地完善已有的那份。
- 建文件夹**用 `write` 写第一个文件**(自动建父目录)。`bash mkdir` 被阶段一的只读门禁拒绝,
  不要试图绕过。
- 条目文件是**纯正文**,不写 frontmatter;frontmatter 只属于总纲。
- 编号用四位零填充(`0001`),文件系统排序即顺序。**不查编号连续性**:完整性由
  `deep_plan_task` 的任务清单承担,不靠文件名。

## 这是项目文档,不是变化记录

四条硬规矩,违反即退回:

- **不写按日期排布的变化记录 / 变更日志。** 变化交给 git,`git diff` 就是本次计划。
- **不写决策记录。** 决策会变(见下节),规定理由写进 **git commit message**。
- **不写一次性计划表 / 待办清单。** 要做拆解用 `deep_plan_task`(给执行阶段用,不进文档)。
- **维护完整、自洽。** 没有 TBD、没有留白、不与本文其余部分或 `docs/` 里其它文档矛盾。
  已有文档**就地完善**;新建文档要同步更新 `docs/INDEX.md`。

### 写作语体(违反即退回)

文档正文用**规范陈述语体**:陈述事实、规定要求、说明理由。判据是「该句可被当作规范条款宣读」。七项禁令:

| # | 禁止 | 改成 |
| --- | --- | --- |
| 1 | `他` / `它` / `他们` / `它们` 指代机制、文档、工具、字段 | 重复该对象的名称;指代人时用「用户」「执行者」「维护者」 |
| 2 | 疑问句与疑问式标题 | 名词短语:「为什么是这两个阶段」→「阶段划分依据」;「锚点是什么」→「锚点定义」 |
| 3 | 「动词 + 什么」短语 | 「做什么」→「能力范围」;「不做什么」→「非目标范围」;「不含什么」→「边界」;「会破坏什么」→「破坏对象」;「什么时候读」→「阅读时机」 |
| 4 | 「一句话」「说明白」「讲清楚」「讲明白」 | 「一句话定位」→「定位总览」;优先用 概括 / 总览 / 解释 / 说明 |
| 5 | 口语与比喻:悄悄 / 炸掉 / 顺手 / 拖慢 / 摸不着 / 很难发现 / 踩坑 / 麻烦 / 拉平 / 干掉 | 静默 / 导致失效 / (删除) / 增加开销 / 无法定位 / 不易察觉 / 缺陷 / 开销 / 展平 / 删除 |
| 6 | 第二人称「你」「您」 | 角色名,或改为无人称陈述 |
| 7 | 【依据】写成口语推理 | 规范陈述:不用比喻拟人、不反问;因果用「因…故…」「…将导致…」 |

**不受约束、按原文保留**:代码块与标识符、命令行、正则、工具返回文案、引文、参数示例(如 `reason="<具体的冲突是什么>"`)、术语与固定语。引用原文时**不得**为迁就语体而改写被引内容。

`其他` / `其余` / `其它` 是限定词,不属禁令 1。

注意:上表禁令针对**叙述**部分;直接指示行动的祈使句(「不要写变更日志」「先改文档再改代码」)是规范文本的正常构成,照常使用。

完整定义见 `docs/INDEX.md` §3.1 与 `docs/02-文档规范/04-写作语体.md`。

### 文档只留结果,决策留在 git commit

**决策是变值,不是定值。** 一条决策今天写进文档,几轮问答后很可能被推翻;而文档是
**长期维护**的,把会被推翻的推理固化进去,等于持续制造自相矛盾。commit 是**时间点快照**,
天然记录议题在当时确定下来的理由,`git log` 就是决策的演进史。

| 内容 | 写在哪 |
|---|---|
| 术语 / 规范用语 / `_Avoid_` | 文档的术语小节 |
| 目标 / 非目标 | 文档 |
| 风险与回滚 | 文档 |
| 计划(可独立验收的条目) | 文档 + `deep_plan_task` |
| 提问式规划的问答过程 | 不落盘(过程不是产出) |
| **规定理由与否决事项** | **git commit message** |

所以:**不要建 `docs/<topic>/decisions/`,不要建 `docs/adr/`,不要写「决策记录」小节。**
拿到结论后把结论变成结果性内容:选定的做法进「计划」,定下的词进「术语」,
划掉的范围进「非目标」。收尾提交时把决策与理由写进 commit message 正文。
## 骨架

````md
# <文档标题：这份文档覆盖什么>
> 这是长期维护的项目文档。不要写变更日志、日期版本或一次性计划表。

## 概览
3-5 句:现状、目标状态、实施时机依据。

## 目标 / 非目标
- 目标: <可验收的陈述>
- 非目标: <明确排除的范围>（没有非目标的方案不可信）


## 术语与领域模型

本项目的**规范用语**与**刻意避免的说法**。只放本项目特有的概念,不放通用编程概念。
术语是列表语义,天然是文件内结构 —— **不要**拆成单独的文件。

格式:

```md
**<规范术语>**:
<简要说明该术语的定义,界定「是什么」而非「做什么」>
_Avoid_: <被否决的同义词>
```

- 有多个词指同一概念时,选最准的那个,其余进 `_Avoid_`。
- 定义控制在一两句话。
- 术语自然成组时才加子标题;只有一组就平铺。

**<规范术语>**:
<简要说明该术语的定义>
_Avoid_: <被否决的同义词>

## 可变决策
**这是用户唯一需要逐项过目的部分。** 表格见下节。

## 计划
本次要做的改动,写成能独立验收的条目(**不是**待办清单,执行状态由 `deep_plan_task` 管):

1. <动作> — 验收: <怎么确认这步成了>
2. ...

## 风险与回滚
| 风险 | 触发信号 | 应对 | 回滚方式 |

## 开放问题
查证不到的事实,写「未能查证 + 已尝试的检索路径」。不要编造。
````

## 可变决策表 schema

每行一个决策。四列缺一不可:

````md
| # | 决策项 | 默认值 | 依据 | 改动代价 |
|---|--------|--------|------|----------|
| V1 | <决策项> | **<Agent 已选的默认值>** | <依据> | 低/中/高 + 改动影响 |
````

规则:

- **默认值必须是已生效的**,不是待定的。
- **依据**要给证据(文件路径:行号 / URL / 命令输出),不是形容词。
- **改动代价**回答"用户改了这一项,哪些步骤要跟着变"。
- 只放**用户可能有不同偏好**的项:取舍、范围、依赖引入、落盘位置、命名、
  是否新增文件、触发方式。不要放纯技术事实。
- 控制在 3-8 行。超过 8 行说明该拆成多份文档;少于 3 行说明自问不够狠。
- 用户改动后,把改动落进文档的相应小节(选中做法进「计划」、定下的词进「术语」、
  划掉的范围进「非目标」),并把这次改动的理由写进 git commit message。

## 收尾呈现契约

文档写完后,`deep_plan_review` 校验通过,**一次**呈现:

1. 文档路径 —— 写成 markdown 链接(结果里已给好,原样复制),**不要把正文贴进对话**。
2. 可变决策表全文。
3. 任务清单。
4. 下一步:**先只提交文档**(`git add docs/ && git commit -m "docs: ..."`)。
   提交归属按**本轮对话的指令**:默认由执行者提交;用户若说"提交由我来",就交给用户。
   提交完成后再问是否批准进入执行阶段。
5. 进入执行阶段后的**代码单独成一个 commit**,和文档那次分开 —— 这条不变。

呈现后停住,等用户回话。不要在同一轮里既呈现又开工。
提交按上面的归属规则做;归属不明时先问,不要猜。
