# 03 规划流程 / 02 · 子代理查证

## 1. 分工

**【规则】** 查证阶段的一切**事实**由子代理查,绝不问用户;决策由 agent 自己下(`references/research-contract.md`)。

| 谁 | 负责 |
| --- | --- |
| 子代理 | 提供事实与证据(现有代码什么样、某规范怎么规定) |
| agent | 下决策、写方案、写文档 |

**【依据】** 事实检索是**可外包的体力活**:读 10 个文件、查 3 个来源,结论可能只有两句。把它放进主上下文会挤掉方案本身所需的空间。而决策无法外包 —— 它需要全部上下文。

## 2. 派发规则

| 规则 | 内容 |
| --- | --- |
| 一次启动全部 | 用**一次** `subagent` 调用的 `children` 数组,不拆成多次调用 |
| 并发 ≤ 3 | 启动开销数千 token,无并行收益就不堆数量 |
| 简报自包含 | 子代理看不到当前对话;必须写清目标、路径、约束、期望输出格式 |
| 任务不重叠 | 每个子代理负责不同模块/主题,避免重复劳动 |
| 先验证再采信 | 报告回来先核对文件存在性、输出非空、结论有路径行号支撑 |
| 报告落 scratch | 写到 `.pi/tmp/`,不让子代理往仓库里写正式产物 |

**【依据】** 「一次启动全部」是因为多次串行调用会让后启动的子代理在时间上落后前一批,失去并行收益;`children` 数组保证它们同时开始。并发上限 3 来自启动成本与协调开销的权衡 —— 每多一个子代理,主对话就要多收一份报告并多验证一遍。

**【依据】** 「先验证再采信」是必需的:子代理是帮手,不是权威。它的报告可能有幻觉、有过时结论、有根本没跑的命令。采信未验证的结论等于把幻觉写进文档。

**【规则】** 子代理**不往仓库写正式产物**,报告落在 `.pi/tmp/`。

**【依据】** scratch 目录在两个阶段都可写(`../01-写入门禁/04` §2),而 `docs/` 只在文档阶段可写。让报告走 scratch,使查证在两个阶段都不受门禁影响;同时报告是**过程产物**,不该混进 `docs/` 的正式内容。

## 3. 可用代理

| 代理 | 用途 |
| --- | --- |
| `researcher` | 联网事实调研,多角度检索 + 交叉验证,产出带 URL 的报告 |
| `scout` | 只读代码库侦察,返回文件路径:行号级别的现状地图 |
| `code-reviewer` | 对已有改动做无偏见审查 |

**【规则】** 派发时用**精确的代理名**,不新造专用代理。

**【依据】** 代理定义过多会降低选择准确性 —— 每个新名字都要在「这个任务该派给谁」上多一次判断,而判断的收益随名字增多而下降。

## 4. 报告大纲

**【规则】** 子代理按下面的结构返回:

```
Verified Facts             每条附证据(路径:行号 或 URL)
Open Unknowns              查不到的、需上级决策的
Design Question Evidence   哪些自问自答的问题因此有了答案
Plan Readiness             ready / ready-with-assumptions / blocked
```

**【规则】** **只证明现状,不给方案。** 方案是 agent 的活。每个结论必须可追溯;没有证据的推断标 `[推断]`,**不得**混入 `Verified Facts`。

**【依据】** 子代理看不到完整上下文,它的方案建议会建立在局部视野上,采信反而有害。要求它「只证明现状」把它的输出限定在它真正擅长的范围:事实。

**【依据】** `[推断]` 标记让「有证据的结论」与「推理出来的结论」在报告里可见地分开。混在一起时,读者无法分辨哪些可以直接进文档、哪些还需要验证。

**【规则】** `Design Question Evidence` 一节把报告与提问式规划**接起来**:它说明哪些 frontier 问题因为这份报告有了答案。

**【依据】** 没有这一节,报告就成了一份孤立的事实清单;agent 得自己做「哪些事实解决了哪个问题」的对应。让子代理做这件事,使结论直接进入规划。

## 5. 停止查证的判据

**【规则】** 下面四条**全部**满足才进入成文(`references/research-contract.md`):

| # | 条件 |
| --- | --- |
| 1 | 设计树上每个 frontier 问题都有答案(查证得来或自己下的决策) |
| 2 | 没有低置信度的答案被当成高置信度用 —— 低置信度的都进了「可变决策表」 |
| 3 | 没有未解决的来源冲突;有冲突的写进「开放问题」并标注双方来源 |
| 4 | 「计划」的每一步都能说出验收方式 |

任一不满足 → 继续查证或继续自问,**不要**把问题抛给用户。

**【依据】** 第 2 条是关键的低置信度出口:一个不确定的结论有两种处理 —— 硬写成结论(错),或暴露给用户让他决定(对)。可变决策表正是「暴露」的位置。第 3 条把无法解决的矛盾显式化,而不是静默地选一边。

## 6. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **子代理报告不进版本库** | 落在 `.pi/tmp/`,会话结束即可能被清理。因此查证过程不可追溯(追溯靠最终文档与 git) |
| L2 | **代理名清单是宿主的** | 表中三个代理由宿主环境提供;环境里没有对应定义时,派发会失败 |
| L3 | **报告质量无法自动校验** | 「每条结论附证据」靠子代理自觉;主对话只能人工核对 |
| L4 | **并发 ≤ 3 无强制** | 只是纪律,派发更多不会被拦。真正的成本是多份报告的验证开销 |
| L5 | **scratch 内容不受门禁约束** | 它在两个阶段都可写,因此子代理写什么都不会被检查 |
