# 00 总览 / 02 · 两阶段模型

## 1. 两个阶段

状态只有两个取值,由 `Phase` 定义(`src/state.ts:49`):

```ts
export type Phase = "writing" | "executing";
```

| 阶段 | 中文名 | 可写 | 可读 | 命令限制 |
| --- | --- | --- | --- | --- |
| `writing` | 文档阶段 | **只有 `docs/`**(外加 scratch) | 全仓库 | **只读命令**,写类命令一律拒绝 |
| `executing` | 执行阶段 | 仓库其余部分,**`docs/` 冻结** | 全仓库 | 无额外限制 |

**【规则】** 两个阶段合起来覆盖整个仓库,不存在第三种「无限制写入」的中间态。未启动时(`active === false`)门禁整体关闭(`src/state.ts:331`),这是唯一例外。

## 2. 判定顺序

`isWriteAllowed()` 的判定为**有序**判定,顺序本身是契约(`src/state.ts:330-340`):

| # | 判定 | 结果 | 行 |
| --- | --- | --- | --- |
| 0 | `!state.active` | 放行 | `:331` |
| 1 | 目标在 scratch(`.pi/tmp/`)内 | 放行 | `:333-337` |
| 2 | `phase === "executing"` | 放行当且仅当**不在** `docs/` 内 | `:338` |
| 3 | 其余(即 `writing`) | 放行当且仅当**在** `docs/` 内 | `:339` |

**【依据】** scratch 判别必须先于阶段判别(`:333` 在 `:338` 之前),否则文档阶段无法接收子代理报告 —— 而子代理报告不是设计产物,不应占用 `docs/`。因 scratch 被规定为「无条件放行」而非「文档阶段的例外」,故 scratch 在两个阶段行为一致。

`isDocPath()` 用的是 `path.relative` 边界测试,不是字符串前缀(`src/state.ts:191-194`):

```ts
const rel = path.relative(path.resolve(cwd, DOCS_DIRNAME), path.resolve(target));
return rel !== "" && !rel.startsWith("..") && !path.isAbsolute(rel);
```

**【依据】** 前缀测试会将 `docsite/x.md` 误判为文档(该路径以 `docs` 开头)。`path.relative` 加 `..` 判定是路径包含关系的正确写法:https://nodejs.org/api/path.html#pathrelativefrom-to。`rel !== ""` 排除 `docs/` 目录自身。

## 3. 阶段划分依据

**【规则】** 阶段的划分依据是**错误代价的承担方**,不是「工作内容」。

| 阶段 | 错误代价的承担方 | 由此允许 |
| --- | --- | --- |
| 文档阶段 | 用户(要读、要审) | 只有可被人一眼看完的文本产物 |
| 执行阶段 | 代码库(已批准的方向落地) | 全部写操作 |

**【不采纳】** 不设独立于 writing 的「review 阶段」。本项目的早期实现曾设三个阶段(`planning` / `review` / `executing`),现已折叠为两个 —— 见 §5。

## 4. 阶段转移

转移**只能**由显式工具调用触发,不存在任何自动转移:

| 从 | 到 | 触发 | 行 |
| --- | --- | --- | --- |
| (未启动) | `writing` | `/deep-plan`、`deep_plan_start` | `src/index.ts:344`、`:450` |
| `writing` | `executing` | `deep_plan_approve`(用户批准) | `src/index.ts:634` |
| `executing` | `writing` | `deep_plan_revise`(发现文档冲突) | `src/index.ts:696` |
| 任意 | (未启动) | `deep_plan_finish` | `src/index.ts:757` |

**【规则】** `writing → executing` 这一步**必须是人的动作**。`deep_plan_approve` 的存在意义即把「解锁代码」绑定在用户身上;模型不得自行跨越该步骤。
**【不采纳】** 不做「模型判定方案已足够好就自动进入执行」。判定标准无法客观化,自动跨越等于取消 S5 的审查点。

## 5. 状态的持久化与折叠

状态由 `toPersisted()` / `fromPersisted()` 显式逐字段拷贝(`src/state.ts:415`、`:432`),不依赖 JSON 序列化的隐式行为。

折叠规则在恢复时生效(`src/state.ts:441-443`):

```ts
phase: d.phase === "executing" ? "executing" : "writing",
```

**【依据】** 旧版本的状态中定义了 `planning` / `review` 两个已不存在的取值。任何非 `executing` 的历史值均被折为 `writing` —— 该折叠指向**安全方向**:旧会话恢复后落在受限较多的阶段,不会因版本升级而意外获得对代码的写权限。

**【规则】** 新增 `Phase` 取值时,必须同时更新这条折叠,并明确新值在旧版本里应折成哪一边。默认折向受限的一侧。

## 6. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **阶段与「思考」无关** | 阶段仅描述**写权限**,不描述 agent 的工作内容。执行阶段同样可以读文档、可以规划 |
| L2 | **执行阶段不限制命令** | `src/index.ts:198` 在 `executing` 时直接跳过只读检查。方案已获批准后不再以命令白名单增加执行开销 |
| L3 | **折叠会丢失历史阶段** | 旧会话恢复后被识别为 `writing`,原 `review` 的语义(「已收尾待批准」)不再被保留。因该语义现由 `deep_plan_review` 的执行本身表达,不需要状态位 |
