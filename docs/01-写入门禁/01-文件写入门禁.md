# 01 写入门禁 / 01 · 文件写入门禁

## 1. 拦截范围

只拦**改变文件内容的工具**,按工具名判定(`src/state.ts:94-103`)。集合 `FILE_MUTATION_TOOLS` 有 8 个成员:

| 工具名 | 来源 | 参数形态 |
| --- | --- | --- |
| `edit` | 内置 | 显式 `path` |
| `write` | 内置 | 显式 `path` |
| `replace` | 行锚点编辑器 | 锚点 |
| `replace_match` | 行锚点编辑器 | 锚点 |
| `insert` | 行锚点编辑器 | 锚点 |
| `copy` | 行锚点编辑器 | 锚点 |
| `move` | 行锚点编辑器 | 锚点 |
| `undo_last_change` | 行锚点编辑器 | 显式 `path` |

**【规则】** 新增任何能改文件的工具时,**必须**把该工具加进这个集合,否则门禁对该工具**完全无效**。

**【依据】** 判定基于工具名而非「参数里看似有路径」—— 后者会误伤只读工具(如 `read` 也有 `path`)。该选择的代价是漏登记时**拦不住**(静默放行,见 §3),而不是**误拦**(误拦会挡掉正常开发,更不易察觉)。选择前者的依据是:误拦会立刻被察觉并修掉,漏登记只在有人专门核查这张表时才暴露 —— 这是本项目最重要的一处人工契约。

**【不采纳】** 不拦 `read` / `grep` / `find` 等只读工具 —— 文档阶段需要读遍整个仓库才能写好文档。

## 2. 目标路径来源

门禁需要知道「本次调用改的是哪个文件」,而写工具分两类(`src/state.ts:350`、`:353-359`):

| 类别 | 字段 | 工具 |
| --- | --- | --- |
| 显式路径 | `path` / `file` / `file_path` | `edit`、`write`、`undo_last_change` |
| 行锚点 | 见下 | `replace`、`replace_match`、`insert`、`copy`、`move` |

锚点字段表:

| 工具 | 锚点参数 |
| --- | --- |
| `replace` | `remove_from`、`remove_to` |
| `replace_match` | `replace_from`、`replace_to` |
| `insert` | `anchor` |
| `copy` / `move` | `source_from`、`source_to`、`insert_after` |

## 3. 判定顺序

`extractWriteTarget()`(`src/state.ts:381-406`)按下列顺序得出一个结论:

| # | 情况 | 返回值 | 含义 | 行 |
| --- | --- | --- | --- | --- |
| 1 | 有显式 `path` 字段 | 该路径 | 直接可用 | `:384` |
| 2 | 无显式路径,也**无任何锚点字段** | `undefined` | 参数形态不认识 | `:387` |
| 3 | 有锚点字段但无解析器 | `""` | 锚点无从解析 | `:389` |
| 4 | 锚点未解析成功 | `""` | 无法归属 | `:396-404` |
| 5 | 多个锚点指向**不同**文件 | `""` | 归属不唯一 | `:396-404` |
| 6 | 全部锚点指向同一文件 | 该路径 | 可用 | `:405` |

**【规则】** 三类返回值在门禁里的处理(`src/index.ts:161-194`):

| 返回值 | 行为 | 触发条件 | 文案要点 |
| --- | --- | --- | --- |
| `undefined` | **拦截** | 工具在 `FILE_MUTATION_TOOLS` 里,但参数既无路径也无锚点 | 「目标路径无法确定」 |
| `""` | **拦截** | 有锚点但无法归属,或锚点指向不一致 | 「锚点无法定位到文件」,并建议先 `read` 或改用 `write` |
| 路径 | 交给 `isWriteAllowed()` | 路径可用 | 阶段文案 |

**【规则】** 全部三类 **fail closed**(不确定即拦),不存在「不确定就放行」的分支。

**【依据】** 放行一个无法归属的写操作,即构成一条绕过全部阶段约束的通道。拦截的代价是可能挡住合法操作,但错误信息明确指出了补救方式(先 `read` 或改用 `write`),模型能自行恢复;放行的代价是门禁形同虚设且**不会留下任何信号**。因两侧代价不对称,故选择拦截。

**【规则】** 门禁**先按工具名筛**,只有 `FILE_MUTATION_TOOLS` 里的工具才会进入 `extractWriteTarget`(`src/index.ts:161`)。

**【依据】** 这意味着 `extractWriteTarget` 的 `undefined` 分支**只对已登记的工具可达**:一个名字不在表里的写工具(如某个新加的工具)**不会触发门禁**,而不是触发后拿到 `undefined` 被拦。由此可得:

- 「未登记的新写工具会被拦」这一表述不成立,实际情况为该写工具会被**放行**。
- `undefined` 分支的实际作用是:一个**已登记**的工具被以不认识的参数形态调用时(例如 `write` 没有 `path`),该调用被拦。

**【依据 —— `undefined` 分支的保留理由】** 该分支防止「工具名对但参数形态变了」(例如 `edit` 改用了新的字段名)的情况,使这类变化 fail closed,而不是静默放行。该分支**不**防新工具 —— 新工具靠维护 `FILE_MUTATION_TOOLS` 表来覆盖(`../../00-总览/01` 的 L1)。

**【不采纳】** 不做「截获到未登记的写工具就放行并记一条日志」—— 日志在 agent 会话里无人查看,等价于放行。

## 4. 多锚点必须一致

当一个调用带多个锚点时,`extractWriteTarget` 要求**每一个**锚点都解析成功,**且全部指向同一个文件**(`src/state.ts:396-404`)。

```
replace(remove_from="abXy", remove_to="cdZw")
        │                    │
        └── 都解析到 a.md ────┴──→ 返回 a.md
        │
        └── 一个解析到 a.md,另一个解析到 b.md ──→ 返回 "" (拦截)
        │
        └── 一个解析到 a.md,另一个从未被服务过 ──→ 返回 "" (拦截)
```

**【依据】** 混合情况曾是真实漏洞:早期实现只要**任一**锚点位于允许的路径上即放行,于是「一个锚点在 `docs/` 的文档里、另一个锚点在源码里」的多锚点编辑能穿过门禁。要求全集合一致把这种构造封死。回归测试见 `../05-测试与验收/01`。

## 5. 阻断文案

三种文案的原文(`src/index.ts:166-191`),动机见 `../03-规划流程/`:

| 场景 | 文案 |
| --- | --- |
| 目标无法确定 | `deep-plan 写保护:<工具> 的目标路径无法确定,已阻止。` + 「文档阶段只允许写 docs/ 下的文档;执行阶段只允许写 docs/ 外的仓库文件。」+ 当前文档路径 |
| 锚点无法定位 | `deep-plan 写保护:<工具> 的锚点无法定位到文件,已阻止。` + 「(先 read 目标文件让锚点可解析,或改用 write 整篇覆盖)」 |
| 阶段不允许 | **文档阶段**:`deep-plan 文档阶段:只能修改 docs/ 下的文档。` + 被阻止的路径 + 「(子代理报告可写 .pi/tmp/ 下的 scratch 文件)」<br>**执行阶段**:`deep-plan 执行阶段:docs/ 已冻结,随文档一起提交。` + 被阻止的路径 + 「要改文档请用 deep_plan_revise 回到文档阶段。」 |

**【规则】** 每条拒绝文案必须包含**补救动作**(应改用的工具,或应调用以回到允许阶段的工具)。仅写「不允许」的文案会导致模型反复重试同样的调用。

## 6. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **仅判定工具名:未登记即完全不设防** | `tool_call` 先按工具名筛(`src/index.ts:161`),名字不在 `FILE_MUTATION_TOOLS` 里的写工具**不进入判定**,直接被放行 —— 不是「拦不住」,而是「不参与」。新增写工具时必须登记(见 §3) |
| L2 | **不解析工具的真实语义** | 门禁信任参数名。`path` 里写的路径是否确为工具将写入的文件,门禁无法验证 —— 门禁不读工具实现 |
| L2b | **路径按进程 cwd 解析** | `extractWriteTarget` 用 `path.resolve(resolved)`(`src/state.ts:403`),不接收 `cwd` 参数;而 `isWriteAllowed` 用传入的 `cwd`(`src/state.ts:332`)。二者在正常运行下相同(会话 cwd 即进程 cwd),但测试或嵌入场景里若两者不同,锚点编辑的判定会错位 |
| L3 | **锚点表需与编辑器同步** | 编辑器新增一种锚点参数名时,`ANCHOR_FIELDS` 必须同步(`src/state.ts:353`),否则新参数会被当成「外来工具」而导致整个调用被拦截 |
| L4 | **`copy` / `move` 不能跨文件** | 三个锚点里 `insert_after` 是目标位置,全集合一致性判定要求该锚点也位于同一文件,因此跨文件移动会被返回 `""` 拦下(`src/state.ts:405`)。文档阶段不构成障碍(移动只在 `docs/` 内),但执行阶段需要跨文件搬代码时只能改用 `write` + `edit` 两步 |
| L5 | **不处理目录级操作** | 门禁只处理带文件路径的调用。建目录依赖 `write` 自动创建父目录,不依赖 `mkdir`;`mkdir` 由 `02` 的命令门禁负责 |
