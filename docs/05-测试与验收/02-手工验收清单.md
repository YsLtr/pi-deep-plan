# 05 测试与验收 / 02 · 手工验收清单

## 使用方式

**【规则】** 本清单的每一条都在一个临时目录里执行,不接触真实仓库。验证方式:**令 agent 在门禁生效时尝试该操作,观察是否被拦,以及拦下时的文案是否与预期一致**。

**【规则】** 每条都必须验证**两侧**:被拦的确实被拦,该放行的确实放行。仅验证拒绝会漏掉「拦得过宽」,仅验证放行会漏掉「拦得不够」。

**【依据】** 门禁的错误有两个方向,而两个方向需要不同的检查:过窄(该拦未拦)会使约束失效,过宽(不该拦却拦)会挡住正常开发。本清单里绝大多数步骤都是成对的。

下表九组对应 `../00-总览/04` §3 的 A1–A9。

## A1 · 启动后的阶段与状态栏

| 步骤 | 预期 |
| --- | --- |
| 执行 `/deep-plan 验收目标 --doc docs/acc-topic/` | 收到通知:阶段为「第一阶段:文档」、「新建文档: …/docs/acc-topic/acc-topic.md」、「两段提交是分开的」 |
| `/deep-plan-status` | 显示阶段、文档路径、可变决策(此时为空) |
| 观察状态栏 | `◐ deep-plan: 文档阶段 (仅 docs/ 可写)` |
| 观察任务面板 | **不显示**(尚无任务) |

**【规则】** 状态栏文案必须同时含「文档阶段」与「仅 docs/ 可写」。

**【依据】** 见 `../04-扩展接口/03` §2:用户不应需要理解「文档阶段」这个术语即可判断当前能否修改代码。

## A2 · 文档阶段的文件写入

| # | 操作 | 预期 |
| --- | --- | --- |
| 1 | 写 `src/x.ts` | **被拦**:「deep-plan 文档阶段:只能修改 docs/ 下的文档」+ 被阻止的路径 + scratch 提示 |
| 2 | 写 `docs/acc-topic/acc-topic.md` | **通过** |
| 3 | 改 `README.md` | **被拦**(同上) |
| 4 | 写 `.pi/tmp/report.md` | **通过**(scratch) |
| 5 | 写 `docs/` 下不存在的深层路径(如 `docs/acc-topic/plan/0001-a.md`) | **通过**,且父目录被自动创建 |

**【依据】** 第 4 条验证 scratch 先于阶段判定(`../00-总览/02` §2 的顺序)。第 5 条验证「建目录靠 `write` 而非 `mkdir`」。

## A3 · 文档阶段的命令门禁

| # | 命令 | 预期 |
| --- | --- | --- |
| 1 | `mkdir -p docs/x` | **被拦**:「被禁止的命令: mkdir」 |
| 2 | `rm -rf src` | **被拦**:「被禁止的命令: rm」 |
| 3 | `echo x > out.txt` | **被拦**:「重定向 > 会写文件」 |
| 4 | `ls -la` | **通过** |
| 5 | `grep -rn "a\|b" src/` | **通过**(引号内的分隔符不误判) |
| 6 | `git status` | **通过** |
| 7 | `git commit -m "x"` | **被拦**:「不在只读白名单」 |
| 8 | `cat x 2>&-` | **通过**(关闭描述符无害) |
| 9 | `du -sh x >& file` | **被拦**(省略 fd 号的重定向仍是写文件) |
| 10 | `cat x 2>/dev/null` | **通过** |

**【规则】** 第 5、7、9、10 四条是关键用例,不能省略。

**【依据】** 第 5 条验分词(引号内的 `|` 是数据);第 7 条验「白名单父命令的子命令仍受限」;第 9 条验 `>&` 的区分规则(`../01-写入门禁/02` §4);第 10 条验 `> /dev/null` 豁免。前三条对应历史上真实出现过的误判或漏判。

## A4 · 锚点编辑

| # | 操作 | 预期 |
| --- | --- | --- |
| 1 | `read` 一份 `docs/` 下的文件,然后按锚点 `replace` | **通过** |
| 2 | `read` 一份仓库文件,然后按锚点 `replace` | **被拦**:「文档阶段:只能修改 docs/ 下的文档」 |
| 3 | 用**本会话从未被服务过**的锚点 `replace` | **被拦**:「锚点无法定位到文件」+ 建议先 `read` 或改用 `write` |
| 4 | 一次 `replace` 的两个锚点分属 `docs/` 与仓库 | **被拦**(混合锚点) |
| 5 | 用不带 `path` 的 `write` 调用 | **被拦**:「目标路径无法确定」 |
| 6 | 用带 `path` 的 `write` 写 `docs/` | **通过** |

**【规则】** 第 4 条是必测的回归项。

**【依据】** 第 4 条对应一个真实漏洞:早期实现只要**任一**锚点位于允许路径上即放行,于是混合锚点的编辑能穿过门禁(`../01-写入门禁/01` §4)。

**【依据 —— 第 5 条的预期文案】** 第 5 条验证的是「已登记工具的参数形态不完整」,而不是「未登记的新工具」。**名字不在 `FILE_MUTATION_TOOLS` 里的工具不会被拦**(`../01-写入门禁/01` §3 的依据),该项没有可执行的验收动作,只能靠核查那张表。

## A5 · `deep_plan_review` 的退回条件

按顺序执行,每步都应**退回并指名原因**:

| # | 状态 | 预期退回原因 |
| --- | --- | --- |
| 1 | 可变决策 0 条 | 「可变决策只有 0 条(要求 3-8 条):自问深度不足」 |
| 2 | 可变决策 3 条、任务 0 条 | 「没有任务拆解(deep_plan_task action=add)」 |
| 3 | 任务已建、`plan/0001-a.md` 是空白 | 指出 `plan/0001-a.md` |
| 4 | 条目文件写入正文 | **通过**,返回「文档阶段完成」+ 决策表 + 任务清单 |

**【规则】** 第 1–3 条的退回原因必须**累积报出**,而不是每次只报一条。

**【依据】** 见 `../02-文档规范/02` §5:三条检查互相独立,一次报全使用户能在一轮里改完。

## A6 · 批准进入执行阶段

| 步骤 | 预期 |
| --- | --- |
| `deep_plan_approve` | 返回「已批准,进入第二阶段:执行」 |
| 观察状态栏 | `▶ deep-plan: 执行阶段 (docs/ 冻结)` |
| 观察任务面板 | **现在开始显示**,首行是任务标题 |

**【规则】** 面板必须在这一步之后才出现。

**【依据】** 见 `../04-扩展接口/03` §3:面板的出现本身即「已进入执行阶段」的信号。

## A7 · 执行阶段的写入

| # | 操作 | 预期 |
| --- | --- | --- |
| 1 | 写 `src/y.ts` | **通过** |
| 2 | 写 `docs/acc-topic/acc-topic.md` | **被拦**:「docs/ 已冻结,随文档一起提交」+ 建议用 `deep_plan_revise` |
| 3 | 按锚点 `replace` 改 `docs/` 下文件 | **被拦**(同上) |
| 4 | 任意命令(如 `rm -rf /tmp/nothing`) | **通过**(执行阶段无命令限制) |

**【依据】** 第 4 条验证「执行阶段跳过只读门禁」(`../00-总览/01` 的 N3)。

## A8 · 冲突回退

| 步骤 | 预期 |
| --- | --- |
| 1 | `deep_plan_step action=start` 开始 T1 |
| 2 | `deep_plan_revise conflict=true reason="文档说 A,代码是 B"` | 返回「已**中止本次执行**」+ 原因 + **列出受阻任务 T1** + 提示用 `unblock` 恢复、不要当作已完成 |
| 3 | 观察状态栏 | 回到 `文档阶段` |
| 4 | 观察下一轮注入文案 | 含「**本次执行因文档冲突被中止**: 文档说 A,代码是 B」 |
| 5 | `deep_plan_task action=list` | T1 状态为 `blocked` |
| 6 | `deep_plan_approve` 重新批准 | 阶段回到执行阶段,**注入里不再出现中止原因** |
| 7 | `deep_plan_task action=list` | T1 **仍是 `blocked`**(批准不清除任务状态) |

**【规则】** 第 2 步必须**列出受阻任务**;第 4 步必须**出现原因**;第 7 步必须**仍受阻**。

**【依据】** 第 2、4 步的动机见 `../03-规划流程/04` §5–§6(任务不能在前提被重写时保持 active;模型需知道上次的中止原因)。第 7 步区分了两件事:批准清除的是 `haltReason`(`src/index.ts:632`),不是任务状态 —— 任务必须靠 `unblock` 显式恢复(`../03-规划流程/04` §6)。

## A9 · 结束

| 步骤 | 预期 |
| --- | --- |
| `deep_plan_finish outcome="…"` | 返回「已结束」+ 文档定稿位置 + 「两段提交应当是分开的」 |
| 写 `src/z.ts` | **通过**(门禁关闭) |
| 写 `docs/a.md` | **通过**(门禁关闭) |
| 执行 `rm -rf x` | **通过** |
| 观察状态栏 | **清空** |
| 观察下一轮注入文案 | **消失**(不再是 deep-plan 上下文) |

**【依据】** 后两行验证「纪律只在本循环内有效」(`../04-扩展接口/02` §1)。

## 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **未登记写工具无法在此验收** | 「新写工具被放行」是一个**缺失的检查**,没有任何操作能触发一条「应被拦」的提示。只能靠核查 `FILE_MUTATION_TOOLS` 表(见 A4 的依据) |
| L2 | **依赖 agent 配合** | 本清单要求 agent 确实去尝试那些被禁止的操作。agent 若「知道不该做」而不尝试,验收即退化为「没有被拦也没有报错」—— 两种情形外观一致 |
| L3 | **手工执行,无自动化** | 这九组没有脚本化。§A2–A8 的断言曾用驱动真实钩子的临时脚本验证过,但该脚本不在仓库里 |
| L4 | **状态栏与面板需真实 TUI** | 无头环境下 `hasUI` 为假,`sync()` 提前返回(`../04-扩展接口/03` §1),A1/A6/A9 的视觉断言无法执行 |
| L5 | **A4 第 1 条依赖同会话的 `read`** | 跨会话的旧锚点查不到表,预期是被拦 —— 该表现与「陈旧锚点」一致,倾向于被误判为缺陷 |
