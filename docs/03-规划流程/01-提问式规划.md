# 03 规划流程 / 01 · 提问式规划

## 1. 设计树

**【规则】** 把方案展开成一棵**设计树**:每个决策分出挂在它下面的子决策。

```
根:要解决的问题
├── 决策 A(选定的做法)
│   ├── A 的子决策 A1
│   └── A 的子决策 A2
└── 决策 B
    └── B 的子决策 B1
```

**【依据】** 决策之间存在**依赖**:「用文件夹布局还是单文件」决定了「条目怎么编号」有没有意义。把这层依赖显式画出来,才能知道哪些问题现在就能答、哪些必须等上游定了才好答 —— 这正是 frontier 的定义所需的信息。

## 2. frontier

**【规则】** 按**轮**推进。**frontier** = 前置决策已定、现在就能回答的那组问题。一轮把整个 frontier 问完,再算下一轮。

**【依据】** 若允许「想到哪问到哪」,问题会违反依赖顺序:在「是否引入话题文件夹」还没定时就去问「文件夹里条目怎么编号」。这样得到的答案是**临时假设**上的答案,上游一变就要重做。按轮推进把「可答」这件事变成显式判据。

**【规则】** 一个问题的答案依赖**同一轮里**另一个未决问题 → 它属于更晚的一轮(`SKILL.md` P1)。

**【依据】** 这条规则是 frontier 定义的操作化判据:同轮内互相依赖说明它们不可能同时可答。把它写成规则,使「这问题该在哪轮」有确定答案,不靠感觉。

## 3. 自问自答

**【规则】** 每个问题**编号**、**当场给出推荐答案**。格式:

```
❓ **Q1** - **<问题标题>**: <问题正文,可以多点、带选项>

➡️ <推荐答案>

---

❓ **Q2** - ...
```

**【规则】** **问题由 agent 提,答案也由 agent 给**。不向用户提问。

**【依据】** 用户的时间应花在只有他能决定的事上 —— 偏好与取舍,而不是给 agent 供料。要求 agent 自答,迫使它先形成判断,而不是把未想清的问题转手给人。用户的介入点被压缩到收尾一次(见 `03`)。

## 4. 提问与回答是强制的

**【规则】** 每轮推进必须**先写出问题、再写出答案**。两步缺一不可。

| 违规形态 | 判定 |
| --- | --- |
| 跳过提问,直接给结论 | 漏掉规划过程 |
| 只写问题,不给答案 | 同样不算 |

**【依据】** 只写答案会让「自问」这一步消失,结果是一份没有暴露过取舍的方案 —— 读者看到的是结论,看不出还有哪些别的选择、为什么否决了它们。只写问题则把工作推给读者。

**【规则】** 「可变决策」至少 3 条是这条纪律的**可检查落点**(`deep_plan_review`,`src/index.ts:542-544`)。

**【依据】** 「有没有真的自问」是主观的,无法直接检查。但一个真的经过多轮提问的方案,必然暴露出若干「用户可能有不同偏好」的取舍 —— 把它们写成可变决策表,条数就成了自问深度的可观测量。少于 3 条时报告的措辞正是「自问深度不足」。

## 5. 找事实不是提问

**【规则】** 环境里能查到的事实**自己去查**(见 `02`),**不要**写进问题里当待办。

**【依据】** 「这个 API 的签名是什么」不是决策,是事实 —— 它只有一个正确答案,查一下就有。把它放进 frontier 会把提问式规划退化成一份待办清单,并让「提问」这件事失去信号价值(真正需要判断的问题被埋在事实问题里)。

## 6. 问完的判据

**【规则】** **frontier 为空**才算问完:每条分支都走到,没有东西被默默假设。

**【依据】** 「没问完」的典型症状是文档里出现没有依据的假设 —— 它没有对应的问答轮次,却被当作前提使用。「每条分支都走到」给出一个可自检的收尾条件。

**【依据】** 问完(结论已齐)之后才进入成文。先成文、后补问会让文档围绕已写的文字调整,而不是围绕结论组织。

## 7. 结论的去向

**【规则】** 提问式规划的产出是**结论**,不是文档正文。结论以「术语」「目标 / 非目标」「计划」这类**结果**写进文档;「为什么这么定」留在 **git commit**(见 `../02-文档规范/03`)。

```
提问轮次 (过程)
    ↓ 提取结论
术语 / 目标 / 非目标 / 计划 / 风险  (写进文档)
    ↓
「为什么这么定、否决了什么」        (写进 git commit)
```

**【依据】** 决策是变值,文档是长期维护的。把决策过程固化进文档,几轮之后文档就会自己和自己矛盾。分成「结果进文档、理由进 commit」两路,使文档只需回答「现在是什么」,而「怎么变成现在这样」由 git 承担。

**【规则】** 问答过程本身**不落盘**。

**【依据】** 过程不是产出。保留它的唯一价值是追溯,而 git 已经承担了追溯。

## 8. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **「frontier 为空」无法自动验证** | 没有工具能检查「所有分支都走到了」。唯一的间接信号是可变决策条数 |
| L2 | **设计树不出现在文档里** | 树是推理的中间结构,只以结论的形式影响文档。因此读者看不到方案的完整推导路径 |
| L3 | **「确需用户定夺」的判据是主观的** | 什么算「用户可能有不同偏好」由 agent 判断。判错的方向有两种:把技术事实塞进可变决策表(浪费用户时间),或漏掉真正的取舍(用户失去介入点) |
| L4 | **纪律靠文案,无强制** | 本部分的全部规则都写在注入文案里。一个不遵守的模型不会被工具拦住 —— 门禁只管可写范围,不管内容质量 |
