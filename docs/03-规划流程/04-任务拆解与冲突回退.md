# 03 规划流程 / 04 · 任务拆解与冲突回退

## 1. 可独立验收的定义

**【规则】** 每个任务必须**可独立验收**:能说清「做什么」与「怎么确认这步成了」。

| 可独立验收 | 不可独立验收 |
| --- | --- |
| 「resolveDocPath 支持三条解析规则」+ 验收:三种输入各跑一次,断言产出路径 | 「改进文档处理」 |
| 「门禁覆盖全部锚点编辑器工具」+ 验收:8 个工具名逐个断言被拦 | 「完善门禁」 |

**【依据】** 「能独立验收」是任务拆解的定义(`references/research-contract.md` 的停止判据第 4 条)。不可验收的任务在执行阶段无法判断是否完成,会退化成「感觉做完了」—— 于是 `done` 变成一句自我评价,而不是一个可核对的事实。

**【规则】** 任务标题用**动作开头的单句**。

**【依据】** 标题在任务面板里按行显示,读者靠它判断「现在在做什么」。名词短语(「文档布局」)描述的是对象,不说明进度;动作短语(「实现话题文件夹布局」)自带「做完/没做完」的判据。

## 2. 任务的两组动作

`deep_plan_task` 管**结构**(`src/tasks.ts:62-180`),`deep_plan_step` 管**状态**(`src/tasks.ts:183-303`)。

### 2.1 `deep_plan_task` — 结构与拆分

| 动作 | 作用 | 约束 | 行 |
| --- | --- | --- | --- |
| `title` | 确立/修正任务标题与范围 | 需要 `title`;整个方案只做一次(重复调用变成「修正」) | `:111` |
| `add` | 追加一个可独立验收的任务 | 需要 `title`;新建 `T{n}`,状态 `planned` | `:130-140` |
| `list` | 查看清单与进度 | 只读 | `:88` |
| `update` | 修正已规划任务的标题/范围 | 需要 `taskId` | `:172` |
| `remove` | 删除任务 | 需要 `taskId`;**只允许删除 `planned` 状态** | `:156-167` |

**【规则】** `remove` 只允许删除 `planned`(尚未开始)的任务(`src/tasks.ts:161-163`)。

**【依据】** 一个已经 `active` / `done` / `blocked` 的任务在历史里留下过痕迹(面板显示过、任务笔记写过原因)。删除它会让那些痕迹失去对应物。要放弃一个已开始的任务,用 `skip`(留下 `skipped` 记录)而不是删除。

**【规则】** 任务 id 由 `T${数量+1}` 生成(`src/tasks.ts:135`)。

**【依据】** 生成规则简单,因此**删除后再添加会产生重复 id**:删掉 `T2`(共 3 个)后添加新的,新任务又拿到 `T3`,与已存在的 `T3` 冲突。当前实现接受这一点 —— 引用任务时以 `taskId` 查找取**第一个**匹配(`src/tasks.ts:217`)。避免的办法是不删任务(用 `skip`)。

### 2.2 `deep_plan_step` — 状态推进

| 动作 | 合法前提 | 结果 | 行 |
| --- | --- | --- | --- |
| `start` | 不是 `done`;没有别的任务处于 `active` | → `active`,记 `startedAt` | `:239-251` |
| `done` | —(从 `planned` 直接 `done` 也会补 `startedAt`) | → `done`,记 `completedAt` | `:252-258` |
| `skip` | — | → `skipped`,记 `completedAt` | `:259-264` |
| `block` | 需要 `note` | → `blocked`,`note` 必填 | `:265-272` |
| `unblock` | 当前必须是 `blocked` | → `active` | `:273-277` |

状态机:

```
planned ──start──→ active ──done──→ done
   │                  │  ↑
   │                  │  └────unblock──── blocked
   │                  └──block(需 note)──→ blocked
   └──done / skip──→ done / skipped
```

**【规则】** 同时只能有**一个** `active` 任务(`src/tasks.ts:242-248`)。

**【依据】** 面板按「当前做着什么」显示,多个 `active` 会让「现在在做什么」这个问题没有单一答案。而且执行阶段的验收是逐任务对照验收方式进行的,并行推进会让「这一步成了没有」无法判断。

**【规则】** `done` 从 `planned` 直接跳跃是允许的,并会补记 `startedAt`(`src/tasks.ts:253`)。

**【依据】** 有些任务小到「想起来就做完了」,强制先 `start` 只会增加一次无意义的调用。补记时间戳使时间数据仍然完整。

**【规则】** `block` 的 `note` **必填**(`src/tasks.ts:266`)。

**【依据】** 受阻的任务会在面板里显示,而「为什么受阻」是它唯一有用的附加信息。一个没有原因的 `blocked` 会让人重新排查一遍已经查过的事。

**【规则】** `unblock` 只能作用于 `blocked` 状态(`src/tasks.ts:274`)。

**【依据】** 这条约束把 `unblock` 变成有意义的动作:它专用于「受阻已解除」。若允许任意状态调用,它就成了 `start` 的同义词,而受阻状态会失去「必须显式解除」这一性质。

## 3. 阶段守卫

**【规则】** `deep_plan_step` 只在**执行阶段**可用(`src/tasks.ts:209-214`)。

```
if (deps.phaseOf() !== "executing") throw ...
```

`deep_plan_task`(结构)在文档阶段**可用**;`deep_plan_step`(状态)不可用。

**【依据】** 这是两者分工的核心:**gated 阶段可以规划结构,但不能声称执行进度**。文档阶段把任务拆好正是它的产出之一;但若此时就能标 `done`,等于在用户批准之前先宣布了「已经做完」——批准这件事就失去内容了。

**【不采纳】** 不允许文档阶段用 `deep_plan_step action=start` 预先把任务标为进行中。

**【依据】** 同上:任何进度声明都必须发生在批准之后。

## 4. 文档冲突的四种情形

**【规则】** 执行中遇到下面任一种,**必须**停下回到文档阶段(`SKILL.md` P5):

| # | 情形 |
| --- | --- |
| 1 | 文档描述与实际代码**不符**(文档说 A,仓库里是 B) |
| 2 | 文档**内部自相矛盾**,或本方案的细节和文档别处打架 |
| 3 | 文档**漏掉了正需要的事实**,靠猜才能继续 |
| 4 | 照文档做下去会**破坏文档里明确的非目标或约束** |

**【规则】** 遇到冲突**不要**:
- 照实际代码改去迁就过时的文档
- 只在代码注释里记一笔
- 当成「已知偏差」继续做

**【依据】** 这四种情形有一个共同点:**已批准的方案不再能指导执行**。此时继续做下去,产出的代码与文档描述的方案不一致,而这个不一致不会被任何人发现 —— 提交信息说「按方案实现」,方案里写着已被绕过的约束。停下回退使这个不一致在发生时就暴露。

**【依据】** 「只在注释里记一笔」是最隐蔽的绕过:它留下了痕迹,却让文档保持错误状态,下一个读文档的人仍会得到错误的前提。

**【规则】** 只是措辞小瑕疵、不影响执行正确性 → **不值得**中止,记下来等收尾时一并处理。

**【依据】** 中止的代价是重新走一遍文档阶段与批准流程。把「措辞」与「方向」分开,使中止被保留给真正需要重新决策的情形。

## 5. 回退动作

```
deep_plan_revise conflict=true reason="<具体的冲突是什么>"
```

`deep_plan_revise`(`src/index.ts:658-721`)按顺序做四件事:

| # | 动作 | 行 |
| --- | --- | --- |
| 1 | 把**进行中**的任务标为 `blocked`,note 写「文档冲突,执行已中止: <reason>」 | `:683-689` |
| 2 | 若 `conflict=true`,把 `reason` 记进 `haltReason` | `:690` |
| 3 | 给文档重新盖 `status: writing` | `:692-695` |
| 4 | 阶段切回 `writing`(放开 `docs/`,冻结仓库) | `:696` |

**【规则】** 第 1 步必须**先做**,在做文档修改之前完成。

**【依据】** `src/index.ts:681-682` 的注释说明了这点:一个进行中的任务不能在它的前提被重写期间还保持 `active` —— 否则「文档改好了」会被读成「工作已完成」。先让它 `blocked`,状态的语义就与事实一致:它的前提正在被修改,所以它现在不能继续。

**【规则】** 返回的文案必须列出**被标记为受阻的任务**并说明用 `unblock` 恢复、**不要**当作已完成(`src/index.ts:703-706`)。

**【依据】** 被中止的任务最容易发生的错误就是被静默遗忘 —— 阶段切回去了,任务列表里那些 `blocked` 就慢慢不再被注意。显式列出让它们保持在视野内。

**【规则】** 文档阶段调用 `revise` 时返回「已在文档阶段,`docs/` 本就可写」而不做任何事(`src/index.ts:666-672`)。

**【依据】** 在文档阶段,`revise` 想达成的状态已经成立。将其变成幂等的空操作,避免误调用改变状态。

## 6. 回退后的恢复流程

```
发现冲突
   ↓ deep_plan_revise conflict=true
docs/ 可写、仓库冻结、进行中任务 → blocked
   ↓ 把文档改对
deep_plan_review
   ↓ 重新收尾(校验:正文非空、可变决策 3-8、任务非空、条目非空)
再提交一次文档
   ↓ 用户批准
deep_plan_approve
   ↓ haltReason 被清除
继续执行;做完受阻任务后 deep_plan_step action=unblock
```

**【规则】** `haltReason` 由下一次 `deep_plan_approve` 清除(`src/index.ts:632`)。

**【依据】** 中止的原因已经被「改文档 + 重新批准」这个动作解决了 —— 保留它只会让下次运行看到一条已过期的告警。清除的时机选在 `approve`(而不是 `revise`),使中止原因在同一轮文档阶段里保持可见。

**【规则】** `haltReason` 会出现在文档阶段的注入文案里,让模型知道为什么要回到文档阶段。

**【依据】** 回到文档阶段时,模型若不知道上次为什么中止,很可能把文档改成同一个错误的样子。把原因摆在它面前,它才能修对。

**【规则】** 受阻任务修完后用 `unblock` 恢复,**不要**当成已完成(`SKILL.md` P5)。

**【依据】** 任务在受阻时**没有完成** —— 它的前提变了,可能还需要重做。直接标 `done` 会让「已完成」包含一件事实上没做的事。`unblock` 把它放回 `active`,让「是否真的做完了」在恢复之后重新判断。

## 7. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **冲突判定靠模型** | 四种情形没有自动检测。模型没识别出来的冲突不会被拦,会静默地被执行下去 |
| L2 | **`revise` 不校验 `reason` 质量** | `reason` 只要求非空字符串。写「有点问题」也能通过,于是 `haltReason` 对下一轮没有指导价值 |
| L3 | **不允许中止非进行中的任务** | 只把 `active` 任务标 `blocked`(`src/index.ts:687`)。`planned` 任务不受影响 —— 它们本来就还没开始,前提变化由文档修改本身反映 |
| L4 | **受阻原因会被后续 note 覆盖** | `unblock` 时若传了 `note`,会覆盖「文档冲突…」那条(`src/tasks.ts:273`)。冲突的上下文可能因此丢失 |
| L5 | **`haltReason` 只保留一条** | 再次中止会覆盖上一次的原因。历史靠 git 与文档本身追溯 |
| L6 | **删除任务后 id 可能重复** | `T{n}` 按数量生成(§2.1)。用 `skip` 代替 `remove` 可避免 |
