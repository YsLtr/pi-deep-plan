# 03 规划流程 / 01 · 提问式规划

## 1. 设计树

**【规则】** 方案展开为**设计树**:每个决策分出挂在该决策下面的子决策。

```
根:要解决的问题
├── 决策 A(选定的做法)
│   ├── A 的子决策 A1
│   └── A 的子决策 A2
└── 决策 B
    └── B 的子决策 B1
```

**【依据】** 决策之间存在**依赖**:「用文件夹布局还是单文件」决定「条目如何编号」是否有意义。将该层依赖显式画出,方能确定哪些问题当前即可回答、哪些须待上游决策确定后方可回答 —— 这正是 frontier 的定义所需的信息。

## 2. frontier

**【规则】** 按**轮**推进。**frontier** = 前置决策已定、现在就能回答的那组问题。一轮把整个 frontier 问完,再算下一轮。

**【依据】** 若允许「想到哪问到哪」,问题将违反依赖顺序:在「是否引入话题文件夹」尚未确定时即去问「文件夹里条目如何编号」。这样得到的答案是**临时假设**上的答案,上游一变即须重做。按轮推进把「可答」这一条件变成显式判据。

**【规则】** 一个问题的答案若依赖**同一轮里**另一个未决问题,则该问题属于更晚的一轮(`SKILL.md` P1)。

**【依据】** 这条规则是 frontier 定义的操作化判据:同轮内互相依赖说明这些问题不可能同时可答。将其写成规则,使「该问题属于哪一轮」有确定答案,不依赖判断者的直觉。

## 3. 自问自答

**【规则】** 每个问题**编号**、**当场给出推荐答案**。格式:

```
❓ **Q1** - **<问题标题>**: <问题正文,可以多点、带选项>

➡️ <推荐答案>

---

❓ **Q2** - ...
```

**【规则】** **问题由 agent 提,答案也由 agent 给**。不向用户提问。

**【依据】** 用户的审查对象应限于仅用户可裁定的事项,即偏好与取舍,而非为 agent 提供素材。要求 agent 自答,可迫使 agent 先形成判断;未形成判断的问题不得转交用户。用户的介入点被压缩到收尾一次(见 `03`)。

## 4. 提问与回答是强制的

**【规则】** 每轮推进须**先写出问题、再写出答案**。两步缺一不可。

| 违规形态 | 判定 |
| --- | --- |
| 跳过提问,直接给结论 | 漏掉规划过程 |
| 只写问题,不给答案 | 同样不算 |

**【依据】** 只写答案会使「自问」这一步消失,结果是一份没有暴露过取舍的方案 —— 读者看到的是结论,无法看出还存在哪些别的选择、以及否决这些选择的理由。只写问题则把工作推给读者。

**【规则】** 「可变决策」至少 3 条是这条纪律的**可核对项**(`deep_plan_review`,`src/index.ts:578-580`)。

**【依据】** 「是否真的自问」是主观的,无法直接检查。但一个确实经过多轮提问的方案,必然暴露出若干「用户可能有不同偏好」的取舍 —— 将这些取舍写成可变决策表,条数即成为自问深度的可观测量。少于 3 条时报告的措辞正是「自问深度不足」。

## 5. 找事实不是提问

**【规则】** 环境里能查到的事实**由 agent 自行查证**(见 `02`),**不得**写进问题里当作待办。

**【依据】** 「这个 API 的签名是什么」不是决策,是事实 —— 该问题只有一个正确答案,可通过检索获得。将事实问题纳入 frontier 会使提问式规划退化为一份待办清单,并使「提问」失去信号价值(真正需要判断的问题被埋在事实问题里)。

## 6. 问完的判据

**【规则】** 须**frontier 为空**方可视为问完:每条分支都走到,不存在被静默假设的项。

**【依据】** 「未问完」的典型症状是文档里出现没有依据的假设 —— 该假设没有对应的问答轮次,却被当作前提使用。「每条分支都走到」给出一个可自检的收尾条件。

**【依据】** 问完(结论已齐)之后方进入成文。先成文、后补问会使文档围绕已写的文字调整,而非围绕结论组织。

## 7. 结论的去向

**【规则】** 提问式规划的产出是**结论**,不是文档正文。结论以「术语」「目标 / 非目标」「计划」这类**结果**写进文档;「规定理由与否决事项」留在 **git commit**(见 `../02-文档规范/03`)。

```
提问轮次 (过程)
    ↓ 提取结论
术语 / 目标 / 非目标 / 计划 / 风险  (写进文档)
    ↓
「规定理由与否决事项」        (写进 git commit)
```

**【依据】** 决策是变值,文档是长期维护的。将决策过程固化进文档,几轮之后文档将自相矛盾。分成「结果进文档、理由进 commit」两路,使文档只需给出当前状态,而状态演变过程由 git 承担。

**【规则】** 问答过程本身**不写入文件**。

**【依据】** 过程不是产出。保留问答过程的唯一价值是追溯,而追溯已由 git 承担。

## 8. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **「frontier 为空」无法自动验证** | 没有工具能检查「所有分支都走到了」。唯一的间接信号是可变决策条数 |
| L2 | **设计树不出现在文档里** | 树是推理的中间结构,只以结论的形式影响文档。故读者看不到方案的完整推导路径 |
| L3 | **「确需用户定夺」的判据是主观的** | 「用户可能有不同偏好」的判定由 agent 作出。判错的方向有两种:把技术事实纳入可变决策表(增加用户审查开销),或漏掉真正的取舍(用户失去介入点) |
| L4 | **纪律靠文案,无强制** | 本部分的全部规则都写在注入文案里。不遵守规则的模型不会被工具拦住 —— 门禁仅覆盖可写范围,不涉及内容质量 |
