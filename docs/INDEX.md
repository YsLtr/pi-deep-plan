# pi-deep-plan — 设计文档索引

本目录是 **pi-deep-plan 的权威设计文档**。代码是实现,文档是契约:实现与文档冲突时,先改文档,再改代码(见 §6 维护约定)。

- 产品:pi 编码代理的深度规划扩展。
- 机制:两阶段门禁 —— 文档阶段只允许写 `docs/`,执行阶段冻结 `docs/`。
- 工程底线:TypeScript,运行时依赖只有命令解析用的 `shell-quote`,扩展只经 pi 的公开接口接入。

## 2. 证据标注约定

文档里每个机制性论断必须携带相应证据,**只允许两类**:

| 写法 | 含义 |
| --- | --- |
| `src/state.ts:330` | 相对**本仓库**根目录的路径 + 行号 |
| `https://nodejs.org/api/path.html` | 外部规范、官方文档、平台官方说明 |

【规则】禁止在正文中引用第三方实现的文件路径、行号或代码。需要比对别的实现来定取值时,比对过程留在别处,不进本目录。

## 3. 内容标记

文档只写**本项目自己最终选定的实现方式**,不出现任何第三方扩展或产品的名称。三种标记:

| 标记 | 含义 | 写法要求 |
| --- | --- | --- |
| **【规则】** | 本文档规定本项目必须遵守的做法 | 直接给取值与验收标准 |
| **【依据】** | 该规则的来源与理由 | 只能是上表两类证据;必须写清「该取值如此规定的理由」 |
| **【不采纳】** | 明确放弃的做法 | 写清理由,防止后续维护者补回该做法;只描述做法,不点名出处 |


## 3.1 写作语体

**【规则】** 本目录的全部正文使用**规范陈述语体**:陈述事实、规定要求、说明理由。判据是「该句可被当作规范条款宣读」。以下七项为禁令。

### 3.1.1 禁止第三人称代词指代事物

**【规则】** 不得以「他」「它」「他们」「它们」指代机制、文档、工具、字段或模型。指代已命名的对象时**重复该名称**;指代人的行为主体时使用角色名「用户」「执行者」「维护者」。

**【依据】** 代词要求读者回溯上下文才能确定所指对象,而规范条款须自足可读。`他 / 它` 在中文技术文档中同时承担生物性别与无生物指代两种功能,歧义面比英语更宽。

`其他`、`其余`、`其它` 是限定词而非代词,不受本项约束。

### 3.1.2 禁止疑问句与疑问式表达

**【规则】** 正文不得出现疑问句。小节标题使用**名词短语**;表格列名不得包含疑问词。

| 禁止 | 应采用 |
| --- | --- |
| 「为什么是这两个阶段」 | 「阶段划分依据」 |
| 「锚点是什么」 | 「锚点定义」 |
| 「怎么验」 | 「验证方式」 |
| 「什么时候读」 | 「阅读时机」 |
| 「为什么这样定」 | 「该取值如此规定的理由」 |

**【规则】** 引用之外不得使用「该不该」「能不能」「是否应该」;改用「应…」「不得…」。

**【依据】** 疑问句把陈述义务转移给读者。规范文档声明取值与理由,不提出问题。

### 3.1.3 禁止 X 什么 式表达

**【规则】** 不得使用「做什么」「不做什么」「管什么」「不含什么」「覆盖什么」「破坏什么」「保持什么」「规定什么」这类「动词 + 什么」的短语作标题或列名。

| 禁止 | 应采用 |
| --- | --- |
| 「范围内(做什么)」 | 「能力范围」 |
| 「范围外(不做什么)」 | 「非目标范围」 |
| 「边界(不含什么)」 | 「边界」 |
| 「会破坏什么」 | 「破坏对象」 |
| 「主上下文要保持什么」 | 「主上下文的保留项」 |

**【依据】** 该构式是 3.1.2 的口语化变体:形式上是短语,功能上仍是提问,同样把内容的界定责任推给读者。

### 3.1.4 禁止啰唆用语

**【规则】** 不得使用「一句话」「说明白」「讲清楚」「讲明白」等以「表达行为本身」替代「表达内容」的措辞。

| 禁止 | 应采用 |
| --- | --- |
| 「一句话定位」 | 「定位总览」 |
| 「说明白这一层做什么」 | 「界定该层范围」 |
| 「讲清楚取值来源」 | 「说明取值来源」 |

**【依据】** 这类措辞描述的是「写作者应达到的效果」,不是条款内容;其占用了标题位置而不携带信息。

### 3.1.5 禁止口语词

**【规则】** 不得使用口语与比喻性措辞。

| 禁止 | 应采用 |
| --- | --- |
| 悄悄 / 偷偷 | 静默 |
| 炸掉 / 崩掉 | 导致失效 / 抛出异常 |
| 顺手 / 顺便 | (删除,或写明具体动作) |
| 拖慢 / 妨碍 | 增加开销 / 追加限制 |
| 摸不着 / 摸清 | 无法定位 / 查明 |
| 很难发现 | 不易察觉 |
| 踩坑 / 坑 | 缺陷 / 已知问题 |
| 麻烦 | 开销 / 成本 |
| 拉平 / 干掉 | 展平 / 删除 |
| 白做 | 无效 |

**【依据】** 比喻要求读者完成一次映射才能得到含义,而映射关系随读者而异;规范条款的取值必须唯一确定。

### 3.1.6 禁止第二人称

**【规则】** 不得使用「你」「您」「你的」。改为角色名(「用户」「执行者」「维护者」)或改为无人称陈述。

**【依据】** 规范文本的读者是不特定的。第二人称把条款限定为对特定人说话,且与「收尾呈现」等面向用户的指令混在同一语体里会造成指代混乱。

### 3.1.7 【依据】的语体要求

**【规则】** 【依据】说明「该取值如此规定的理由」,须写成规范陈述:不得使用比喻与拟人,不得使用反问;因果关系使用「因…故…」「…将导致…」「…的前提是…」,不使用「所以其实」「说白了」。

| 口语式依据 | 规范式依据 |
| --- | --- |
| 「放行一个无法归属的写操作,等于给出一条绕过约束的通道」 | 「放行一个无法归属的写操作,即构成一条绕过约束的通道」 |
| 「抛错会引发一轮排查」 | 「抛错将引发以失败原因排查为目的的额外轮次」 |
| 「取决于读者先翻到哪个文件」 | 「取决于检索命中的文件」 |

**【依据】** 【依据】的读者是后来的维护者,其判断依据是该理由能否被检验。比喻与反问不可检验。

### 3.1.8 不受本约束约束的内容

以下内容按其原文保留,不适用本节各条:

| 内容 | 理由 |
| --- | --- |
| 代码块、代码标识符、命令行、正则 | 原文即契约 |
| 工具返回文案、`SKILL.md` 引文、提交信息模板 | 引用别人的原文 |
| 参数示例(如 `reason="<具体的冲突是什么>"`) | 字面量 |
| 用于说明「不该这样写」的**反例引文** | 被引对象即违规样本 |
| 术语与固定语(「可变决策」「文档阶段」) | 见 §4 |

**【规则】** 引用原文时不得为迁就语体而改写被引内容;若被引内容本身不合语体,在引文之外的叙述中说明。
## 4. 术语表

| 术语 | 含义 | 详见 |
| --- | --- | --- |
| **文档阶段 (writing)** | 只允许写 `docs/` 的阶段;执行阶段的文档冻结由该定义反向界定 | `00` |
| **执行阶段 (executing)** | `docs/` 冻结、仓库其余部分可写的阶段 | `00` |
| **门禁 (gate)** | 工具调用发生前的强制拦截点,不依赖模型自觉 | `01` |
| **话题 (topic)** | 一个长期维护的文档集合,对应一个文件夹 | `02` |
| **总纲 (overview)** | 话题文件夹内的主文档,`docs/<topic>/<topic>.md` | `02` |
| **条目 (entry)** | 计划拆分出的单个可独立验收项,一个文件 | `02` |
| **可变决策** | 已生效但用户可能希望修改的默认值,收尾时逐条过目 | `02` |
| **锚点 (anchor)** | 编辑器返回的 4 字符行引用,用于在路径未知时定位文件 | `01` |
| **fail closed** | 目标形态可识别、但无法归属到唯一文件时判为不允许 | `01` |
| **scratch** | `.pi/tmp/`,子代理报告的落脚点,门禁放行 | `01` |
| **冲突回退** | 执行中发现文档与事实矛盾时中止执行、回到文档阶段 | `03` |

更细的字段级术语在各文档内就近定义。

## 5. 已知限制

- 本目录只描述**本项目自身**。本项目依赖 pi 宿主提供的钩子与工具接口,但不描述 pi 的实现。
- 门禁是**尽力而为**的静态检查,不是沙箱。判定基于工具名与参数文本,能拦住的用法在 `01-写入门禁/` 逐条列出,拦不住的同样列出。
- 本目录不含面向使用者的上手教程、发布说明或 API 参考(本扩展没有可生成文档的公共 API)。

## 6. 维护约定

1. 改门禁判定(放行/阻断的规则、清单成员):先改 `01-写入门禁/` 对应文件,再改代码。
2. 改文档位置或文件命名规则:先改 `02-文档规范/01-话题文件夹布局.md`。
3. 改给模型的纪律(阶段注入、收尾呈现、反模式):先改 `03-规划流程/`,并同步改动 `../skills/deep-plan/SKILL.md` —— 两者必须一致。
4. 加命令或工具:先改 `04-扩展接口/01-命令与工具清单.md`。
5. 改任何取值(条数上下限、补零位数、深度上限):先改对应文档,并在该处保留【依据】;**不得**仅改代码。
6. 新增主题:在对应文件夹下加编号文件,并同步更新该文件夹 `README.md` 的文件索引与本文件的 §1 总目录。
7. 任何「做不到」的结论写进对应文档的**已知限制**一节,不写进设计正文当承诺。
8. 本目录只放**长期有效的设计**;修复过程、排查记录、A/B 结论、按日期排布的变化记录都不入文档(历史由 git 记录)。
9. 新增或改写正文:先核对 §3.1 写作语体,再落笔。语体属文档契约的一部分,不以「意思一样」为由放宽。
10. 改动 §3.1 的任何一项:同步改动 `02-文档规范/` 与 `../skills/deep-plan/references/plan-format.md` —— 三处是同一套语体的三份表达(见 §3.1 的说明)。

## 已知限制

- 文档描述的是**设计契约**,与代码同步维护。`01`–`05` 的文件级论断都带 `src/*.ts:行号` 证据,行号会随代码改动漂移;改代码时按下表反向核对。
- 取值类条目(条数上下限、补零位数、命令深度上限)多数由本项目**首次规定**,没有外部权威可引;这类条目的【依据】写的是推导过程或约束来源,不是出处。
- 术语表刻意保持在 12 条;扩容前先考虑是否应放入对应文档的局部术语小节。
