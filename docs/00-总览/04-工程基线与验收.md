# 00 总览 / 04 · 工程基线与验收

## 1. 依赖基线

| 类别 | 内容 | 行 |
| --- | --- | --- |
| 运行时依赖 | `shell-quote@^1.11.0` | `package.json` |
| 对等依赖 (peer) | `@earendil-works/pi-coding-agent >=0.85.0`、`typebox` | `package.json` |
| 开发依赖 | `@types/node`、`typescript` | `package.json` |

**【规则】** 运行时依赖只允许一个:`shell-quote`。新增任何运行时依赖前必须先说明该依赖替代了多少行自写代码。

**【依据】** `shell-quote` 被用于**命令分词**而非简单地 `split(" ")`(`src/readonly.ts:18`)。只读判定必须理解引号与操作符,否则 `echo "a; rm -rf /"` 会被当成两条命令或一条无害命令 —— 两者均为错判。手写一个正确的 shell 分词器要覆盖引号、转义、操作符、命令替换,远超本扩展的规模;该库正是这个单点需求的成熟实现。

其余一律用 Node 内置模块:`node:fs`、`node:path`(`src/state.ts:12-13`)。**不引入**测试框架 —— 测试直接使用 Node 内置 test runner。

**【不采纳】** 不引入 YAML 解析库来做 frontmatter(理由见 `01-定位与范围.md` §3 的 N5)。不引入路径匹配库(如 `micromatch`)来判定 `docs/` 包含关系 —— `path.relative` 已经正确(`src/state.ts:192`)。

## 2. 验证基线

| 命令 | 作用 | 行 |
| --- | --- | --- |
| `npm run typecheck` | `tsc -p tsconfig.json`,零错误通过 | `package.json` |
| `npm test` | `node --experimental-strip-types --test src/*.test.ts` | `package.json` |

**【规则】** 提交前必须两者都通过。类型检查与测试都不通过时不允许提交。

**【依据】** 用 `--experimental-strip-types` 直接执行 `.ts`(`package.json:20`)使源码无需构建步骤即可测试 —— 这也意味着**源码里不能使用需要类型擦除以外的 TypeScript 特性**(如 `enum`、参数属性、命名空间)。新增这类语法将直接导致测试无法运行。

## 3. 验收标准

一次完整的 deep-plan 循环,以下每项都要成立:

| # | 验收项 | 验证方式 |
| --- | --- | --- |
| A1 | 启动后阶段为 `writing`,状态栏显示「文档阶段」 | `/deep-plan-status` |
| A2 | 文档阶段改仓库代码被拒,改 `docs/` 下文件通过 | 手工(见 `../05-测试与验收/02`) |
| A3 | 文档阶段 `mkdir`、`rm`、重定向被拒;`ls`、`grep`、`git status` 通过 | 同上 |
| A4 | 用行锚点编辑 `docs/` 下文件通过,编辑仓库文件被拒 | 同上 |
| A5 | `deep_plan_review` 在可变决策 < 3 条、任务为空、条目文件为空时退回 | 同上 |
| A6 | `deep_plan_approve` 后阶段为 `executing` 且状态栏变为「执行阶段」 | `/deep-plan-status` |
| A7 | 执行阶段改 `docs/` 下文件被拒,改仓库代码通过 | 手工 |
| A8 | 执行阶段 `deep_plan_revise` 带 `conflict` 回到 `writing`,进行中任务变 `blocked`,原因出现在下轮注入里 | 手工 |
| A9 | `deep_plan_finish` 后门禁关闭,状态栏清空 | `/deep-plan-status` |

A2–A8 的可执行断言在 `../05-测试与验收/02-手工验收清单.md` 逐条给出。

## 4. 提交基线

**【规则】** 扩展**自己不执行任何 git 命令**。

**【依据】** 见 `01-定位与范围.md` §3 的 N1。扩展只做两件事:声明本次提交的边界(文档阶段提 `docs/`,执行阶段提代码),以及说明提交归属按当次对话的指令走(`src/index.ts` 的收尾文案)。真正的 `git commit` 由 agent 或用户执行 —— 扩展不做推定。
