# 04 扩展接口 / 02 · 上下文注入

## 1. 机制

**【规则】** 纪律通过 `before_agent_start` 钩子返回一条消息注入(`src/index.ts:252`),`customType: "deep-plan-context"`,`display: false`。

| 属性 | 值 | 作用 |
| --- | --- | --- |
| `customType` | `"deep-plan-context"` | 让注入可被识别为该扩展的上下文 |
| `display` | `false` | 不在 UI 里显示,只进模型上下文 |
| `content` | 多行文本,空行过滤后 join | 注入正文 |

**【规则】** 未启动时(`!state.active`)直接 `return`,`before_agent_start` 不注入任何东西(`src/index.ts:253-254`)。

**【依据】** 这是纪律**只在本循环内**有效的机制:一次 deep-plan 结束后,下一轮普通对话不应继续看到「只能写 docs/」这类话。

**【规则】** 文案用**数组 + `.filter((l) => l !== "")` + `.join("\n")`** 拼装,条件行用 `? :` 产生空串来省略。

**【依据】** 直接写模板字符串需要处理缩进与多余换行;数组形式使每一行独立可读、可条件化,`filter` 负责把不生效的行去掉。**这要求任何一行都不能是空串** —— 需要空行时必须采用 `""` 之外的写法(如 `"\n要强调的行"` 自带前导换行)。

**【规则】** 文案里的文档路径必须用 `planLink()`(`src/index.ts:264`、`:315`)而不是裸路径。

**【依据】** `planLink()` 产出 markdown 链接,使模型能在回复里直接引用文档。裸路径会使每次引用都变成一次手工拼链接。

## 2. 文档阶段注入

内容分七段(`src/index.ts:259-300`):

| 段 | 作用 |
| --- | --- |
| 标题与范围 | `[DEEP PLAN — 第一阶段:文档]` + 可写范围 + 「不要尝试绕过」+ 一次性放行的申请入口与其前提(仅限实际只读的命令) |
| 上下文事实 | 本次文档路径、`docs/` 现有文档(最多 20 个)、目标 |
| 冲突提示 | 若 `haltReason` 存在,显示「本次执行因文档冲突被中止」+ 原因 |
| 纪律 | 5 条:自问自答 / 子代理查事实 / 可变决策 / 只留结果 / 写给未来的读者 |
| 文档写法要求 | 话题文件夹布局、`mkdir` 禁令、条目一文件、术语位置、`INDEX.md` 同步 |
| 收尾 | 先 `deep_plan_task` 拆任务,再 `deep_plan_review` |
| 提交 | 归属与两段分开 |

**【规则】** `docs/` 现有文档列表**截断到 20 个**(`src/index.ts:265` 的 `.slice(0, 20)`)。

**【依据】** 列表用于使模型知道「哪些文档已存在、应写入哪一文件」。20 个足以覆盖绝大多数仓库,而全量列出将在文档数多的项目里挤占上下文。

**【规则】** `haltReason` 存在时,注入里必须出现该项内容(`src/index.ts:267-269`)。

**【依据】** 见 `../03-规划流程/04` §6:在不知上次中止原因的情况下,模型很可能把文档改成同一个错误的样子。

## 3. 执行阶段注入

内容分四段(`src/index.ts:310-332`):

| 段 | 作用 |
| --- | --- |
| 阶段与冻结 | `docs/` 已冻结、仓库其余部分可写、全部工具可用 |
| 已定稿文档 | 路径链接 |
| 四条纪律 | 按任务推进 / 提交只针对代码 / 提交归属 / 完成后 `deep_plan_finish` |
| 冲突处理 | 「发现文档冲突时:停止执行,不要绕过」的完整流程 |

**【规则】** 冲突处理段必须包含**四种冲突情形**与**明确的停下动作**(`deep_plan_revise conflict=true`),以及「措辞小瑕疵不值得中止」的反向判据。

**【依据】** 见 `../03-规划流程/04` §4。「不要绕过」是一条否定要求 —— 仅写「不要绕过」不足以告知模型应采取的动作。给出具体工具调用与恢复流程,模型才有可执行的动作。

## 4. 两段注入的差异

| 维度 | 文档阶段 | 执行阶段 |
| --- | --- | --- |
| 首要约束 | 只能写 `docs/` + scratch | `docs/` 冻结 |
| 命令限制 | 只读(单条命令可申请一次性放行) | 无 |
| 主要工作 | 提问、查证、写文档 | 按任务推进 |
| 冲突动作 | 不适用(本就在文档阶段) | `deep_plan_revise conflict=true` |
| 提交 | 只提文档 | 只提代码 |
| 结束动作 | `deep_plan_review` | `deep_plan_finish` |

**【规则】** 注入顺序固定为「阶段 → 范围 → 事实 → 纪律 → 收尾动作」。

**【依据】** 范围(可写路径)是**最易导致工具被拒**的信息,必须尽早出现。事实(路径、已有文档)在纪律之前,使纪律可以引用上述事实。

## 5. 与 `SKILL.md` 的关系

| 载体 | 读者 | 详略 |
| --- | --- | --- |
| `before_agent_start` 注入 | 模型,每次运行 | 精简;只列规则与动作 |
| `skills/deep-plan/SKILL.md` | 模型,按需加载 | 完整;含动机、格式示例、反模式清单 |
| `../03-规划流程/` | 维护者 | 完整;含理由与依据 |

**【规则】** 三者是同一套纪律的三份表达。改动任一处必须同步其余两处(`../../INDEX.md` 的维护约定第 3 条)。

**【依据】** 三份表达面向不同读者,无法合并;而内容重复意味着不一致的风险。将同步写成维护约定,使同步是明确要求,而不是「最好也改一下」。

**【依据】** 注入保持精简,因注入每轮都会出现 —— 完整版的 `SKILL.md` 有 278 行,每轮注入将持续占用上下文。注入只列规则,模型需要细节时按 `SKILL.md` 的指引加载。

## 6. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **注入每轮重复** | 每次 `before_agent_start` 都发送一遍完整文案。长会话里该部分将反复占用上下文 |
| L2 | **注入内容不随任务状态变化** | 执行阶段的注入不包含任务进度(当前 `active` 任务)。模型需自行调 `deep_plan_task action=list` 查看 |
| L3 | **文案与 SKILL.md 的一致性无检查** | 两处内容漂移不会被工具发现 |
| L4 | **条件行依赖 `filter` 非空** | 需要插入空行时不能用空串(会被过滤掉),必须靠 `"\n..."` 的前导换行。这是拼装方式带来的隐性约定 |
| L5 | **`docs/` 列表截断无提示** | 超过 20 个文档时,模型看到的是不完整列表,而注入里没有说明该列表已被截断 |
