# 02 文档规范 / 03 · 决策归属与提交边界

## 1. 决策不进文档

**【规则】** `docs/` 下**不设**「决策记录」小节,不建 `docs/<topic>/decisions/`,不建 `docs/adr/`。决策的唯一出处是 **git commit message**(`plan-format.md`)。

| 内容 | 写在哪 |
| --- | --- |
| 术语 / 规范用语 / `_Avoid_` | 文档的术语小节 |
| 目标 / 非目标 | 文档 |
| 风险与回滚 | 文档 |
| 计划(可独立验收的条目) | 文档 + `deep_plan_task` |
| 提问式规划的问答过程 | 不落盘(过程不是产出) |
| **为什么这么定、否决了什么** | **git commit message** |

**【依据】** 决策是**变值,不是定值**。一条决策今天写进文档,几轮问答后很可能被推翻;而文档是**长期维护**的,把会被推翻的推理固化进去,等于持续制造自相矛盾。commit 是**时间点快照**,天然记录「当时为什么这么定」,`git log` 就是决策的演进史。

这条规则来自一次实际退化:曾经同一话题的决策被同时放进话题内的 `decisions/` 目录和跨话题的 `docs/adr/`,同一决策出现在两处会各自演化,而读到哪一份取决于读者翻到哪个文件。当时加过一个交叉检查来抓重复,但那是治症状 —— 根因是「决策被写进文档」这个前提本身。删掉决策文件位之后,重复问题从源头消失。

**【规则】** 拿到结论后要把它变成**结果性内容**:选定的做法进「计划」,定下的词进「术语」,划掉的范围进「非目标」。

**【依据】** 这是把「决策」转写成「结论」的固定动作。一份只说「我们讨论后决定不用 X」的文档对读者没有价值;说「非目标:X」才有 —— 后者直接告诉读者范围边界,不需要知道讨论过程。

**【不采纳】** 不在文档里保留「决策历史」小节按时间排列。

**【依据】** 那是变更日志的形态(`../../INDEX.md` 的维护约定第 8 条)。文档写「现在是什么」,git 写「怎么变成现在这样的」。

## 2. 决策的表达方式

决策虽然不专门成节,但它的**结果**会以三种形态出现在文档里:

| 决策类型 | 在文档里的落点 | 例子 |
| --- | --- | --- |
| 选定某种做法 | 「计划」条目 | 「`--doc` 尾斜杠表示话题文件夹」 |
| 定下某个术语 | 「术语与领域模型」 | 「**话题** = 长期文档集合,`_Avoid_`:计划/需求」 |
| 明确排除某范围 | 「非目标」 | 「非目标:不做文档归档」 |
| **用户可能想改的默认值** | 「可变决策」表 | 「条目补零 4 位」 |

**【规则】** 「可变决策」表是**唯一**面向用户审查的决策清单,条数 3–8(见 `02` §4)。

**【依据】** 前三类决策一旦定下就该被执行,不需要用户逐条过目;只有「用户可能有不同偏好」的项才需要他决定。把它们分开,使审查点集中在一处。

## 3. 两段提交边界

**【规则】** 一次完整的 deep-plan 循环产生**两个** commit:文档一个,代码一个。

```
文档阶段收尾 ──→ commit #1: 只有 docs/ 的改动
                        ↓ 用户批准
执行阶段完成 ──→ commit #2: 只有代码的改动
```

**【依据】** 两个 commit 使「批准」这件事在 git 历史里可见:看 `git log` 能分辨「方案是什么时候被定下的」与「实现是什么时候做的」。合成一个 commit 后,这两件事在历史上无法区分 —— 而这正是本项目想固定的顺序。

**【规则】** 扩展**自己不执行任何 git 命令**(`../../00-总览/01` 的 N1)。它只声明边界,并在收尾时把边界与归属说清楚。

**【依据】** 提交动作必须留给人可干预的位置。若扩展自动提交,「用户批准了才继续」这句话在文档阶段结束时就已经不成立了。

## 4. 提交归属

**【规则】** 提交由谁执行**按当次对话的指令**决定,不写死。

| 情况 | 归属 |
| --- | --- |
| 默认 | 由执行者(agent)提交 |
| 用户说「提交由我来」或本轮对话委托给用户 | 交给用户 |
| 归属不明 | **先问,不要猜** |

**【依据】** 提交涉及仓库历史,是用户可能想亲自控制的操作(可能要用特定的提交信息、签名、或与其他改动合并)。把它固定给某一方,在另一种偏好下都会变成摩擦。因此归属是可配置的,默认值取「不额外打扰用户」的一侧。

**【规则】** 收尾呈现时必须同时说明:先只提交文档、代码单独成一个 commit、以及归属按本轮指令。

**【依据】** 边界(提什么)与归属(谁提)是两个独立信息,收尾时都要给出,否则读者只知道「提交」而不知道「谁在什么时候提」。呈现契约的完整内容见 `../03-规划流程/03`。

## 5. INDEX.md 的角色

**【规则】** `docs/INDEX.md` 是 `docs/` 的入口,行为两件事:话题表(一行一个话题,指向它的总纲)与本仓库的开发约定(测试与类型检查命令、决策不进文档的约定等)。

**【依据】** `docs/` 被定义为本项目的**开发文档**,取代传统的根目录 `development.md`(`plan-format.md`)。既然它是开发文档的入口,就不该只是话题列表 —— 新人需要从同一处知道「有哪些话题」与「这个项目怎么开发」。

**【规则】** 新增或改名话题时必须同步更新 `INDEX.md`。

**【依据】** 索引与目录实际内容会漂移。索引由模型维护,`/deep-plan-docs` 如实展示两者供对照(`../04-扩展接口/01`),因此漂移是**可见**的 —— 可见的漂移会被修,不可见的不会。

## 6. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **决策写进 commit 只能靠纪律** | 扩展不读 git,无法验证某个 commit 是否带了理由。「决策写进 commit message」是文案要求,没有强制手段 |
| L2 | **索引漂移无自动修复** | 工具只展示现状,不改写 `INDEX.md`。漂移要人来修 |
| L3 | **提交边界无法强制** | 扩展不执行 git,因此「文档一个 commit、代码一个 commit」只能靠说明与纪律;用户或 agent 若合成一个,扩展不会知道 |
| L4 | **跨话题决策无专门位置** | 删掉 `docs/adr/` 后,一条影响多个话题的决策没有「专属文件」。它作为 commit message 存在,或在某个相关话题的非目标/计划里被引用 |
