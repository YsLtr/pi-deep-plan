# 01 写入门禁 / 03 · 锚点解析

## 1. 问题

行锚点编辑器(`replace` / `replace_match` / `insert` / `copy` / `move`)的工具参数里**没有文件路径**,用的是 4 字符行锚点。

```
replace(remove_from="abXy", remove_to="cdZw", text="...")
                          ↑ 没有 path 参数
```

门禁必须知道「改的是哪个文件」才能判断阶段是否允许。锚点解析要解决的全部问题即在此。

## 2. 锚点定义

编辑器在**读取**文件时,为每一行返回一个 4 字符锚点,行格式是:

```
anchor│content
```

锚点是行在**那次读取**里的句柄,不是行号 —— 行内容变了,锚点跟着变(故陈旧锚点会被编辑器自己拒绝)。

## 3. 锚点来源

**【规则】** 锚点表由 `tool_result` 钩子在每次 `read` 之后增量学习,不读取编辑器的内部注册表(`src/index.ts:143-149`)。

```
read(file) ──→ tool_result 事件
                    ↓
            event.toolName === "read" 且 !isError
                    ↓
            从 event.input 取路径 (path / file_path / file)
                    ↓
            逐个 text 片段交给 collectAnchors(text, path, anchorPaths)
                    ↓
            anchorPaths: Map<anchor, filePath>
```

路径的取值顺序是 `path` → `file_path` → `file`(`src/index.ts:145`)。

**【依据】** **不能** import 编辑器的锚点注册表。宿主给每个包各自独立的模块根,扩展无法共享编辑器包的依赖实例 —— 直接 import 将因找不到模块而失败。会话记录里的 `read` 结果是唯一可得的信号,故门禁自行维护一份表。

**【规则】** `tool_result` 里只在 `toolName === "read"` 且 `isError` 为假时才学习。错误结果里不会包含服务过的行。

## 4. 行格式的识别

识别用一个正则(`src/state.ts:456`):

```ts
const SERVED_ROW_RE = /^\s*[+-]?([A-Za-z]{4})│/;
```

逐片段说明:

| 片段 | 含义 |
| --- | --- |
| `^\s*` | 允许行首空白(diff 输出会缩进) |
| `[+-]?` | 允许 diff 前缀 —— 服务过的行、`+` 新增行、`-` 删除行三种都算 |
| `([A-Za-z]{4})` | **恰好 4 个** ASCII 字母,这是锚点的形状 |
| `│` | U+2502 制表符竖线,不是 ASCII 的 `\|` |

**【规则】** 锚点必须恰好 4 个字母。数字、其他长度、混入非字母均不算。

**【依据】** 这条约束使「正文里偶然出现的竖线」不会被误认成锚点。`[+-]?` 是必需的:编辑器的 diff 结果里新增/删除行同样带锚点,如果只认无前缀的行,刚改过的文件的锚点就学不到。

**【依据】** 分隔符必须用 U+2502 (`│`) 而不是 ASCII `|` —— 后者在代码正文(管道、正则、表格)里大量出现,以 ASCII `|` 作分隔会把普通文本误判成锚点行。

**【不采纳】** 不用「任意 4 个字符」或「4 位十六进制」。放宽将显著提高误匹配率,而误匹配的后果是被误拦(门禁认为锚点指向了别的文件)。

## 5. 学习与查询

| 函数 | 位置 | 职责 |
| --- | --- | --- |
| `collectAnchors(text, filePath, into)` | `src/state.ts:465` | 遍历文本行,把命中的锚点写进映射 |
| `planTargetFor(anchor)` | `src/index.ts:152` | 查表,未命中返回 `undefined` |
| `anchorPaths` | `src/index.ts:141` | `Map<anchor, filePath>`,会话内累积 |

**【规则】** 表是**只增不改**的。同一锚点在后续读取里指向别处时,以最后写入的为准(`src/state.ts:468` 用 `set` 覆盖),但已学到的条目不主动清理。

**【依据】** 锚点由内容决定,内容变了锚点即变 —— 因此同一个锚点值基本不会在两次读取里指向不同文件。表的大小随会话读取量增长,不做容量控制;会话结束时由 `session_shutdown` 一并清空(`src/index.ts:123`),与 `state` 的重置同步,两者生命周期一致。

## 6. 与门禁的接合

锚点查询结果交由 `extractWriteTarget` 处理(`src/index.ts:178`),三态对应关系:

| `planTargetFor` 返回 | `extractWriteTarget` 结果 | 门禁行为 |
| --- | --- | --- |
| `undefined` 或 `""` | `""` | **拦截**(「锚点无法定位到文件」) |
| 路径 | 该路径(需与其他锚点一致) | 交给 `isWriteAllowed()` |

调用时锚点可能带行内容,所以取 `│` 之前的部分再查(`src/state.ts:402`):

```ts
resolveTarget(anchor.split(HASH_SEP)[0]!.trim())
```

## 7. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **只认本会话服务过的锚点** | 表在扩展加载时创建(`src/index.ts:141`),由 `read` 结果学习,并在 `session_shutdown` 时与 `state` 一起清空(`:123`)。跨会话编辑用旧锚点会因查不到而被拦 —— 编辑器本身也会拒绝陈旧锚点,两者结论一致 |
| L2 | **依赖 `read` 结果被完整回传** | 若宿主截断 `read` 的文本结果,被截掉部分的锚点学不到,那些行的编辑会被拦。补救方式是重新 `read` 那一段 |
| L3 | **表无上限** | 长会话里可能积累大量条目。未做容量控制,因为条目是 4 字符键 → 路径,规模由读取量决定而非无限增长 |
| L4 | **`undo_last_change` 走路径分支** | 该工具虽属锚点编辑器家族,但参数里有显式 `path`,因此不经过锚点解析(`src/state.ts:384` 优先返回显式路径) |
| L5 | **不校验锚点是否陈旧** | 门禁只判定「这个锚点属于哪个文件」,不判断锚点是否仍然有效。陈旧判定由编辑器自己做 |
