# 02 文档规范 / 01 · 话题文件夹布局

## 1. 三个概念

| 概念 | 定义 | 路径 |
| --- | --- | --- |
| **话题 (topic)** | 一个长期维护的文档集合,对应一个文件夹 | `docs/<topic>/` |
| **总纲 (overview)** | 话题的主文档,承载目标、术语、风险、可变决策 | `docs/<topic>/<topic>.md` |
| **条目 (entry)** | 计划拆分出来的单个可独立验收项,各自成文件 | `docs/<topic>/plan/NNNN-<slug>.md` |

```
docs/
├── INDEX.md
└── deep-plan-layout/
    ├── deep-plan-layout.md          ← 总纲
    └── plan/
        ├── 0001-state-plandir-entrypath.md
        └── 0002-resolvedocpath-folder-layout.md
```

**【规则】** 话题是**长期存在的集合,不是一次 run**。一次 run 只是往某个话题里增补内容。

**【依据】** `planDir()` 的命名与注释明确写「A topic is a long-lived document set, not a run」(`src/state.ts:159-164`)。按 run 建立文件夹会使每次规划产生一个新目录,同一话题的结论将散落在多个日期目录中;此时读者须先确定「哪次 run 讨论过该话题」才能找到内容,而正确的检索方式应按主题。

**【规则】** 路径里**不带日期**。

**【依据】** `src/state.ts:162-163` 明确写了「There is no date」。日期是变更记录的组织方式,不是设计的组织方式;历史由 git 承担(见 `../../INDEX.md` 的维护约定第 8 条)。

## 2. `--doc` 的三条解析规则

`resolveDocPath()`(`src/state.ts:211-233`)按下面的顺序判定:

| # | 输入形态 | 判定 | 结果 | 行 |
| --- | --- | --- | --- | --- |
| 1 | 有 `--doc`,以`\`或`/`结尾,**或**指向已存在的目录 | 话题文件夹 | `docs/<topic>/<topic>.md` | `:223-227` |
| 2 | 有 `--doc`,无扩展名 | 单文件 | `<wanted>.md` | `:229` |
| 3 | 有 `--doc`,带扩展名 | 该文件 | 原样 | `:230` |
| 4 | 没有 `--doc` | goal 的 slug | `docs/<slugify(goal)>.md` | `:233` |

具体例子:

| 命令 | 结果 | 形态 |
| --- | --- | --- |
| `/deep-plan <goal> --doc docs/foo/` | `docs/foo/foo.md` | **话题文件夹** |
| `/deep-plan <goal> --doc docs/foo` | `docs/foo.md` | **单文件**(不带话题) |
| `/deep-plan <goal> --doc docs/foo/bar.md` | `docs/foo/bar.md` | 指定文件 |
| `/deep-plan <goal>` | `docs/<goal-slug>.md` | 单文件 |

**【规则】** 话题文件夹**只在调用方明确要求时**才建立(尾斜杠,或指向已存在的目录)。

**【依据】** 这是**向后兼容**的要求(`src/state.ts:198-201` 的注释):裸名字 `docs/foo` 在旧版本里表示「单文件 `docs/foo.md`」。如果改成「裸名也升级为话题文件夹」,既有用法的含义会在不声不响中改变 —— 文档会建到用户没指定的位置。区分靠**尾斜杠这一个字符**,是唯一不需要猜测的判据。

**【规则】** 三条规则之外没有第 4 种:不存在的目录名**不**被当成话题(`isDirectory` 为假,`src/state.ts:236-242`)。

**【依据】** 若「任何不带扩展名的路径都当话题」,则 `--doc docs/foo` 的既有语义(单文件)必然改变。用「已存在」作判据使升级是显式的:用户先建目录(或先建过话题),才得到话题语义。

## 3. 路径推导函数

全部是**纯函数**,不创建任何东西(`src/state.ts:179` 注释 明确:「Pure: nothing is created」):

| 函数 | 签名 | 返回 | 行 |
| --- | --- | --- | --- |
| `docsDir(cwd)` | → `string` | `docs/` 的绝对路径 | `:128` |
| `indexFile(cwd)` | → `string` | `docs/INDEX.md` | `:132` |
| `planDir(cwd, topic)` | → `string` | `docs/<topic>/` | `:165` |
| `entryPath(cwd, topic, kind, slug, seq)` | → `string` | `docs/<topic>/<kind>/NNNN-<slug>.md` | `:179` |

**【规则】** 建目录只发生在 `docs/` 根(`src/state.ts:212` 的 `mkdirSync`)与写文件的瞬间。话题文件夹与 `plan/` 子目录由 **`write` 写第一个文件时自动创建父目录**产生,不调用 `mkdir`。

**【依据】** 文档阶段的门禁拒绝 `mkdir`(`../01-写入门禁/02` §3.1 的拒绝清单里有 `mkdir`)。若布局依赖显式建目录,文档阶段就无法建立话题文件夹 —— 而布局恰恰是文档阶段的产物,两者会互相矛盾。让 `write` 承担建目录,门禁与布局就一致了。

**【规则】** 序列号补零到 **4 位**(`padSequence`,`src/state.ts:170-172`)。

**【依据】** 补零使文件系统的字典序等于数字序:`0009-…` 排在 `0010-…` 之前。不补零时 `10` 会排在 `9` 之前。4 位意味着单话题可容纳 9999 个条目,远超实际需要。

## 4. 条目编号的语义

**【规则】** 编号只表达**文件系统排序**,不表达执行顺序的强制性。`deep_plan_review` **不检查编号连续**。

**【依据】** 执行顺序的权威是 `deep_plan_task` 的任务列表(`status` 字段与 `taskId`),不是文件名。若两处都能表达顺序,就会产生「文件编号说 3 在前、任务状态说 3 已完成」这类互相矛盾的读数。文件名只负责「读的时候按稳定顺序排列」这一件事。

## 5. 总纲的位置与迁移

一条已存在的话题总纲,在被移进文件夹后仍可由 `resolveOverview()` 找回(`src/state.ts:144-152`):

| 顺序 | 判定 | 结果 |
| --- | --- | --- |
| 1 | 记录中的路径**存在** | 采用该路径 |
| 2 | 否则,`docs/<stem>/<stem>.md` **存在**(话题已建文件夹) | 用文件夹版 |
| 3 | 都不存在 | 返回**原记录路径**(供调用方据此报错) |

**【依据】** 一次 run 的 `planPath` 在启动时记录。若中途把文档从 `docs/foo.md` 移进 `docs/foo/foo.md`(布局升级),记录就指向了不存在的旧路径。第 2 步让三个阶段转移工具(`review` / `approve` / `revise` / `finish`)自动跟随移动,而不是静默跳过定稿。

**【规则】** 第 3 步返回原路径而**不是** `undefined`。

**【依据】** 调用方需要知道「原本要找的是哪个文件」才能给出可读的错误信息(`src/state.ts:152`)。返回 `undefined` 将丢弃该信息。

## 6. 存量单文件话题

**【规则】** `docs/foo.md` 这种单文件形态**继续有效**,不会被自动迁移,也不被排斥。

**【依据】** 迁移会改动用户的既有文件,而布局升级是**内容决策**而非格式决策 —— 只有当一个话题真的长出多个条目时才值得拆成文件夹。强制迁移会让「只想写一段说明」的用法付出建目录的代价。`listDocs()` 递归收集(`src/state.ts:244-259`),因此单文件与文件夹话题在索引里并存。

## 7. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **单文件话题没有 `plan/`** | 条目只能存在于话题文件夹里。单文件话题要拆条目,须先升级为话题文件夹 |
| L2 | **`plan/` 之外没有其他条目位** | 决策不进文档(见 `03`),故不设 `decisions/`;此属刻意设计,不是缺失 |
| L3 | **话题名取目录名** | 总纲文件名 = 目录名(`src/state.ts:225-226`)。重命名目录会使总纲文件名与目录名不匹配,`resolveOverview` 的第 2 步会失效 |
| L4 | **路径推导不校验 `docs/` 之外** | `entryPath` / `planDir` 是纯字符串拼接,不做越界检查。越界由 `resolveDocPath` 在入口处拒绝(`src/state.ts:216-221`) |
