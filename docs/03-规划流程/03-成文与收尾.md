# 03 规划流程 / 03 · 成文与收尾

## 1. 文档的定位

**【规则】** `docs/` 是本项目的**开发文档 (development)**,取代传统的根目录 `development.md`。构建方式、测试命令、目录约定、各话题的设计结论都住在这里;入口是 `docs/INDEX.md`。

**【依据】** 见 `../02-文档规范/03` §5。定位写进纪律是必需的 —— 否则模型会把 `docs/` 当作「本次规划的产物暂存处」,而它实际上是**长期维护的开发文档**。定位不同,写法就不同(见 §2)。

## 2. 四条硬规矩

**【规则】** 文档是项目文档,**不是这一次的变化记录**。违反即退回:

| # | 规矩 | 理由 |
| --- | --- | --- |
| 1 | **不写按日期排布的变化记录 / 变更日志** | 变化交给 git,`git diff` 就是本次计划 |
| 2 | **不写决策记录** | 决策会变;「为什么这么定」进 git commit message,文档只留**结果** |
| 3 | **不写一次性计划表 / 待办清单** | 要拆解用 `deep_plan_task`(给执行阶段用,不进文档) |
| 4 | **维护完整** | 没有 TBD、没有留白、不与本文其余部分或 `docs/` 里其它文档矛盾 |

**【依据】** 前三条有一个共同点:它们都是**把短期信息写进长期文档**。日期、决策、待办都有明确的时效性,而文档会长期存在。写进去之后,文档就开始随每轮迭代积累自相矛盾。第 4 条是结果要求:一份有留白的文档无法被当作契约使用,因为读者不知道空白处是「没有」还是「还没写」。

**【规则】** 已有文档**就地完善**(改、补、删),**不新建平行文档**。

**【依据】** 同一话题的两份文档会各自演化,而读者读到哪一份取决于他先翻到哪个。`/deep-plan-docs` 能列出全部文档,但仍需要人来发现重复。就地完善是避免产生的唯一办法。

## 3. 结果进文档,决策进 commit

这是本部分最重要的约定,完整理由见 `../02-文档规范/03` §1。分工:

| 内容 | 写在哪 | 为什么 |
| --- | --- | --- |
| 术语 / 规范用语 / `_Avoid_` | 文档的术语小节 | 长期稳定,是共识不是取舍 |
| 目标 / 非目标 | 文档 | 结论,形态稳定 |
| 风险与回滚 | 文档 | 结论 |
| 计划(可独立验收的条目) | 文档 + `deep_plan_task` | 结论 |
| **为什么这么定、否决了什么** | **git commit message** | 决策会变,commit 记的是当时 |
| 提问式规划的问答过程 | 不落盘 | 过程,不是产出 |

**【规则】** 收尾提交时把决策与理由写进 **commit message 正文**(几段散文,说清取舍与否决项)。

**【依据】** commit 是时间点快照,天然记录「当时为什么这么定」。文档是长期维护的,固化会被推翻的推理等于持续制造自相矛盾。**扩展不替用户跑 git**(`../00-总览/01` 的 N1),它只要求提交时带上这些内容。

## 4. 内容要求

**【规则】** 每条结论**附证据**(路径:行号 或 URL),**不许形容词**。

**【依据】** 「很流行」「看起来不错」这类判断无法被检验,也无法在后来被推翻 —— 它们不携带信息。`src/state.ts:191` 或一条 URL 可以让下一个人自己去看。这是本套文档自身的证据标注约定(`../../INDEX.md` §2)在纪律层的对应要求。

**【规则】** 可变决策表 3–8 行,每行是**已生效的默认值**。

**【规则】** 「非目标」「开放问题」**不许空着**。查不到就写「未能查证 + 已尝试的路径」。

**【依据】** 空着的「开放问题」有两种解读:真的没有未知,或者没认真找。要求填写「已尝试的路径」把后者暴露出来。

## 5. 任务拆解

**【规则】** 用 `deep_plan_task` 拆解执行阶段的任务:

| 动作 | 用途 |
| --- | --- |
| `action=title` | 确立**动作开头的单句标题** + 范围(整个流程只做一次) |
| `action=add` | 逐条追加,每条必须**可独立验收** |
| `action=list` | 复核清单与进度 |

**【规则】** 任务**至少一条**,否则 `deep_plan_review` 退回(`src/index.ts:549-551`)。

**【依据】** 没有任务拆解意味着执行阶段没有可对照的验收点 —— 它会退化成「按文档大概做做」。最少一条保证了「方案里说的改动」与「执行时核对的东西」之间存在显式对应。

## 6. 收尾呈现契约

**【规则】** `deep_plan_review` 校验通过后,**一次**呈现三样东西(`SKILL.md` P4):

| # | 呈现 | 要求 |
| --- | --- | --- |
| 1 | 文档路径 | 写成 markdown 链接(结果里已给好,原样复制)。**不要把正文贴进对话** |
| 2 | 可变决策表全文 | 用户逐项过目的部分 |
| 3 | 任务清单 | — |

然后说明两步:先只提交文档 → 提交完成后问是否批准进入执行阶段。

**【规则】** 呈现后**停住**等回话,不要自己往下开工。

**【依据】** 呈现的目的是取得用户判断,而判断需要时间。若在同一轮里既呈现又开工,用户看到的时候工作已经做完 —— 审查点就失去了意义。

**【规则】** 只给「路径 + 可变决策表 + 任务清单」,**不重贴文档正文**。

**【依据】** 正文可能很长,贴进对话会淹没真正需要看的部分(可变决策表)。文档本身可通过路径打开,不需要复制一份。

## 7. 提交说明

**【规则】** 呈现时说明:先只提交文档,给出示例

```
git add docs/ && git commit -m "docs: ..."
```

并注明 README、AGENTS.md 等**不在 `docs/` 内**的文件属于代码提交,不要混进来。提交归属按本轮对话的指令(见 `../02-文档规范/03` §4)。

**【依据】** 「文档一次提交、代码一次提交」的边界在实际操作中会被「顺手把所有改动一起提交」破坏。示例命令与那句提醒把边界具体化到命令行层面 —— `git add docs/` 与 `git add -A` 的差别就是边界本身。

## 8. 反模式清单

出现任一项即停手重来(`SKILL.md` 的反模式节)。

### 8.1 规划方式

| 反模式 | 正确做法 |
| --- | --- |
| 规划中途停下来问用户 | 自问自答;确需用户定夺的记成可变决策项,收尾一起审 |
| 把没验证的推断写进 `Verified Facts` 或当既定事实 | 标 `[推断]` 或进开放问题 |
| 出现「待用户确认」的占位符 | 改成可变决策表里一行带默认值的 V |
| 跳过提问环节直接给结论 | 每个 frontier 问题都要先写问题、再写答案 |

### 8.2 文档写法

| 反模式 | 正确做法 |
| --- | --- |
| 文档里写按日期排布的变化记录 / 变更日志 | 变化交给 git |
| 文档里写一次性计划表或待办清单 | 拆解用 `deep_plan_task` |
| 同一主题新建平行文档 | 就地完善已有文档,并在 `INDEX.md` 定位它 |
| 把计划条目塞回总纲的子标题 | 一个计划条目一个文件 |
| 给条目文件写 frontmatter | frontmatter 只属于总纲;条目是纯正文 |
| 文档里写决策记录 / 建 `decisions/` / 建 `docs/adr/` | 决策的家是 git commit message |
| 留下 TBD / 留白 / 与其它文档矛盾 | 文档必须自洽完整 |
| 把文档正文再贴一遍进对话 | 只给路径 + 可变决策表 + 任务清单 |

### 8.3 越过门禁

| 反模式 | 正确做法 |
| --- | --- |
| 用 `bash mkdir` 建话题文件夹 | 用 `write` 写第一个文件,父目录自动创建 |
| 被范围限制拦住后改用 bash 重定向绕开 | 立刻停止;这是纪律违背 |
| 呈现完之后自己往下开工 | 停住等用户提交文档并批准 |
| 把两段提交混在一起 | 第一阶段只提交 `docs/`;第二阶段只提交仓库代码 |

### 8.4 执行与回退

| 反模式 | 正确做法 |
| --- | --- |
| 发现文档冲突后绕过它继续做 | 停手,`deep_plan_revise conflict=true`(见 `04`) |
| 把中止执行说成「任务已完成」 | 受阻的任务必须 `unblock` 后再做,不能算 done |
| 可变决策表为空或超过 8 条 | 回到提问式规划;`deep_plan_review` 会退回 |

**【依据】** 反模式清单与规则清单是同一套约定的两种写法。规则说「该做什么」,反模式说「最容易做错的是什么」——后者按实际出错频率排列,是规则的补充而非重复。

## 9. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **反模式只能"停手重来",无强制** | 清单写在注入文案里。违反不会被工具拦住,只能靠模型遵守与用户发现 |
| L2 | **「不重贴正文」无检查** | 呈现时贴了正文,工具不会报错 |
| L3 | **索引同步靠纪律** | 新建话题后忘记更新 `INDEX.md`,不会被拦;`/deep-plan-docs` 只能展示出漂移 |
| L4 | **`docs/` 之外的文件归属靠提醒** | README、AGENTS.md 属于代码提交,这一点写在文案里。混进文档提交不会被拦 |
| L5 | **「附证据」是格式要求,不是正确性要求** | 门禁不验证证据是否真实存在、行号是否对得上。本套文档自身的行号也会随代码漂移 |
