# 05 测试与验收 / 03 · 回归风险点

## 怎么用

**【规则】** 改动下面任一处之前,先读表里对应的「信号」列 —— 那是这个改动出错时**能观察到**的现象。

**【依据】** 回归之所以难发现,是因为改动者看的是自己改的那个函数,而错误出现在它与别处的接口上。把「接口 + 出错时的现象」写在一起,使改动者能预判要去看哪里。

## 1. 门禁相关的风险(最高)

| # | 改动 | 会破坏什么 | 出错信号 |
| --- | --- | --- | --- |
| R1 | 给工具改名,或新增写工具却不登记 `FILE_MUTATION_TOOLS` | 该工具完全不参与判定(`../01-写入门禁/01` §3) | 文档阶段能改仓库文件,**没有任何报错或提示**。这是最隐蔽的一类 —— 只有主动尝试才会发现 |
| R2 | 放宽 `extractWriteTarget` 的多锚点一致性(改成「任一命中即可」) | 混合锚点编辑可以穿过门禁 | `replace` 的两个锚点分属 `docs/` 与仓库时**不再被拦**(A4 第 4 条) |
| R3 | 把 `isDocPath` 的前缀判定换成字符串 `startsWith("docs")` | `docsite/` 之类的路径被误认为文档 | 写 `docsite/x.md` 在文档阶段**被放行**;`../00-总览/02` §2 |
| R4 | 调整 `isWriteAllowed` 的判定顺序(把阶段判定放到 scratch 之前) | scratch 在文档阶段被拒 | 子代理报告写 `.pi/tmp/` **被拦**(A2 第 4 条) |
| R5 | 放宽 `readonly.ts` 的重定向豁免(把 `>&` 一律当无害) | `>& file` 变成可写 | `du -sh x >& file` **被放行**(`readonly.test.ts` 的 DENIED 第 3、4 条会失败) |
| R6 | 改 `READ_ONLY_BINARIES`,或删掉某个命令的逐参数规则 | 该命令的子命令/危险参数不再受限 | `git commit` 或 `find -exec` **被放行**(A3 第 7 条) |
| R7 | 改 `SERVED_ROW_RE`(放宽锚点形状) | 正文被误认成锚点行 | 锚点编辑被**误拦**,或指向错误的文件 |
| R8 | 改 `HASH_SEP` 或锚点参数名表 `ANCHOR_FIELDS` | 某类锚点无法解析 | 该工具的锚点编辑一律「锚点无法定位到文件」(A4 第 3 条的表现) |

**【规则】** R1–R8 任一处改动后,**必须**跑 `npm test`,并按 `02` 的 A2–A4 手工验一遍。

**【依据】** 这些改动都在判定逻辑里,而判定逻辑的错误方向是「静默放行」。它不会抛错,只会让门禁在某条路径上失去作用。

## 2. 路径与布局相关的风险

| # | 改动 | 会破坏什么 | 出错信号 |
| --- | --- | --- | --- |
| R9 | 改 `resolveDocPath` 的三条规则(尤其「裸名」的分支) | 既有用法的含义漂移 | 文档被建到用户没指定的位置(`../02-文档规范/01` §2) |
| R10 | 去掉 `resolveOverview` 的文件夹跟随 | 话题迁入文件夹后阶段转移失效 | `deep_plan_finish` 报「文档不存在,跳过定稿」(A9) |
| R11 | 改 `padSequence` 的位数 | 文件系统排序错乱 | 条目文件列表里 `0010` 排在 `0009` 之前 |
| R12 | 改 `listDocs` / `listEntryFiles` 的递归范围 | 文档漏收或误收 | `/deep-plan-docs` 的输出与实际目录不符;`deep_plan_review` 漏掉空条目文件 |
| R13 | 改 `extractWriteTarget` 的路径解析方式(见 `../01-写入门禁/01` 的 L2b) | 锚点判定的基准与 `isWriteAllowed` 不一致 | 两者 cwd 不同时锚点编辑判定错位。正常运行下不显现,**只在测试或嵌入场景暴露** |

## 3. 状态相关的风险

| # | 改动 | 会破坏什么 | 出错信号 |
| --- | --- | --- | --- |
| R14 | 新增 `Phase` 取值但不更新 `fromPersisted` 的折叠 | 旧会话恢复后落在错误的一侧 | 老会话恢复后能写它本不该写的一侧(`../00-总览/02` §5) |
| R15 | 新增 `PlanState` 字段但漏进 `toPersisted` | 该字段不持久化 | 会话重开后该字段丢失,行为回到默认值 |
| R16 | 让 `INACTIVE` 被直接使用(不展开 `{ ...INACTIVE }`) | 共享常量被污染 | 上一次 run 的可变决策/任务出现在下一次 run 里 |
| R17 | 把 `INACTIVE.phase` 改成 `"executing"` | 忘记判 `active` 的地方变成放行 | 门禁关闭状态下仍按执行阶段放行(反之更危险) |
| R18 | 新增一条改变 `phase` 的代码路径 | 阶段变化的可审计性下降 | `/deep-plan-status` 显示与最后一次显式工具调用不符 |

**【规则】** R14–R18 的验证方式:**重启会话**后用 `/deep-plan-status` 核对阶段与内容。

**【依据】** 状态相关的错误只在**跨会话恢复**时显现,单次运行里看不出来。这是本清单里唯一需要「重开会话」才能验的一类。

## 4. 纪律与文案相关的风险

这是**唯一无法靠测试发现**的一类 —— 文案不在测试范围内(`01` §4 的第 7 项)。

| # | 改动 | 会破坏什么 | 出错信号 |
| --- | --- | --- | --- |
| R19 | 改注入文案时删掉某条纪律 | 模型不再受该约束 | 只有观察实际运行才会发现;`02` 的 A8 第 4 条覆盖了「中止原因出现在注入里」这一项 |
| R20 | 改注入文案的空行处理(用空串想插空行) | 空行被 `filter` 吃掉 | 注入文案排版挤在一起(`../04-扩展接口/02` §1) |
| R21 | 改 `SKILL.md` 但没同步注入,或反之 | 三份表达漂移 | 模型的行为与文档描述不符;`../../INDEX.md` 维护约定第 3 条 |
| R22 | 改 `plan-format.md` 的骨架但不改文档 | 规范与实现不一致 | `deep_plan_review` 的校验与骨架要求不匹配 |

**【规则】** R19、R21、R22 的改动必须在提交信息里说明「文案改了哪一条」,以便后来核对。

**【依据】** 文案的改动没有自动检查,唯一的补偿是让人在提交历史里能看到「这次动了哪条纪律」。

## 5. 任务与回退相关的风险

| # | 改动 | 会破坏什么 | 出错信号 |
| --- | --- | --- | --- |
| R23 | 去掉 `deep_plan_step` 的阶段守卫 | 文档阶段就能声称执行进度 | 批准之前任务就能被标 `done`(`../03-规划流程/04` §3) |
| R24 | 让 `revise` 不再先标记受阻任务 | 任务在前提被重写时仍显示 `active` | A8 第 5 步显示 `active` 而不是 `blocked` |
| R25 | 让 `approve` 顺带清除任务状态 | 受阻任务的「未完成」事实被抹掉 | A8 第 7 步的 T1 不再是 `blocked` |
| R26 | 让 `haltReason` 在 `revise` 时就清除 | 回到文档阶段时不知道为何而回 | A8 第 4 步的注入里没有中止原因 |
| R27 | 允许删除非 `planned` 状态的任务 | 历史痕迹失去对应物 | 已 `done` 的任务能被删掉(`../03-规划流程/04` §2.1) |

## 6. 优先级

**【规则】** 改动时按下面优先级决定验收强度:

| 优先级 | 范围 | 必须做的验证 |
| --- | --- | --- |
| **高** | R1–R8(门禁判定) | `npm test` **且** 手工跑 `02` 的 A2–A4 |
| **中** | R9–R13(路径)、R14–R18(状态) | `npm test`;R14–R18 额外重开会话核对 |
| **低** | R19–R22(文案) | 通读改动前后的差异;确认三份表达同步 |
| **中** | R23–R27(任务/回退) | 手工跑 `02` 的 A8 |

**【依据】** 优先级按「出错后多久才会被发现」排列:门禁的漏洞可能长期不被察觉(R1 尤其),而文案的改动下一次运行就能感觉到不对劲。

## 7. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **R1 无法自动检查** | 「所有写工具都登记了」是一个全称判断,需要知道环境里有哪些工具。当前没有这个清单,只能人工核对 |
| L2 | **R13 在正常运行下不显现** | 它只在 cwd 不一致的场景暴露,因此不会被 `02` 的手工验收发现 |
| L3 | **R19–R22 无任何检查** | 文案不在测试范围内,也没有断言。这是本清单里唯一完全依赖认真的部分 |
| L4 | **本表靠人工维护** | 新增风险点需要有人主动加进来;代码变化不会提醒这张表已过时 |
