# 项目文档格式

文档写入 `docs/` 下。**本次目标文档**由 `/deep-plan <目标> [--doc <路径>]` 确定;
阶段一期间,`docs/` 下**任意**文档与 `.pi/tmp/`(子代理报告)可写。

**范围是 harness 层的硬拦截。** 阶段一仅放行 `docs/` 内的写入;`edit`/`write`/`replace`/`replace_match`/`insert`/`copy`/`move`/`undo_last_change`
对 `docs/` 之外的写入会被直接阻断。`bash`/`powershell` 仅放行只读命令。被拦截时不得改用重定向或其他工具绕过。**实际只读、只是未被识别的命令**可用 `deep_plan_request_allow` 申请一次性放行(须带 `readOnly=true` 与只读依据,需用户同意;同一命令再次调用仍需申请);写类命令不得申请。
修改已有文档须带 `path`(或整篇 `write` 覆盖);否则门禁无法判定目标,一律拦截。

## docs/ 是开发文档 (development)

`docs/` 即本项目的**开发文档**,取代传统的根目录 `development.md`:
构建方式、测试命令、目录约定与各话题的设计**结论**均收录于此。

- **入口是 `docs/INDEX.md`**:一行一个话题,并指向该话题的入口文件。新成员从该文件开始阅读。
- 撰写项目的开发方式这类内容时,写入 `docs/` 下的对应话题;**不得**在仓库根目录新建 `development.md`。

## 布局:话题是文件夹,计划条目是文件

`docs/` 下每**一个话题**是一个文件夹,话题内部的**每个计划条目**是一个文件:

```
docs/
  INDEX.md                     话题索引 / 开发文档入口
  <topic>/
    <topic>.md                 总纲:概览 / 目标与非目标 / 术语 / 风险 / 开放问题
    plan/NNNN-<slug>.md        一个计划条目一个文件
```

- 话题文件夹只在需要时建。旧的单文件话题 `docs/<slug>.md` 仍然合法(没有条目可分的文档
  不值得拆),但**别为同一话题再建一份平行文档** —— 就地完善已有的那份。
- 建文件夹**用 `write` 写第一个文件**(自动建父目录)。`bash mkdir` 被阶段一的只读门禁拒绝,
  不要试图绕过。
- 条目文件为**纯正文**,不写 frontmatter;frontmatter 仅属于总纲。
- 编号用四位零填充(`0001`),文件系统排序即顺序。**不查编号连续性**:完整性由
  `deep_plan_task` 的任务清单承担,不靠文件名。

## 这是项目文档,不是变化记录

四条硬规矩,违反即退回:

- **不写按日期排布的变化记录 / 变更日志。** 变化交给 git,`git diff` 就是本次计划。
- **不写决策记录。** 决策会变(见下节),规定理由写进 **git commit message**。
- **不写一次性计划表 / 待办清单。** 要做拆解用 `deep_plan_task`(给执行阶段用,不进文档)。
- **维护完整、自洽。** 没有 TBD、没有留白、不与本文其余部分或 `docs/` 里其它文档矛盾。
  已有文档**就地完善**;新建文档要同步更新 `docs/INDEX.md`。

### 写作语体(违反即退回)

文档正文用**规范陈述语体**:陈述事实、规定要求、说明理由。判据是「该句可被当作规范条款宣读」。七项禁令:

| # | 禁止 | 改成 |
| --- | --- | --- |
| 1 | `他` / `它` / `他们` / `它们` 指代机制、文档、工具、字段 | 重复该对象的名称;指代人时用「用户」「执行者」「维护者」 |
| 2 | 疑问句与疑问式标题 | 名词短语:「为什么是这两个阶段」→「阶段划分依据」;「锚点是什么」→「锚点定义」 |
| 3 | 「动词 + 什么」短语 | 「做什么」→「能力范围」;「不做什么」→「非目标范围」;「不含什么」→「边界」;「会破坏什么」→「破坏对象」;「什么时候读」→「阅读时机」 |
| 4 | 「一句话」「说明白」「讲清楚」「讲明白」 | 「一句话定位」→「定位总览」;优先用 概括 / 总览 / 解释 / 说明 |
| 5 | 口语与比喻:悄悄 / 炸掉 / 顺手 / 拖慢 / 摸不着 / 很难发现 / 踩坑 / 麻烦 / 拉平 / 干掉 | 静默 / 导致失效 / (删除) / 增加开销 / 无法定位 / 不易察觉 / 缺陷 / 开销 / 展平 / 删除 |
| 6 | 第二人称「你」「您」 | 角色名,或改为无人称陈述 |
| 7 | 【依据】写成口语推理 | 规范陈述:不用比喻拟人、不反问;因果用「因…故…」「…将导致…」 |
| 8 | 非规范动作动词 | 「落进」→「写入」;「只放」→「仅收录」;「跑 git」→「执行 git」;「塞进」→「纳入」;「拆成」→「拆分」 |
| 9 | 拟人化与含糊搭配 | 「回答"要跟着变哪些"」→「须说明:用户修改后哪些步骤须随之变更」;「不是待定的」→「须为已确定的值」;「不是形容词」→「不得使用无判据的修饰性描述」 |
| 10 | 无判据的程度词 | 「自问不够狠」→「自问程度不足,未能识别出足够多的可变决策项」 |
| 11 | 「一次性」不得简写为「一次」 | 「一次呈现」→「一次性呈现」;「第一次打扰用户」→「首次打扰用户」 |
| 12 | 正反杂糅(规定行为与禁止行为合写进一句) | 「文档是规格,不是现状记录」→ 分列「文档描述代码应有的行为」与「文档不得记录代码的当前状态」 |

**不受约束、按原文保留**:代码块与标识符、命令行、正则、工具返回文案、引文、参数示例(如 `reason="<具体的冲突是什么>"`)、术语与固定语。引用原文时**不得**为迁就语体而改写被引内容。

`其他` / `其余` / `其它` 是限定词,不属禁令 1。

注意:上表禁令针对**叙述**部分;直接指示行动的祈使句(「不要写变更日志」「先改文档再改代码」)是规范文本的正常构成,照常使用。

完整定义见 `docs/INDEX.md` §3.1 与 `docs/02-文档规范/04-写作语体.md`。

### 文档只留结果,决策留在 git commit

**决策是变值,不是定值。** 一条决策今天写进文档,几轮问答后很可能被推翻;而文档是
**长期维护**的,把会被推翻的推理固化进去,等于持续制造自相矛盾。commit 是**时间点快照**,
天然记录议题在当时确定下来的理由,`git log` 就是决策的演进史。

| 内容 | 写在哪 |
|---|---|
| 术语、规范用语、`_Avoid_` | 文档的术语小节 |
| 目标 / 非目标 | 文档 |
| 风险与回滚 | 文档 |
| 计划(可独立验收的条目) | 文档 + `deep_plan_task` |
| 提问式规划的问答过程 | 不写入文件(过程不是产出) |
| **规定理由与否决事项** | **git commit message** |

因此:**不得创建 `docs/<topic>/decisions/`,不得创建 `docs/adr/`,不得写「决策记录」小节。**
拿到结论后,须把结论转换为结果性内容:选定的做法写入「计划」,确定的术语写入「术语」,
排除的范围写入「非目标」。收尾提交时,把决策与理由写入 commit message 正文。

````md

> 这是长期维护的项目文档。不要写变更日志、日期版本或一次性计划表。

## 概览
3-5 句:现状、目标状态、实施时机依据。

## 目标 / 非目标
- 目标: <可验收的陈述>
- 非目标: <明确排除的范围>（没有非目标的方案不可信）


## 术语与领域模型

本项目的**规范用语**与**刻意避免的说法**。仅收录本项目特有的概念,不收录通用编程概念。
术语是列表语义,天然属于文件内结构 —— **不得**拆分为单独的文件。

格式:

```md
**<规范术语>**:
<给出该术语的定义:说明其指代的对象,而非其用途或动作>
_Avoid_: <被否决的同义词>
```

- 存在多个词指同一概念时,采用最精确的一个,其余记入 `_Avoid_`。
- 定义长度限一两句。
- 仅当术语自然成组时添加子标题;仅有一组时平铺列出。

**<规范术语>**:
<给出该术语的定义>
_Avoid_: <被否决的同义词>

**这是用户唯一需要逐项过目的部分。** 表格见下节。

## 计划

1. <动作> — 验收方式: <确认该步完成的方法>
2. ...

## 风险与回滚
| 风险 | 触发信号 | 应对 | 回滚方式 |

## 开放问题
查证不到的事实,写「未能查证 + 已尝试的检索路径」。不要编造。
````

## 可变决策表 schema

每行一个决策。四列缺一不可:

````md
| # | 决策项 | 默认值 | 依据 | 改动代价 |
|---|--------|--------|------|----------|
| V1 | <决策项> | **<Agent 已选的默认值>** | <依据> | 低/中/高 + 改动影响 |
````

规则:

- **默认值必须已生效**:须为已确定并可直接执行的值,不得填写未确定的值或建议值。
- **依据**必须给出证据:文件路径与行号、URL,或命令输出;不得使用无判据的修饰性描述。
- **改动代价**须说明:用户修改该项后,哪些步骤须随之变更。
- 仅收录**用户可能有不同偏好**的项:取舍、范围、依赖引入、文件位置、命名、
  是否新增文件、触发方式。不收录纯技术事实。
- 行数限 3–8 行。超过 8 行表明应拆分为多份文档;少于 3 行表明自问程度不足,未能识别出足够多的可变决策项。
- 用户修改某项后,须把修改写入文档的相应小节(选定的做法写入「计划」、确定的术语写入「术语」、
  排除的范围写入「非目标」),并把本次修改的理由写入 git commit message。

## 收尾呈现契约

文档写完后,`deep_plan_review` 校验通过,以**一次性**呈现的方式给出下列内容:

1. 文档路径 —— 写成 markdown 链接(结果里已给好,原样复制),**不要把正文贴进对话**。
2. 可变决策表全文。
3. 任务清单。
4. 下一步:**先只提交文档**(`git add docs/ && git commit -m "docs: ..."`)。
   提交归属按**本轮对话的指令**确定:默认由执行者提交;用户若表示「提交由我来」,则交由用户提交。
   提交完成后再询问用户是否批准进入执行阶段。
5. 进入执行阶段后的**代码单独成一个 commit**,和文档那次分开 —— 这条不变。

呈现后停止,等待用户答复。不得在同一轮内既呈现又开工。
提交按上述归属规则执行;归属不明时先询问用户,不得推定。
