# 04 扩展接口 / 01 · 命令与工具清单

## 1. 三个命令

命令是**面向用户**的入口。全部**不触发模型调用**(`deep-plan` 启动时发送一条用户消息是唯一例外)。

| 命令 | 参数 | 触发模型 | 作用 | 行 |
| --- | --- | --- | --- | --- |
| `/deep-plan` | `<目标> [--doc <路径>]` | **是**(发一条 `pi.sendUserMessage`) | 启动一次 run | `:305-366` |
| `/deep-plan-status` | 无 | 否(纯 UI 通知) | 显示当前阶段、文档、可变决策 | `:368-383` |
| `/deep-plan-docs` | 无 | 否(纯 UI 通知) | 列出 `docs/` 文档与索引状态 | `:385-419` |

**【规则】** 后两个命令必须**不**触发模型调用。

**【依据】** 后两个命令属**查询**命令 —— 用户查看状态时不应付出一次模型往返的代价与延迟。

### 1.1 `/deep-plan` 的参数解析

```
/--doc(?:=|\s+)(\S+)/        ← 提取路径(:309)
raw.replace(/--doc(?:=|\s+)\S+/, "")   ← 从目标里剥离(:311)
```

两种写法都接受:`--doc docs/foo/` 与 `--doc=docs/foo/`。

**【规则】** 目标是必填的;为空时提示用法并**不**启动(`src/index.ts:317-324`)。

**【依据】** 目标决定了默认文档路径(经 slug)与注入文案中的规划主题。缺目标时启动将得到一个没有主题的 run —— 不如直接提示用法。

### 1.2 已在进行的处理

**【规则】** 已有进行中的 run 时(`state.active` 为真),提供三选一(`src/index.ts:325-338`):

| 选项 | 行为 |
| --- | --- |
| 继续当前规划 | 发一条「继续当前 deep-plan(<阶段>)」消息 |
| 放弃并重新开始 | 状态重置为 `INACTIVE`,继续启动新 run |
| 取消 | 不改变任何状态 |

**无 UI 时默认「继续当前规划」**(`:329`)。

**【依据】** 直接覆盖一个进行中的 run 将丢失该 run 的可变决策与任务。要求用户显式选择「放弃」,使丢失是有意的。无 UI 时选择最保守的一侧:继续而非重置。

### 1.3 启动时的提示

启动后发送一条通知,包含(`src/index.ts:347-355`):阶段、**是完善已有文档还是新建**、文档路径、`docs/` 现有文档数、以及「两段提交是分开的」。

**【依据】** 「新建与完善」决定模型的写法 —— 新建须写出完整骨架,完善须就地改。该信息应在启动时即给出。

### 1.4 `/deep-plan-docs` 的分组

按布局分组显示(`src/index.ts:393-407`):

| 判定 | 显示 |
| --- | --- |
| `docs/INDEX.md` | `索引` |
| `docs/<topic>/<topic>.md`(目录名 = 文件名) | `话题 <topic>/` |
| 层级 ≥ 3 | `条目` |
| 其余 | `单文件` |

末尾附索引存在性;缺失时用 `warning` 级提示(`:408-412`)。

**【依据】** 这是唯一可观察「索引与实际内容是否漂移」的入口,故必须**如实展示**两者,不做修正。

## 2. 八个工具

工具是**面向模型**的入口。全部用 `Type.Object` 声明参数。

### 2.1 六个核心工具(来自 `index.ts`)

| 工具 | 参数 | 作用 | 行 |
| --- | --- | --- | --- |
| `deep_plan_start` | `goal`(必)、`doc`(选) | 启动文档阶段。命令入口不可用时的备用入口 | `:420-476` |
| `deep_plan_record_variable` | `item`、`defaultValue`、`evidence`、`cost`(全必) | 记录一条可变决策 | `:479-512` |
| `deep_plan_review` | 无 | 收尾文档阶段:校验 + 呈现 | `:514-605` |
| `deep_plan_approve` | `approvalNote`(选) | 进入执行阶段 | `:607-656` |
| `deep_plan_revise` | `reason`(必)、`conflict`(选) | 回到文档阶段 | `:658-721` |
| `deep_plan_finish` | `outcome`(必)、`status`(选) | 结束并定稿 | `:723-780` |

### 2.2 两个任务工具(来自 `tasks.ts`)

| 工具 | 参数 | 作用 | 行 |
| --- | --- | --- | --- |
| `deep_plan_task` | `action`、`title`、`scope`、`taskId` | 任务**结构**:title / add / list / update / remove | `src/tasks.ts:61-180` |
| `deep_plan_step` | `action`、`taskId`、`note` | 任务**状态**:start / done / skip / block / unblock | `src/tasks.ts:182-303` |

动作细节与状态机见 `../03-规划流程/04` §2。

**【规则】** `deep_plan_start` 的 description 必须写明「仅在命令入口不可用时使用」。

**【依据】** 正常入口是 `/deep-plan`。模型若习惯性调用该工具启动,将绕过命令中的交互(已有 run 时三选一)与提示。将该工具标为备用入口,使默认路径明确。

**【规则】** `deep_plan_task` 与 `deep_plan_step` 的**分工**必须体现在各自的 description 里:`task` 管结构且文档阶段可用,`step` 管状态且仅执行阶段可用。

**【依据】** 两个工具的 action 词形相近(一为 `add`,一为 `start`),未写明分工则倾向混用。分工是真实约束(`src/tasks.ts:209` 的阶段守卫),description 必须与该约束一致。

## 3. 阶段转移的触发者

| 转移 | 触发 | 行 |
| --- | --- | --- |
| (未启动) → `writing` | `/deep-plan` 或 `deep_plan_start` | `:344`、`:450` |
| `writing` → `executing` | `deep_plan_approve` | `:634` |
| `executing` → `writing` | `deep_plan_revise` | `:696` |
| 任意 → (未启动) | `deep_plan_finish` | `:757` |

**【规则】** 除此之外**没有**别的代码路径改变 `phase`。

**【依据】** 阶段是门禁的唯一输入之一,任何隐式的阶段变更都会导致「当前阶段」难以推理。将阶段变更限制在四个显式工具调用上,使阶段变化始终对应一次可审计的模型动作。

## 4. 工具的返回值约定

**【规则】** 工具返回 `content: [{ type: "text", text: ... }]`,文本是**给人读的**;`details` 一律为 `undefined`。

**【规则】** 已经满足条件时不抛错,而是返回一句说明:

| 情况 | 返回 |
| --- | --- |
| `deep_plan_start` 且已有进行中的 run | 「deep-plan 已在进行中(<阶段>)」+ 现状摘要(`:441-446`) |
| `deep_plan_review` 且已不在 `writing` | 「当前阶段是 <phase>,文档阶段已收尾」(`:522-527`) |
| `deep_plan_revise` 且已在 `writing` | 「已在文档阶段,docs/ 本就可写」(`:666-672`) |
| `deep_plan_task action=remove` 且状态非 `planned` | 抛错,说明只能删除尚未开始的任务(`src/tasks.ts:162`) |

**【依据】** 对**幂等的重复调用**,返回说明而不抛错 —— 模型重试同一动作时,抛错将引发以失败原因排查为目的的额外轮次,而事实是该项工作已经成立。对**违反约束的调用**(删除已开始的任务)抛错,因其确属违规。

## 5. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **`deep_plan_start` 的 description 与命令功能重复** | 两者都能启动,但有交互差异。模型需读 description 才能确定用哪一个 |
| L2 | **可变决策无删除动作** | 仅有 `deep_plan_record_variable`(追加)。记错一行时,只能靠后续重写文档时忽略该行,记录本身仍留在状态里 |
| L3 | **`deep_plan_finish` 的 `outcome` 不进文档** | 该值只出现在工具返回值里(`src/index.ts:764`),没有被写进文档或状态。结束原因因此只有本次对话可见 |
| L4 | **无 `deep_plan_cancel`** | 「放弃」只能在 `/deep-plan` 的交互里选择,或走 `deep_plan_finish status=abandoned` |
| L5 | **命令不返回结构化结果** | 三个命令都走 `ui.notify`,文本无法被程序消费 |
| L6 | **`deep_plan_finish` 的 status 与文档 status 取值不同名** | 参数用 `done` / `abandoned`,写进 frontmatter 的是 `approved` / `writing`(`src/index.ts:745-749`)。两套词表之间有一次映射 |
