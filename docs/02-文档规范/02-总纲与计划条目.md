# 02 文档规范 / 02 · 总纲与计划条目

## 1. 总纲骨架

总纲是话题的主文档,承载**结果性内容**。`skills/deep-plan/references/plan-format.md` 给出面向模型的可读版本,本节给出契约与理由。

```
# <文档标题:本文档的覆盖范围>
> 这是长期维护的项目文档。不要写变更日志、日期版本或一次性计划表。

## 概览            # 3-5 句:现状、目标状态、实施时机依据
## 目标 / 非目标    # 目标可验收;非目标明确排除
## 术语与领域模型    # 本项目的规范用语与刻意避免的说法
## 可变决策         # 用户唯一需要逐项过目的部分(表见 §4)
## 计划            # 能独立验收的条目,不是待办清单
## 风险与回滚       # 风险 / 触发信号 / 应对 / 回滚方式
## 开放问题         # 未能查证的事实:「未能查证 + 已尝试的检索路径」
```

**【规则】** 总纲**必须**有非空正文。只有 frontmatter 的文档会被 `deep_plan_review` 拒绝(`src/index.ts:538-539`)。

**【规则】** 「非目标」不得为空。

**【依据】** 一份没有排除范围的方案无法被验证 —— 方案未界定排除范围,故任何偏离均可被解释为「本就在范围内」。写出非目标等于写下判据:事后可判断某项改动是否应归属于本次范围。

**【规则】** 「开放问题」中未能查证的事实必须写成「未能查证」并附上已尝试的检索路径,**禁止编造**。

**【依据】** 未知写成已知是这类文档最贵的错误:该写法使不确定性表现为确定结论,后续所有依赖该结论的判断都会连带出错。写下检索路径使下一个人能从该处继续,而不必从头试一遍。

## 2. 计划条目

**【规则】** 每个计划条目**一个文件**,存放于话题的 `plan/` 下,文件名 `NNNN-<slug>.md`。条目文件是**纯正文**,不写 frontmatter。

**【依据】** 一个文件一个条目使条目能被单独链接、单独评审、单独引用(`plan-format.md` 记录了这条动机)。埋在总纲的 `##` 小标题里做不到这一点。

**【规则】** frontmatter **只属于总纲**。

**【依据】** 条目的生命周期状态由 `deep_plan_task` 的任务状态承担(见 `04-扩展接口/03`)。若条目文件也带 `status`,则状态存在两处:`deep_plan_task` 记为 `done`、文件头记为 `writing`,读者无法确定以哪一处为准。故文件只承载内容,状态只存在于一处。

**【规则】** 条目内容须写成**能独立验收**的形式:说明实施内容,并给出该步骤的确认方式。

**【依据】** 「能独立验收」是任务拆解的定义(见 `../03-规划流程/04`)。不可验收的条目在执行阶段无法判断是否完成,将退化为「认为已做完」。

**【规则】** 条目文件必须**非空正文**。空文件或只有空白的文件会被 `deep_plan_review` 拒绝并指名(`src/index.ts:551-560`)。

**【依据】** 一个空条目文件等同于「有小标题而无正文」—— 而一项一条目这一拆分方式,仅当每个文件确实载有内容时才有价值。空文件是最易漏掉的形式缺陷:该文件在目录列表里与正常条目无异。

**【不采纳】** 不检查条目编号连续(`../02-文档规范/01` §4)。编号仅负责排序,完整性由任务列表承担。

## 3. frontmatter

字段表(`src/archive.ts:17-24`):

| 字段 | 类型 | 谁写 | 含义 |
| --- | --- | --- | --- |
| `title` | `string` | 阶段转移时 | 文档标题 |
| `status` | `writing` \| `approved` | 阶段转移时 | 文档所处阶段 |
| `topics` | `string` | 阶段转移时 | 本文档覆盖的话题,供后续 run 路由 |
| `created` | `string` | 阶段转移时 | 创建日期 |
| `updated` | `string` | 阶段转移时 | 更新日期 |
| `approved` | `string` | `deep_plan_approve` | 批准日期 |

**【规则】** frontmatter 由扩展在**阶段转移时重新写入**(`stampDoc`,`src/archive.ts:103`),模型无需维护该字段。

**【依据】** 若由模型维护 frontmatter,一次整篇 `write` 覆盖即可能使其丢失,而丢失的后果是「文档不再有阶段标记」—— 一项静默的元数据损失。由扩展在每个转移点重写,模型即无需记录该字段(`src/archive.ts:4-6` 的注释说明了这一点)。

**【规则】** 解析只认 `---` 包裹的 `key: value`,不引入 YAML 库(`src/archive.ts:27` 的正则)。

**【依据】** 见 `../00-总览/01` §3 的 N5。`FIELD_ORDER` 固定了字段渲染顺序(`src/archive.ts:52-58`),使同一次转移的写入是稳定的。

### 文件不存在时的行为

**【规则】** `stampDoc()` 在文件不存在时**返回 `undefined` 且不创建文件**(`src/archive.ts:107-113`)。

**【依据】** 阶段转移工具(如 `deep_plan_finish`)可能在文档已被移走或删除后调用。此时创建空文档比不创建更糟 —— 该做法将留下一份没有内容的「定稿」。返回 `undefined` 使调用方获知定稿被跳过,并如实报告(见 `../04-扩展接口/01`)。

## 4. 可变决策表

```
| # | 决策项 | 默认值 | 依据 | 改动代价 |
|---|--------|--------|------|----------|
| V1 | <决策项> | **<已选的默认值>** | <依据> | 低/中/高 + 改动影响 |
```

| 规则 | 内容 |
| --- | --- |
| 默认值必须已生效 | 不是「待定」,不是「建议」。方案按该值可直接执行 |
| 依据须给证据 | 文件路径与行号 / URL / 命令输出;不得使用无判据的修饰性描述 |
| 改动代价要具体 | 载明改动该项后须随之调整的步骤 |
| 仅收录偏好类项 | 取舍、范围、依赖引入、文件位置、命名、是否新增文件、触发方式 |
| 不收录纯技术事实 | 「Node 支持 `path.relative`」不是决策 |
| 条数 **3–8** | 超过 8 行表明应拆分为多份文档;少于 3 行表明自问深度不足 |

**【规则】** 可变决策是**用户唯一需要逐项过目的部分**(`plan-format.md`)。

**【依据】** 可变决策应限于仅用户可裁定的事项,即偏好与取舍。技术事实与执行细节记入正文,无需用户逐项审查。若将两者混同,审查成本将由「3 分钟看完」上升为「读完整份文档」。

**【规则】** 用户修改某项后,须把修改写入文档的相应小节(选定的做法写入「计划」、确定的术语写入「术语」、排除的范围写入「非目标」),并把理由写入 commit message。

**【依据】** 可变决策表是**面向用户**的摘要,正文才是权威。若仅改表而不改正文,文档内部将出现两个版本 —— 读者获取的版本取决于检索命中的小节。

**【依据】** 3–8 的上下限来自 `deep_plan_review` 的校验(`src/index.ts:542-548`):少于 3 条被视为「自问深度不足」,多于 8 条被视为「应拆分为多个文档」。

## 5. 校验汇总

`deep_plan_review`(`src/index.ts:514-605`)按顺序检查:

| # | 检查 | 不通过时 | 行 |
| --- | --- | --- | --- |
| 1 | 当前阶段是 `writing` | 提示「文档阶段已收尾」 | `:522-527` |
| 2 | 文档路径已分配 | 抛错 | `:528` |
| 3 | 总纲正文非空 | 抛错「文档正文为空」 | `:540` |
| 4 | 可变决策 3–8 条 | 记为问题 | `:542-548` |
| 5 | 任务列表非空 | 记为问题 | `:549-551` |
| 6 | 每个条目文件正文非空 | 记为问题并指名文件 | `:557-565` |

**【规则】** 检查 4–6 是**累积**的(收集全部问题一次报出),检查 1–3 是**立即失败**的。

**【依据】** 前三条不通过时根本无法继续校验(阶段不对、无路径、读不到文件);后三条互相独立,一次性报全可使问题在**一轮**内改完,而不必逐个试错。

## 6. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **总纲骨架无强制字段** | 校验只查「正文非空」,不检查骨架的小节是否齐全。少写「非目标」不会被工具拦住,只能靠纪律与用户审阅 |
| L2 | **不检查文档间的一致性** | 两个话题文档互相矛盾时工具不会发现。跨文档一致性靠 `../03-规划流程/03` 的纪律 |
| L3 | **条目与任务非一一对应** | `deep_plan_review` 只要求「任务列表非空」,不要求每个条目文件都有一个任务,反之亦然。两者是不同层的产物 |
| L4 | **frontmatter 字段值不做语义校验** | `status` 之外的字段只做字符串收敛,不验证日期格式 |
