# 交接

把当前会话压缩成一条交接,写入项目根 `AGENTS.md`,并与仓库当前改动一并提交。

## AGENTS.md 的结构

**【规则】** 文件只含两部分:项目用途(1 至 2 句)与交接。交接占全文绝大部分。

**【规则】** 约定、命令、规范不写入本文件。这类内容归项目的长期文档;在本项目中是 `docs/`,入口为 `docs/INDEX.md`。

**【依据】** `AGENTS.md` 每次交接整体重写,而约定长期不变。两类内容的寿命不同:混在一处时,约定会随交接被覆盖,交接会被约定淹没。

## 交接的内容

**【规则】** 各节按下列顺序书写。**下次交接时整节替换**,不做增量追加。

| 节 | 内容 |
| --- | --- |
| 上次完成的工作 | 上次做了什么,粒度到可核对 |
| 当前仓库状况 | 工作树是否干净,进行到哪一步 |
| 未决问题 | 等用户裁决的事项 |
| 后续任务 | 仅在用户指定时写入;未指定时明写「用户未指定后续任务」 |

**【规则】** 全文末尾附时间戳,含日期、时间、时区。

**【规则】** 不重复 `docs/`、提交信息与 diff 已有的内容;需要时给出路径。

**【依据】** 交接的用途是使下一个会话在数分钟内知道从哪里继续。重复既有信息会挤占上下文;给出路径使读者按需取用。

## 提交

**【规则】** 先更新 `AGENTS.md`,再 `git add -A`,与仓库当前改动一并提交。提交信息描述本次实际改动,不以「更新交接」充当主要描述。

**【规则】** 存在进行中的 deep-plan 时,先 `deep_plan_finish` 再更新 `AGENTS.md`。定稿会重命名文档,该重命名属同一次提交。

**【规则】** 完成的标准是 `git status --short` 为空。

**【依据】** 一并提交使下一个会话从一致的 git 快照继续;分开提交会在下一次无关改动中留下仅含交接的噪声。

## 语体

**【规则】** 正文遵守项目已定义的写作规范。本项目的规范见 `docs/INDEX.md` §3.1。
