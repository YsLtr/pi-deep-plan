# 方案文档格式

方案写在仓库内 `docs/plans/<YYYY-MM-DD>-<slug>.md`。它是 P1–P3 期间唯一允许写的文件
(`.pi/tmp/` 除外,那是子代理报告的 scratch)。

**写保护是 harness 层的硬拦截。** `edit`/`write`/`replace`/`replace_match`/`insert`/
`copy`/`move`/`undo_last_change` 对其它路径的写入会被直接阻断,`bash`/`powershell`
只放行只读命令;被拦时不要用重定向或别的工具绕。改方案文档本身也要带 `path`
(或整篇 `write` 覆盖),否则门禁无法判定目标而一律拦下。
## 骨架

````md
# <任务标题：动作开头的单句>

## 概览
3-5 句话：现状是什么、要改成什么、为什么现在做。

## 目标 / 非目标
- 目标: <可验收的陈述>
- 非目标: <明确排除的范围>（没有非目标的方案不可信）

## 决策记录
每条自问自答的结论。格式：

### D<n>. <决策标题>
- **结论**: <选定的做法>
- **依据**: <证据；来自查证的附文件路径:行号 或 来源 URL>
- **置信度**: 高 / 中 / 低
- **备选**: <被否决的方案与否决理由>
- **备选**: <被否决的方案与否决理由>

够得上 ADR 的硬决策（难反转 / 读者会问"为什么这么干" / 真权衡过）在这一条里补 ADR 语义的备选，
真正的 ADR 文件与 `CONTEXT.md` 都是 P5 的任务，不在规划阶段创建。

置信度低的结论必须同时出现在「可变决策表」里。

## 术语与领域模型

domain-modeling 在规划阶段的落点：本项目的**规范用语**与**刻意避免的说法**。
按 `domain-modeling/CONTEXT-FORMAT.md` 的格式写，只放本项目特有的概念，不放通用编程概念。

**<规范术语>**:
<一两句话说明它是什么>
_Avoid_: <被否决的同义词>

落盘到仓库根的 `CONTEXT.md` 是 P5 的任务；本方案只承载内容。

## 可变决策
**这是用户唯一需要逐项过目的部分。** 表格见下节。

## 执行步骤
编号，每步可独立验收：

1. <动作> — 验收: <怎么确认这步成了>
2. ...

## 风险与回滚
| 风险 | 触发信号 | 应对 | 回滚方式 |

## 开放问题
查证不到的事实，写「未能查证 + 已尝试的检索路径」。不要编造。
````

## 可变决策表 schema

每行一个决策。四列缺一不可：

````md
| # | 决策项 | 默认值 | 依据 | 改动代价 |
|---|--------|--------|------|----------|
| V1 | <一句话说明这是什么选择> | **<Agent 已选的默认值>** | <为什么选它> | 低/中/高 + 一句话说明改了会怎样 |
````

规则：

- **默认值必须是已生效的**，不是待定的。方案按默认值即可直接执行。
- **依据**要给证据（文件路径:行号 / URL / 命令输出），不是形容词。
- **改动代价**回答"用户改了这一项，方案里哪些步骤要跟着变"。
- 只放**用户可能有不同偏好**的项：取舍、范围、依赖引入、落盘位置、命名、
  是否新增文件、触发方式。不要放纯技术事实。
- 控制在 3-8 行。超过 8 行说明该拆成多个方案；少于 3 行说明自问不够狠。
- 用户改动后，把改动同步进「决策记录」，保持两份一致。

## 单一审查呈现契约

方案写完后，**一次**呈现给用户，包含：

1. 方案文档路径——写成 markdown 链接（`deep_plan_review` 结果里已给好，原样复制），
   **不要把正文贴进对话**，正文只存在于文档里，用户自己打开看。
2. 可变决策表全文。
3. 三个选项：**批准执行** / **修改可变决策** / **打回重做**。

呈现后停住，等用户回话。不要在同一轮里既呈现又开工。
