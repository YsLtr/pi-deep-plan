# Deep Plan

把非平凡任务**先落成文档,再落成代码**,全程不问用户任何问题。用户只在两处介入:
提问式规划**不**面向用户(问题与答案都由你给),用户只在收尾审查文档、以及批准开始改代码。

**两个大阶段:**

| 阶段 | 可写范围 | 产出 | 提交 |
| --- | --- | --- | --- |
| 一、文档 | `docs/` 下任意文档 (+ `.pi/tmp/` scratch) | 完善后的项目文档 | **只提交文档** |
| 二、执行 | 仓库其余部分(`docs/` 冻结) | 代码改动 | **只提交仓库** |

阶段一内部仍是 `自问 → 自查 → 成文 → 收尾`,但**不再按日期产出一次性计划**:
文档是长期维护的项目开发文档,变化交给 git,`git diff` 就是本次计划。

本 skill 由 `pi-deep-plan` 扩展提供**harness 层强制**:两个阶段的可写范围都被实际拦截,
不是靠自觉。门禁细节见下方 P0。

---

## P0. 启动与文档位置

用 `/deep-plan <目标> [--doc <路径>]` 启动。扩展会立刻:

- 定位**目标总纲**:`--doc docs/topic/`(结尾斜杠)或指向已存在目录 → 话题文件夹
  `docs/topic/topic.md`;`--doc docs/x.md` → 该文件;裸名 `--doc docs/x` → 仍按文件处理(兼容);
  完全不给 `--doc` → 按目标的 slug 定位 `docs/<slug>.md`(同一话题再次规划落到同一份文档)
- 把可写范围限制在 `docs/` 下 + `.pi/tmp/`,仓库其余部分一律拦截
- 拦截所有编辑器工具对 docs/ 之外的写入(`edit`/`write`/`replace`/`replace_match`/`insert`/`copy`/`move`/`undo_last_change`)
- 把 `bash`/`powershell` 限制在只读命令白名单内
- 状态栏显示当前阶段

被拦时不要尝试绕过:文档阶段就是只改文档,`deep_plan_approve` 是用户批准后用的,不是绕门工具。

改已有文档时必须**带 `path`**(或改用 `write` 整篇覆盖):`replace`/`insert` 这类按行编辑靠锚点定文件,
锚点定位不到时门禁会一律拦下。

本 skill 自带两套纪律,**不需要加载任何外部 skill**:提问式规划见 P1,文档写法见
[references/plan-format.md](./references/plan-format.md),事实查证见
[references/research-contract.md](./references/research-contract.md)。


## P1. 提问式规划(自问自答)

用**设计树 + frontier** 把方案问清楚。这是本 skill 自己的纪律,不要去找外部 skill。

- 把方案展开成一棵**设计树**:每个决策分出挂在它下面的子决策。
- 按**轮**推进。**frontier** = 前置已定、现在就能答的问题。一轮把整个 frontier 问完。
- 每个问题**编号**,并**当场给出你的推荐答案**,再算下一轮 frontier。
- 问题的答案依赖同一轮里另一个未决问题 → 它属于**更晚**的一轮,不属于这一轮。
这是**自问自答**的提问式规划:**问题由你提,答案也由你给**。用户不在这一环里 ——
他不会看到这些问题,也不该被这些问题打断(唯一的例外见下方"确需用户定夺时")。

一轮的格式:

```
❓ **Q1** - **<问题标题>**: <问题正文,可以多点、带选项>

➡️ <你的推荐答案>

---

❓ **Q2** - **<问题标题>**: ...

➡️ <你的推荐答案>
```

**提问与回答环节是强制的,不是可选的:**
每轮推进都必须**先写出问题、再写出答案**这两步。跳过提问直接给结论 = 漏掉了规划过程,
收尾时会被 `deep_plan_review` 退回(它要求「可变决策」至少 3 条 —— 那是 frontier 里
真正需要取舍的那些问题的落点)。只写问题不给答案同样不算。

铁律:

- **找事实是你的活。** 环境里能查到的事实自己去查(见 P2),不要写进问题里当待办。
- **答案自己给,并给推荐理由。** 每个 frontier 问题都给出你的推荐答案,不要留空。
- **frontier 为空**才算问完:每条分支都走到,没有东西被默默假设。
- **确需用户定夺时**才记成「可变决策」(V1、V2...),用一个已生效的默认值暴露出来,
  留给收尾审查;不要在规划中途停下来问用户。
- 问完(写进文档)之后才进入 P3 成文。

提问式规划的产出是**结论**,不是文档正文:问出来的结论以「术语」「目标 / 非目标」「计划」
这类**结果**写进文档(见 P3),**「为什么这么定」留在 git commit 里**。
决策会变,所以不把决策过程固化进文档 —— 详见 P3。

## 文档的定位

`docs/` 就是本项目的**开发文档 (development)**,它取代了传统的根目录 `development.md`:
构建、测试、约定、各话题的设计结论都住在这里,`docs/INDEX.md` 是入口。

## P2. 自查(派子代理,不问用户)

**找到事实是你的活,永远不是用户的活。** 一次 `subagent` 调用、`children` 数组
并行派发,并发 ≤ 3,简报自包含。

- 联网事实 → `researcher`;代码库现状 → `scout`;已有改动审查 → `code-reviewer`。
- 派发契约、报告大纲、停止判据见扩展包内 `references/research-contract.md`。
- **不要阻塞**:子代理是异步的。等报告期间继续推进不依赖它的 frontier 问题。
- 报告回来后**先验证再采信**:文件是否真存在、结论是否带路径:行号或 URL。
- 报告写入 `.pi/tmp/`(scratch,不受门禁限制)。子代理只证明现状,方案由你写。

## P3. 成文(写好这份文档)

把内容写进本次的目标文档。骨架与各节要求见扩展包内 `references/plan-format.md`。

**文档是项目文档,不是这一次的变化记录。** 四条硬规矩:

- **不写按日期排布的变化记录。** 变化交给 git,`git diff` 就是本次计划。
- **不写决策记录。** 决策会变 —— 「为什么这么定」写进 **git commit message**,
  文档只留**结果**。理由与边界见下节。
- **不写一次性计划表 / 待办清单。** 要拆解就用 `deep_plan_task`(那是给执行阶段用的,不进文档)。
- **维护完整。** 没有 TBD、没有留白、不与文档其余部分或 `docs/` 里其它文档相互矛盾。
  已有的目标文档**就地完善**(改、补、删),不要新建平行文档。

### 文档只留结果,决策留在 git commit(重要)

这是本 skill 的长期约定:**决策是变值,不是定值。** 一条决策今天写进文档,三轮问答后很可能
被推翻;文档是**长期维护**的,固化会被推翻的推理等于持续制造自相矛盾。而 commit 是
**时间点快照**,天然记录「当时为什么这么定」,翻 `git log` 就能看到演进。

| 内容 | 写在哪 | 为什么 |
|---|---|---|
| 术语 / 规范用语 / `_Avoid_` | 文档的术语小节 | 长期稳定,是共识不是取舍 |
| 目标 / 非目标 | 文档 | 结论,会随话题演进但形态稳定 |
| 风险与回滚 | 文档 | 结论 |
| 计划(可独立验收的条目) | 文档 + `deep_plan_task` | 结论 |
| **为什么这么定、否决了什么** | **git commit message** | 决策会变,commit 记的是当时 |
| 提问式规划的问答过程 | 不落盘 | 过程,不是产出 |

实作:

- **不要建 `docs/<topic>/decisions/`,不要建 `docs/adr/`,不要写「决策记录」小节。**
- 拿到决策结论后,把它**变成结果性内容**写进文档:选定的做法进「计划」,
  定下的词进「术语」,划掉的范围进「非目标」。**推理过程不进文档。**
- 收尾提交时,把决策与理由写进 **commit message 正文**(几段散文,说清取舍与否决项)。
  扩展不替你跑 git,只要求提交时带上这些内容。

内容要求:

- 每条结论附证据(路径:行号 或 URL),不许形容词。
- 「可变决策表」3-8 行,每行是**已生效的默认值**:提问式规划覆盖不到的取舍、或用户当时没定的
  细节,自己定一个默认值并在这里暴露,收尾时让用户逐项推翻。
- 「非目标」「开放问题」不许空着。查不到就写"未能查证 + 已尝试的路径"。
再拆解执行阶段的任务:

- `deep_plan_task action=title` 确立**动作开头的单句标题** + 范围(整个流程只做一次)。
- `deep_plan_task action=add` 逐条追加,每条必须**可独立验收**。
- `deep_plan_task action=list` 复核清单与进度。

写完调 `deep_plan_review` 收尾。它会校验:文档正文非空、可变决策 3-8 条、
**任务至少一条**、**计划条目文件都非空**。
不达标会退回并列出原因。

## P4. 收尾与提交文档(第一次打扰用户)

`deep_plan_review` 校验通过后,**一次**呈现:

1. 文档路径 —— 写成 markdown 链接(结果里已经给好,原样复制)。**不要把正文贴进对话**。
2. **可变决策表全文** —— 用户逐项过目的部分。
3. 任务清单。

然后说明接下来的两步:

1. **先只提交文档** —— 提交归属按**本轮对话的指令**:默认由你(执行者)提交;
   用户说"提交由我来"就交给用户,扩展本身从不代跑 git。给出示例:

   ```
   git add docs/ && git commit -m "docs: ..."
   ```

   注意:README、AGENTS.md 等**不在 docs/ 内**的文件属于代码提交,不要混进来。
2. 提交完成后,再问是否批准进入执行阶段。

呈现后**停住**等回话,不要自己往下开工。

用户要改文档 → 用 `deep_plan_revise` 回到文档阶段(已经在文档阶段就直接改),
改完再 `deep_plan_review`。

---

## P5. 执行(批准后)

用户批准后调 `deep_plan_approve`:**`docs/` 冻结**,仓库其余部分放开。于是两个阶段的
提交天然分开 —— 文档那次已经在 P4 提交过,这里产生的只会是代码。

- `deep_plan_step action=start` 开始一个任务(同时只能有一个进行中)。
- 做完对照该任务的验收方式确认,再 `deep_plan_step action=done`。
- 卡住时用 `action=block note=...` 记录受阻原因,解除后 `action=unblock`;确实不做的用 `action=skip`。
### 发现文档冲突 → 停止执行,不要绕过(硬要求)

执行中**必须停下来回到文档阶段**的情况:

- 文档描述与实际代码不符(文档说 A,仓库里是 B)
- 文档内部自相矛盾,或本方案的细节和文档别处打架
- 文档漏掉了你正需要的事实,靠猜才能继续
- 照文档做下去会破坏文档里明确的非目标或约束

遇到任一种,**不要**「照实际代码改」去迁就过时的文档,也不要只在代码注释里记一笔。
正确动作:

```
deep_plan_revise conflict=true reason="<具体的冲突是什么>"
```

它会把进行中的任务标为**受阻**、冻结仓库、放开 `docs/`,并记录中止原因(下一次运行会看到)。
然后在文档阶段把文档改对 → `deep_plan_review` 重新收尾 → **再提交一次文档** → 用户批准后继续。
受阻的任务修完后用 `deep_plan_step action=unblock` 恢复,**不要**当成已完成。

只是措辞小瑕疵、不影响执行正确性 → 不值得中止,记下来等收尾时一并处理。

- 执行中冒出的新决策:小改直接做并记录;**改变已批准范围的**也要先回文档阶段,
  不要自作主张扩大范围。
- 全部任务完成后调 `deep_plan_finish` 收尾。它把文档定稿(写在原地,不归档、不改名)。
- **提交边界(硬要求)**:这个阶段的提交**只包含仓库代码**。
  `docs/` 的改动属于第一阶段,已经提过了;若确需再改文档,按上面走 revise 并单独提交。
  判断标准:`git add -A && git status --short` 里不应出现 `docs/`。
- **与 handoff 合并**:需要更新 `AGENTS.md` 并提交时,按 `~/.pi/agent/skills/handoff/SKILL.md` 走。
  `AGENTS.md` 不在 `docs/` 内,属于代码提交,和代码一起提交是对的。

## 文档的生命周期

扩展在阶段转换时自动维护文档的 frontmatter,你不需要手写:

```yaml
---
title: <文档标题>
status: writing | approved     # writing=文档阶段;approved=已批准执行
topics: <这份文档覆盖的主题>
created: YYYY-MM-DD
updated: YYYY-MM-DD
approved: YYYY-MM-DD
---
```

**文档长期留在 `docs/` 原地**:不归档、不按日期重命名、不按日期新建。同一主题的再次规划
会落到同一份文档上继续完善。历史由 git 记录 —— 这也是为什么文档里不写变化记录。

**索引**:`docs/INDEX.md` 是**话题清单 / 开发文档入口**,一行一个话题并指向它的总纲(入口)。
新增话题、或某话题的范围变了,都要同步更新它。
用 `/deep-plan-docs` 可以列出当前 docs/ 的文档与索引状态(按 索引/话题/条目/单文件 分组)。

**决策不在文档里**:它的唯一出处是 git commit message。文档不写决策记录、不建
`decisions/`、不建 `docs/adr/` —— 决策会变,而文档要长期自洽。

## 反模式(出现即停手重来)

- **规划中途停下来问用户** → P1 是自问自答:事实自己查,答案自己给;确实需要用户定夺的记成 V,收尾一起审。
- 把没验证的推断写进 `Verified Facts` 或当作既定事实 → 标 `[推断]` 或进开放问题。
- 出现"待用户确认"的占位符 → 改成「可变决策表」里一行带默认值的 V。
- **文档里写按日期排布的变化记录 / 变更日志** → 变化交给 git,`git diff` 就是本次计划。
- **文档里写一次性计划表或待办清单** → 拆解用 `deep_plan_task`,文档只写长期有效的项目内容。
- **同一主题新建一份平行文档** → 就地完善已有文档,并在 `docs/INDEX.md` 里定位它。
- **把计划条目塞回总纲的子标题**(条目已经该各自成文件时)→ 一个计划条目一个文件。
- **用 `bash mkdir` 建话题文件夹** → 用 `write` 写第一个文件,父目录自动创建;mkdir 会被门禁拒绝。
- **给条目文件写 frontmatter** → frontmatter 只属于总纲;条目是纯正文。
- **在文档里写决策记录 / 建 `decisions/` / 建 `docs/adr/`** → 决策会变,它的家是 git commit message。
- **跳过提问环节直接给结论** → P1 是强制的:每个 frontier 问题都要先写出问题、再写出答案。
- 文档里留下 TBD / 留白 / 与 `docs/` 其它文档矛盾 → 文档必须自洽完整。
- 被范围限制拦住后改用 bash 重定向绕开 → 立刻停止,这是纪律违背。
- 呈现完之后自己往下开工 → P4 必须停住等用户提交文档并批准。
- 把文档正文再贴一遍进对话 → 只给路径 + 可变决策表 + 任务清单。
- 把两段提交混在一起 → 第一阶段只提交 `docs/`;第二阶段只提交仓库代码。
- **发现文档冲突后绕过它继续做**(照代码改、写进注释、当成已知偏差)→ 停手,`deep_plan_revise conflict=true`。
- 把中止执行说成"任务已完成" → 受阻的任务必须 `unblock` 后再做,不能算 done。
- 可变决策表为空或超过 8 条 → `deep_plan_review` 会退回;自问深度不对,回到 P1。
