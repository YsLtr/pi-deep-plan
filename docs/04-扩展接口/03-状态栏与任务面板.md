# 04 扩展接口 / 03 · 状态栏与任务面板

## 1. `sync()` 的唯一刷新点

**【规则】** 所有 UI 刷新都经过一个函数 `sync(ctx)`(`src/index.ts:48-74`),在每次状态变化后调用。

| 时机 | 调用方 |
| --- | --- |
| 恢复会话 | `session_start`(`:117`) |
| 命令启动 | `/deep-plan`(`:353`) |
| 工具启动 | `deep_plan_start`(`:459`) |
| 阶段转移 | `approve` / `revise` / `finish` |
| 任务增删 | `deep_plan_task` |
| 任务推进 | `deep_plan_step` |

**【依据】** 单一刷新点使「界面显示的是最新状态」成为一条结构性保证 —— 任何改变状态的地方只要调 `sync`,界面就一致。若各处自行更新不同的 UI 部分,就会产生「状态栏说执行阶段、面板还在显示文档阶段的任务」这类分裂。

**【规则】** `!ctx.hasUI` 时直接返回(`src/index.ts:49`)。

**【依据】** 非交互环境(如 `pi -p` 无头运行)没有状态栏。提前返回避免在每个环境里都判一次能力。

## 2. 状态栏

**【规则】** 状态栏用 `setStatus(STATUS_KEY, label)`,`active` 为假时传 `undefined` 清除(`src/index.ts:51`)。

文案两态(`src/index.ts:57-60`):

| 阶段 | 颜色 | 文案 |
| --- | --- | --- |
| `writing` | `warning` | `◐ deep-plan: 文档阶段 (仅 docs/ 可写)<进度>` |
| `executing` | `success` | `▶ deep-plan: 执行阶段 (docs 冻结)<进度>` |

进度后缀仅在有任务时出现:` ${done}/${total}`(`src/index.ts:56`)。

**【依据】** 颜色区分**限制强度**:文档阶段用 `warning`(受限、需要小心),执行阶段用 `success`(已解锁)。这不是装饰 —— 用户扫一眼状态栏就该知道「现在能不能改代码」。

**【依据】** 无任务时不显示 `0/0`:那会让读者以为是「进度为零」,而事实是「还没有任务清单」。

**【规则】** 文案里必须同时给出**阶段名**与**可写范围**,不能只给阶段名。

**【依据】** 「文档阶段」是内部术语,用户不一定知道它意味着什么;括注的「仅 docs/ 可写」把含义直接给出。用户不需要读懂术语就能判断当前能否改代码。

## 3. 任务面板

**【规则】** 面板显示条件是 **`tasks.length > 0` 且 `phase === "executing"`**(`src/index.ts:63`)。

**【依据】** 面板的目的是显示**执行进度**,而进度只在执行阶段有意义。文档阶段虽然也能建任务(`deep_plan_task` 可用),但那些任务尚未开始 —— 此时显示面板会把「已规划」误读成「正在进行」。等批准后再显示,面板的出现本身就标志着进入执行阶段。

**【规则】** 面板首行是任务标题(缺失时用「任务清单」),用 `muted` 颜色(`src/index.ts:65`)。

**【规则】** `setWidget` 包在 `try/catch` 里(`src/index.ts:66-70`),捕获失败后忽略。

**【依据】** `setWidget` 在非交互 TUI 里可能不可用。面板是辅助显示,不该因为环境不支持而中断工具执行。

**【规则】** 不满足显示条件时调 `setWidget(WIDGET_KEY, undefined)` 清除(`src/index.ts:72`)。

**【依据】** 与状态栏同理:不清除会让上一个阶段的面板留在界面上。

## 4. 任务行的渲染

任务行由 `renderTaskLines(tasks, theme)` 产生(`src/tasks.ts:32-41`),状态用符号标记(`src/tasks.ts:24-30`):

| 状态 | 符号 |
| --- | --- |
| `planned` | ☐ |
| `active` | ▶ |
| `done` | ☑ |
| `skipped` | ⤼ |
| `blocked` | ⛔ |

**【依据】** 符号使一整列任务能在一行一个的形式下快速扫读 —— 颜色与符号配合,让「哪些还没做」在视觉上直接可见。

## 5. 进度统计

**【规则】** 进度用 `progressOf(tasks)`(`src/tasks.ts:43-47`),**`skipped` 不计入总数**。

**【依据】** `skipped` 的任务是**决定不做**的,不是待完成的。把它算进分母会让进度永远到不了满 —— 一个已经明确放弃的任务会让「全部完成」这个状态不可达。

**【规则】** 进度格式为 `done/total`,只用在状态栏后缀与 `deep_plan_task action=list` 的输出里。

## 6. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **面板不显示可变决策** | 可变决策要靠 `/deep-plan-status` 查看。面板只显示任务 |
| L2 | **面板不显示受阻原因** | `blocked` 任务显示 ⛔ 符号,但 `note`(受阻原因)不在面板里 —— 它只在 `deep_plan_task action=list` 的输出中 |
| L3 | **进度不含 `skipped`** | 一个任务被 `skip` 后总数会减少,进度可能从 `2/5` 跳到 `2/4`。这是刻意的(见 §5),但看起来像进度增加了 |
| L4 | **`setWidget` 失败被静默忽略** | `catch` 块为空,失败不产生任何提示。在不支持面板的环境里,用户不会知道自己少了这块显示 |
| L5 | **`STATUS_KEY` / `WIDGET_KEY` 为常量** | 同一会话里只能有一处状态与一处面板;扩展不支持同时显示多个 run 的进度 |
