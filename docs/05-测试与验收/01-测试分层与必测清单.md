# 05 测试与验收 / 01 · 测试分层与必测清单

## 1. 分层

**【规则】** 两层:**纯函数自动化测试**(`npm test`)+ **手工集成验收**(`02`)。不引入测试框架,采用 Node 内置 test runner。

| 层 | 覆盖 | 命令 | 文件 |
| --- | --- | --- | --- |
| 自动化 | 判定逻辑(路径、门禁、锚点、命令) | `npm test` | `src/state.test.ts`、`src/readonly.test.ts` |
| 手工 | 钩子、命令、工具、注入、UI | 见 `02` | — |

**【依据】** 判定逻辑是**可穷举的纯函数**:给定输入,输出确定。这类逻辑用自动化测试能覆盖全部边界,且**拦错一次的代价很高**(挡住正常开发),值得测试。而钩子与工具的行为需要真实的会话、UI 与工具调用链,构造成本高于收益 —— 上述行为的正确性靠 `02` 的手工清单与门禁返回文案的直观性来保证。

**【依据】** 不引入测试框架:`package.json` 的 test 脚本直接执行 `node --experimental-strip-types --test src/*.test.ts`(`../00-总览/04` §2)。测试文件只用 `node:assert/strict` 与 `node:test` 两个内置模块。

## 2. `src/state.test.ts` 必测清单

共 **12 个 test**(其中 2 个按平台跳过)。

| # | test 名 | 断言的判定 | 行 |
| --- | --- | --- | --- |
| 1 | `planLink builds a clickable markdown link (windows)` | Windows 路径下的链接形式。**仅 win32 运行** | `:24` |
| 2 | `planLink builds a clickable markdown link (posix)` | POSIX 路径下的链接形式。**仅非 win32 运行** | `:31` |
| 3 | `planLink keeps a path outside cwd absolute` | cwd 之外的路径保持绝对 | `:38` |
| 4 | `planLink keeps non-ascii hrefs percent-decoded` | 非 ASCII 路径**不做百分号编码** | `:44` |
| 5 | `entryPath names one file per plan item` | `planDir` / `0001` 补零 / slug 归一 | `:54` |
| 6 | `gate covers the whole anchored editor family` | `FILE_MUTATION_TOOLS` 含全部 8 个写工具 | `:69` |
| 7 | `extractWriteTarget resolves anchored edits through the resolver` | 锚点解析成功;混合/部分不可解析时 **fail closed** | `:78` |
| 8 | `extractWriteTarget reports unidentifiable and foreign calls distinctly` | `undefined`(外来工具)与 `""`(无法归属)可区分 | `:103` |
| 9 | `isWriteAllowed scopes each stage to its own side of docs/` | 文档阶段:`docs/` 树 + scratch;执行阶段:仓库,`docs/` 拒 | `:115` |
| 10 | `collectAnchors reads served and diff rows, ignores prose` | 服务行与 `+`/`-` diff 行都识别;正文不误判 | `:144` |
| 11 | `resolveDocPath accepts folder,file,explicit and bare forms` | 四种输入形态各产出正确路径 | `:173` |
| 12 | `resolveOverview follows a topic that moved into its folder` | 话题迁入文件夹后仍能找到总纲 | `:206` |

**【规则】** 平台相关的 test 必须用 `{ skip: ... }` 显式跳过,而不是在函数体里 `if` 返回。

**【依据】** `skip` 会使 test runner 报告为「跳过」(`:24`、`:31`),在结果里可见;函数体内 `if` 返回会被报告为「通过」—— 那是在报告里伪造了一个未执行的断言。

**【规则】** 断言失败时必须带上下文(`assert.equal(actual, expected, message)`)。

**【依据】** 门禁测试的失败信息须能定位到「产生该结果的输入」,否则一个失败只会显示 `false !== true`。

## 3. `src/readonly.test.ts` 必测清单

共 **2 个 test**,用两个命令数组驱动。

### 3.1 `readers pass the planning gate`(`:29`)

`ALLOWED` 数组(`:8-18`),9 条:

| # | 命令 | 覆盖的规则 |
| --- | --- | --- |
| 1 | `cd /repo && ls -la && echo "---" && cat package.json` | `cd` 在白名单;多段命令逐段判定 |
| 2 | `ls -la docs/adr 2>&1 \| head -60` | `2>&1` 是无害重定向;管道拆分 |
| 3 | `head -25 ... && echo '=== pkg ===' && cat package.json` | 单引号内容不被当命令 |
| 4 | `grep -rn todo src/` | 基础白名单 |
| 5 | `git status` | `git` 只读子命令 |
| 6 | `du -sh docs legacy dist 2>/dev/null` | `> /dev/null` 无害 |
| 7 | `du -sh dist 2>&1 >/dev/null` | `2>&1` 与 `>/dev/null` 组合 |
| 8 | `FOO=1 grep -rn "selectors" ... 2>/dev/null \| head -10` | `VAR=` 前缀;引号内内容;管道 |
| 9 | `cat x 2>&-` | `>&-`(关闭描述符)无害 |

### 3.2 `writers and unknown commands stay blocked`(`:36`)

`DENIED` 数组(`:21-27`),6 条:

| # | 命令 | 覆盖的规则 |
| --- | --- | --- |
| 1 | `echo x > out.txt` | `>` 写文件 |
| 2 | `echo x >> /dev/null.bak` | `>>` 目标**不是** `/dev/null` |
| 3 | `du -sh x >& file` | `>& file` 省略 fd 号 = 写文件(关键用例) |
| 4 | `du -sh x >& /tmp/f` | 同上,路径形式 |
| 5 | `echo hi 2>&1 > out.txt` | 无害与有害重定向混合 |
| 6 | `rm -rf src` | 拒绝清单 |

**【规则】** `>& file` 与 `>& /tmp/f` **必须**留在 DENIED 里(第 3、4 条)。

**【依据】** 这两条是同一条规则(§`../01-写入门禁/02` 的「省略 fd 号的 `>&` 仍是写文件」)的回归测试。把 `>&` 一律视为无害将漏掉该规则 —— 而漏掉的后果是文档阶段可以借助 stdout 重定向写文件。

**【规则】** 无害重定向的正例与反例必须**成对**出现:每一条「应该放行」的重定向形态,都要有一条「看起来像但实际会写」的反例。

**【依据】** 重定向判定是白名单式豁免,最易出现的错误是豁免过宽。成对的正反例使放宽的改动立刻被捕获。

## 4. 未覆盖项

| # | 未覆盖 | 风险 |
| --- | --- | --- |
| 1 | 钩子行为(`session_start` / `tool_call` / `before_agent_start`) | 门禁的实际拦截只由手工验收覆盖;`extractWriteTarget` 已测,但「该函数被正确接进 `tool_call`」未测 |
| 2 | 命令的实现(`/deep-plan` 的参数解析、已有 run 的三选一) | `--doc` 的 `=值` 形式、三选一的三个分支都无自动化覆盖 |
| 3 | 六个核心工具的校验顺序 | `deep_plan_review` 的六项检查(见 `../02-文档规范/02` §5)只在手工清单里验证 |
| 4 | 状态持久化的往返 | `toPersisted` / `fromPersisted` 的字段与折叠逻辑没有测试 |
| 5 | `tasks.ts` 的状态机 | 非法转移(重复 `start`、对非 `blocked` 调 `unblock`)无测试 |
| 6 | `archive.ts` 的 frontmatter 往返 | 解析 / 渲染 / 写入的边界(引号、冒号、缺失文件)无测试 |
| 7 | 注入文案内容 | 文案里是否含某条规则无断言。文案被误删不会被发现 |

**【规则】** 新增或修改门禁判定时,**必须**在 `state.test.ts` 或 `readonly.test.ts` 里加对应断言;仅改判定不加测试视为未完成。

**【依据】** 判定逻辑是本项目里唯一「出错将挡住正常开发、且不易凭肉眼发现」的部分。该逻辑现有测试,是这套代码里最可靠的一环;改动时绕过测试会使该保证失效。
