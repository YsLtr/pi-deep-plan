# 02 文档规范 / 03 · 决策归属与提交边界

## 1. 决策不进文档

**【规则】** `docs/` 下**不设**「决策记录」小节,不建 `docs/<topic>/decisions/`,不建 `docs/adr/`。决策的唯一出处是 **git commit message**(`plan-format.md`)。

| 内容 | 写在哪 |
| --- | --- |
| 术语 / 规范用语 / `_Avoid_` | 文档的术语小节 |
| 目标 / 非目标 | 文档 |
| 风险与回滚 | 文档 |
| 计划(可独立验收的条目) | 文档 + `deep_plan_task` |
| 提问式规划的问答过程 | 不写入文件(过程不是产出) |
| **规定理由与否决事项** | **git commit message** |

**【依据】** 决策是**变值,不是定值**。一条决策今天写进文档,几轮问答后很可能被推翻;而文档是**长期维护**的,把会被推翻的推理固化进去,等于持续制造自相矛盾。commit 是**时间点快照**,天然记录「当时的定值理由」,`git log` 即决策的演进史。

这条规则来自一次实际退化:同一话题的决策曾被同时写入话题内的 `decisions/` 目录与跨话题的 `docs/adr/`,同一决策出现在两处会各自演化,读者获取的内容取决于检索命中的文件。当时加过一个交叉检查以捕获重复,但该检查只处理症状 —— 根因是「决策被写进文档」这一前提本身。删掉决策文件位之后,重复问题从源头消失。

**【规则】** 拿到结论后须将其转为**结果性内容**:选定的做法进「计划」,定下的词进「术语」,划掉的范围进「非目标」。

**【依据】** 这是把「决策」转写成「结论」的固定动作。一份只说「讨论后决定不用 X」的文档对读者没有价值;写成「非目标:X」方有价值 —— 后者直接给出范围边界,无需读者了解讨论过程。

**【不采纳】** 不在文档里保留「决策历史」小节按时间排列。

**【依据】** 那是变更日志的形态(`../../INDEX.md` 的维护约定第 8 条)。文档记载当前状态,git 记载状态演变过程。

## 2. 决策的表达方式

决策不单独成节,决策的**结果**以四种形态出现在文档中:

| 决策类型 | 在文档里的落点 | 例子 |
| --- | --- | --- |
| 选定某种做法 | 「计划」条目 | 「`--doc` 尾斜杠表示话题文件夹」 |
| 定下某个术语 | 「术语与领域模型」 | 「**话题** = 长期文档集合,`_Avoid_`:计划/需求」 |
| 明确排除某范围 | 「非目标」 | 「非目标:不做文档归档」 |
| **用户可能想改的默认值** | 「可变决策」表 | 「条目补零 4 位」 |

**【规则】** 「可变决策」表是**唯一**面向用户审查的决策清单,条数 3–8(见 `02` §4)。

**【依据】** 前三类决策一经定下即应被执行,无需用户逐条审查;第四类「用户可能有不同偏好」的项方需用户裁定。将两类分开,可使审查点集中于一处。

## 3. 两段提交边界

**【规则】** 一次完整的 deep-plan 循环产生**两个** commit:文档一个,代码一个。

```
文档阶段收尾 ──→ commit #1: 只有 docs/ 的改动
                        ↓ 用户批准
执行阶段完成 ──→ commit #2: 只有代码的改动
```

**【依据】** 两个 commit 使「批准」这件事在 git 历史里可见:依 `git log` 可分辨「方案的定值时点」与「实现的完成时点」。合并为一个 commit 后,这两件事在历史上无法区分 —— 而这正是本项目要固定的顺序。

**【规则】** 扩展**自身不执行任何 git 命令**(`../../00-总览/01` 的 N1)。扩展只声明边界,并在收尾时说明边界与归属。

**【依据】** 提交动作必须保留用户可干预的位置。若扩展自动提交,「用户批准后才继续」这一约定在文档阶段结束时即已不成立。

## 4. 提交归属

**【规则】** 提交由谁执行**按当次对话的指令**决定,不写死。

| 情况 | 归属 |
| --- | --- |
| 默认 | 由执行者(agent)提交 |
| 用户说「提交由我来」或本轮对话委托给用户 | 交给用户 |
| 归属不明 | **先问,不要猜** |

**【依据】** 提交涉及仓库历史,是用户可能想亲自控制的操作(可能要用特定的提交信息、签名,或与其他改动合并)。将归属固定给某一方,在另一种偏好下都会造成摩擦。故归属可配置,默认值取「不额外打扰用户」的一侧。

**【规则】** 收尾呈现时必须同时说明:先只提交文档、代码单独成一个 commit、以及归属按本轮指令。

**【依据】** 边界(提交范围)与归属(提交方)是两个独立信息,收尾时均须给出;否则读者仅知「提交」而不知「由谁在何时提交」。呈现契约的完整内容见 `../03-规划流程/03`。

## 5. INDEX.md 的角色

**【规则】** `docs/INDEX.md` 是 `docs/` 的入口,承载两项内容:话题表(一行一个话题,指向该话题的总纲)与本仓库的开发约定(测试与类型检查命令、决策不进文档的约定等)。

**【依据】** `docs/` 被定义为本项目的**开发文档**,取代传统的根目录 `development.md`(`plan-format.md`)。既然是开发文档的入口,即不应仅是话题列表 —— 新成员须自同一处获知「存在哪些话题」与「本项目的开发方式」。

**【规则】** 新增或改名话题时须同步更新 `INDEX.md`。

**【依据】** 索引与目录实际内容会产生漂移。索引由模型维护,`/deep-plan-docs` 如实展示两者供对照(`../04-扩展接口/01`),故漂移是**可见**的 —— 可见的漂移将被修正,不可见的则不会。

## 6. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **决策写进 commit 只能靠纪律** | 扩展不读 git,无法验证某个 commit 是否带了理由。「决策写进 commit message」是文案要求,没有强制手段 |
| L2 | **索引漂移无自动修复** | 工具只展示现状,不改写 `INDEX.md`。漂移须由维护者修正 |
| L3 | **提交边界无法强制** | 扩展不执行 git,因此「文档一个 commit、代码一个 commit」只能靠说明与纪律;用户或 agent 若合成一个,扩展不会知道 |
| L4 | **跨话题决策无专门位置** | 删掉 `docs/adr/` 后,一条影响多个话题的决策没有「专属文件」。该决策以 commit message 形式存在,或在某个相关话题的非目标/计划里被引用 |
