# 00 总览 / 03 · 架构与文件职责

## 1. 模块划分

源码在 `src/` 下共七个文件:五个源文件与两个测试文件。**依赖方向单向**,`state.ts` 是唯一的被依赖方(`src/index.ts:11-39`):

```
                      index.ts
        ┌──────────┬──────┴─────┬──────────┐
        ↓          ↓            ↓          ↓
   readonly.ts  tasks.ts   archive.ts      │
                     │                     │
                     └─────────────────────┤
                                           ↓
                                       state.ts
```

`tasks.ts` 是四个子模块里**唯一有内部依赖的一个**:`src/tasks.ts:12` 以 `import type` 引入 `PlanState` / `PlanTask` / `PlanTaskStatus`。该依赖是**类型级**的,不产生运行时耦合,但意味着 `state.ts` 的任务相关类型是 `tasks.ts` 的契约。其余三个子模块之间没有依赖。


| 文件 | 行数 | 职责 | 依赖该文件者 |
| --- | --- | --- | --- |
| `src/index.ts` | 790 | 扩展入口:注册命令与工具、挂钩子、门禁的调用点、状态栏 | — |
| `src/state.ts` | 470 | 状态形状、阶段语义、路径推导、门禁的**判定函数** | `index.ts`、`tasks.ts`(仅类型) |
| `src/readonly.ts` | 458 | 只读命令判定:命令分词、白名单、拒绝清单 | `index.ts` |
| `src/tasks.ts` | 308 | 任务系统:`deep_plan_task` / `deep_plan_step` 与状态机 | `index.ts` |
| `src/archive.ts` | 119 | 文档 frontmatter 的解析、渲染、写回 | `index.ts` |
| `src/state.test.ts` | 226 | `state.ts` 的单元测试 | — |
| `src/readonly.test.ts` | 40 | `readonly.ts` 的单元测试 | — |

**【规则】** `state.ts` 仅收录 I/O 之外的内容。该文件导出的是**纯函数 + 状态形状**,`fs` 只用于 `existsSync` / `statSync` / `mkdirSync` 这类无副作用查询(`src/state.ts:145`、`:233`、`:212`)。判定逻辑必须能在测试里不进文件系统就跑完。

**【依据】** 门禁的正确性只能靠测试保证 —— 门禁拦错一次即挡住正常开发。把判定做成纯函数(`isWriteAllowed`、`isDocPath`、`extractWriteTarget`、`resolveDocPath`)的前提是 `state.test.ts` 能用构造的路径直接断言,不必真的创建仓库(`src/state.test.ts:115`)。

**没有 `util.ts` / `helpers.ts`**。公共逻辑各自就近定义:路径推导在 `state.ts`,命令分词在 `readonly.ts`。

## 2. 各文件边界

| 文件 | 不含 |
| --- | --- |
| `index.ts` | 判定规则本身。该文件只**调用** `isWriteAllowed` / `extractWriteTarget` / `readOnlyVerdict`,不内联规则 |
| `state.ts` | 命令白名单(在 `readonly.ts`)、任务状态机(在 `tasks.ts`)、frontmatter 格式(在 `archive.ts`)、任何文案(文案在 `index.ts`) |
| `readonly.ts` | 文件路径判定。该文件仅判定「这条命令是否只读」,不涉及阶段 |
| `tasks.ts` | 阶段判定本身。该文件只**读** `phaseOf()` 的结果做守卫(`src/tasks.ts:209`) |
| `archive.ts` | 文档内容。该文件只处理 frontmatter 块,正文原样透传 |

## 3. 状态的流转

状态是单个对象,存于会话中(不是磁盘),由扩展自行管理:

```
                    session_start
                         ↓
              sessionManager.getEntries()
                         ↓ 找 customType = stateEntryType 的最后一笔
                  fromPersisted()          src/index.ts:110-118
                         ↓
              ┌──→ state (内存中唯一副本) ──┐
              │                            │
      工具/命令修改 state                   sync() 刷新 UI
              │                            │    src/index.ts:45-76
              ↓                            ↓
         persist()                    状态栏 + 任务面板
              ↓                     (面板仅 executing 显示)
     pi.appendEntry(stateEntryType, toPersisted(state))
```

**【规则】** 状态只有**一个内存副本**(`src/index.ts:45`),所有修改均经 `persist()` 写回会话。不得引入第二处状态缓存 —— 否则将出现「内存记为 writing,持久化记为 executing」的双份真相。

**【依据】** 状态存于会话而非磁盘:阶段与本次 run 绑定,跨会话残留将导致下次启动时门禁凭空生效。`session_shutdown` 时重置为 `INACTIVE`(`src/index.ts:121`)。

## 4. 钩子挂载点

| 钩子 | 位置 | 职责 |
| --- | --- | --- |
| `session_start` | `src/index.ts:110` | 从会话恢复状态,建锚点表,刷新 UI |
| `session_shutdown` | `src/index.ts:120` | 重置 `state` 为 `INACTIVE`,并清空锚点表(`:122`)—— 两者生命周期保持一致 |
| `tool_result` | `src/index.ts:140` | 学习锚点 → 文件 的映射(见 `../01-写入门禁/03`) |
| `tool_call` | `src/index.ts:156` | **门禁**:写操作与命令的拦截点 |
| `before_agent_start` | `src/index.ts:217` | 注入当前阶段的纪律文案 |

**【规则】** 门禁只在 `tool_call` 一处实现。不在 `tool_result` 里做「事后纠正」式拦截 —— 该时点副作用已经发生。
