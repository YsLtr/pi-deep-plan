# 01 写入门禁 / 04 · 状态与持久化

## 1. `PlanState` 字段表

单个接口承载全部门禁所需信息(`src/state.ts:51-72`):

| 字段 | 类型 | 谁写 | 作用 | 行 |
| --- | --- | --- | --- | --- |
| `active` | `boolean` | 启动/结束工具 | 门禁总开关。`false` 时全部放行 | `:52` |
| `phase` | `Phase` | 阶段转移工具 | 决定放行 `docs/` 的哪一侧 | `:53` |
| `planPath` | `string?` | 启动工具 | 本次 run 完善的那个文档的绝对路径 | `:55` |
| `goal` | `string?` | 启动 | 启动时的原始请求文本 | `:57` |
| `variables` | `VariableDecision[]` | `deep_plan_record_variable` | 可变决策,收尾要呈给用户 | `:58` |
| `tasks` | `PlanTask[]` | `deep_plan_task` / `deep_plan_step` | 执行任务 | `:60` |
| `taskTitle` | `string?` | `deep_plan_task action=title` | 人读的任务标题 | `:62` |
| `taskScope` | `string?` | `deep_plan_task action=title` | 人读的范围说明 | `:63` |
| `scratchAllow` | `boolean?` | 启动 | 是否放行 `.pi/tmp/` 写入 | `:65` |
| `startedAt` | `number?` | 启动 | 开始时间戳 | `:66` |
| `approvedAt` | `number?` | `deep_plan_approve` | 批准时间戳 | `:67` |
| `haltReason` | `string?` | `deep_plan_revise` | 上次因文档冲突中止的原因;下次 `approve` 清除 | `:71` |

**【规则】** 门禁只读 `active` / `phase` / `scratchAllow` 三个字段。其余字段不参与放行判定。

**【依据】** 把「哪些字段影响放行」缩到三个,使门禁的正确性可以靠少量组合穷举验证(`../05-测试与验收/01` 的测试只构造这三个字段的不同取值)。

## 2. 未启动态

```ts
export const INACTIVE: PlanState = {
	active: false,
	phase: "writing",
	variables: [],
	tasks: [],
	taskTitle: undefined,
	taskScope: undefined,
	scratchAllow: true,
};
```
(`src/state.ts:75-83`)

**【规则】** `INACTIVE.phase` 必须是 `"writing"`,不是 `"executing"`。

**【依据】** 阶段只在 `active` 为真时有意义。取 `writing` 而非 `executing` 是因为:若某处忘了判 `active`,`writing` 的后果是「挡住代码写入」(安全),`executing` 的后果是「放行全部仓库写入」(危险)。默认值取安全的一侧。

**【规则】** 内存中的状态副本必须是 `INACTIVE` 的**浅拷贝** `{ ...INACTIVE }`(`src/index.ts:45`),不能直接用 `INACTIVE` 本身。

**【依据】** `variables` 与 `tasks` 是数组,直接复用常量会让某次运行的修改永久污染这个共享常量 —— 之后启动的每次 run 都会带着上一次的决策与任务。

## 3. 序列化

`toPersisted()`(`src/state.ts:415-428`)是**逐字段显式拷贝**,不是展开运算符。

**【依据】** `{ ...state }` 会把未来新增的字段一并写入,也会把原型链上的东西带出去。显式列举使新增字段时必须**主动**决定它是否该被持久化 —— 漏掉时的行为是「不持久化」(值变成默认),而不是「悄悄持久化了不该存的东西」。

`fromPersisted()`(`src/state.ts:432-460`)做**逐字段类型校验**:`active` 必须是 `boolean`,否则整体判定为无效数据并返回 `undefined`(`src/state.ts:435`);字符串字段用 `typeof x === "string" ? x : undefined` 收敛;数组字段用 `Array.isArray` 收敛。

**【规则】** 恢复时不做类型假设。外部数据的每个字段都必须过类型判断,不合法就取默认值。

**【依据】** 会话记录由宿主持久化,可能来自旧版本、或被人为改写。直接信任会让一个类型错误(`phase` 是数字、`tasks` 是对象)在很久之后以难以定位的方式炸掉门禁。

## 4. 阶段的折叠

```ts
const phase: Phase = d.phase === "executing" ? "executing" : "writing";
```
(`src/state.ts:441-443`)

**【规则】** 任何不等于 `"executing"` 的历史值都折进 `"writing"`。

**【依据】** 旧版本有三个阶段(`planning` / `review` / `executing`)。文档阶段的两个取值都该折进新的 `writing` —— 一个「写了一半」的方案恢复时应继续写文档,这是安全的。反过来把未知值当成 `executing` 会让旧会话凭空获得仓库写权限。详见 `../00-总览/02-两阶段模型.md` §5。

### 其他字段的向后兼容

| 字段 | 旧值 | 折成 | 依据 |
| --- | --- | --- | --- |
| `scratchAllow` | 缺失 | `true`(`:454`) | 缺失时应当**允许** scratch:它是子代理报告的落脚点,关掉只会让报告无处可写,不带来安全收益 |
| `variables` | 非数组 | `[]`(`:448`) | 收尾校验会因数量不足而退回,是可见的失败 |
| `tasks` | 非数组 | `[]`(`:449`) | 同上 |

**【规则】** 布尔字段的默认值取「不阻断工作流」的一侧,数组字段的默认值取空数组(让下游校验报错),两者都避免静默地放行危险操作。

## 5. 持久化时机

| 时机 | 位置 |
| --- | --- |
| 启动 | `deep_plan_start` / `/deep-plan` |
| 每次状态修改后 | 各工具的 `persist()` 调用 |
| 恢复 | `session_start`(`src/index.ts:110-118`) |
| 清空 | `session_shutdown`(`src/index.ts:120-122`) |

存法:宿主会话记录的 `customType` 条目,恢复时取**最后一条**(`src/index.ts:112-115`)。

**【依据】** 每次修改都写一条,而不是原地更新 —— 会话记录是追加日志,取最后一条即最新态。这样即使中途某次写入失败,也只会回退到上一个一致的状态。

## 6. 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| L1 | **状态存会话,不存磁盘** | 换会话即重置。这是刻意的(见 `../00-总览/03` §3),但意味着「关掉窗口再打开」不会恢复未完成的规划 |
| L2 | **无版本号字段** | 折叠逻辑靠「不等于 `executing` 就是 `writing`」推断,没有显式的 schema 版本。新增阶段取值时必须手工更新这条折叠 |
| L3 | **`variables` / `tasks` 不做元素级校验** | 只验证是数组,不验证每个元素的形状(`src/state.ts:448-449`)。元素形状由写入方保证 |
| L4 | **`haltReason` 只在 `approve` 时清除** | 若用户走 `deep_plan_finish` 结束,该字段随之丢弃(整个状态重置),不会残留 |
| L5 | **时间戳只用于展示** | `startedAt` / `approvedAt` 不参与任何判定 |
