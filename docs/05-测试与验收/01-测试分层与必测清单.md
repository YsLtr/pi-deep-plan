# 05 测试与验收 / 01 · 测试分层与必测清单

## 1. 分层

**【规则】** 两层:**纯函数自动化测试**(`npm test`)+ **手工集成验收**(`02`)。不引入测试框架,采用 Node 内置 test runner。

| 层 | 覆盖 | 命令 | 文件 |
| --- | --- | --- | --- |
| 自动化 | 判定逻辑(路径、门禁、锚点、命令) | `npm test` | `src/state.test.ts`、`src/readonly.test.ts`、`src/intercept.test.ts` |
| 手工 | 钩子、命令、工具、注入、UI | 见 `02` | — |

**【依据】** 判定逻辑是**可穷举的纯函数**:给定输入,输出确定。这类逻辑用自动化测试能覆盖全部边界,且**拦错一次的代价很高**(挡住正常开发),值得测试。而钩子与工具的行为需要真实的会话、UI 与工具调用链,构造成本高于收益 —— 上述行为的正确性靠 `02` 的手工清单与门禁返回文案的直观性来保证。

**【依据】** 不引入测试框架:`package.json` 的 test 脚本直接执行 `node --experimental-strip-types --test src/*.test.ts`(`../00-总览/04` §2)。测试文件只用 `node:assert/strict` 与 `node:test` 两个内置模块。

**【规则】** 平台相关的 test 必须用 `{ skip: ... }` 显式跳过,而不是在函数体里 `if` 返回。

**【依据】** `skip` 会使 test runner 报告为「跳过」(`:24`、`:31`),在结果里可见;函数体内 `if` 返回会被报告为「通过」—— 那是在报告里伪造了一个未执行的断言。

**【规则】** 断言失败时必须带上下文(`assert.equal(actual, expected, message)`)。

**【依据】** 门禁测试的失败信息须能定位到「产生该结果的输入」,否则一个失败只会显示 `false !== true`。

### 3.2 `writers and unknown commands stay blocked`(`:68`)

`DENIED` 数组(`:33-59`),24 条,同样分两组。前 6 条是重定向写与拒绝清单:

| # | 命令 | 覆盖的规则 |
| --- | --- | --- |
| 1 | `echo x > out.txt` | `>` 写文件 |
| 2 | `echo x >> /dev/null.bak` | `>>` 目标**不是** `/dev/null` |
| 3 | `du -sh x >& file` | `>& file` 省略 fd 号 = 写文件(关键用例) |
| 4 | `du -sh x >& /tmp/f` | 同上,路径形式 |
| 5 | `echo hi 2>&1 > out.txt` | 无害与有害重定向混合 |
| 6 | `rm -rf src` | 拒绝清单 |

**【规则】** `>& file` 与 `>& /tmp/f` **必须**留在 DENIED 里(第 3、4 条)。

**【依据】** 这两条是同一条规则(§`../01-写入门禁/02` 的「省略 fd 号的 `>&` 仍是写文件」)的回归测试。把 `>&` 一律视为无害将漏掉该规则 —— 而漏掉的后果是文档阶段可以借助 stdout 重定向写文件。

**【规则】** 无害重定向的正例与反例必须**成对**出现:每一条「应该放行」的重定向形态,都要有一条「看起来像但实际会写」的反例。

**【依据】** 重定向判定是白名单式豁免,最易出现的错误是豁免过宽。成对的正反例使放宽的改动立刻被捕获。

后 18 条(`:41-58`)是裸 shell、解释器与两层家族的写形态:

| # | 命令 | 覆盖的规则 |

| 10 | `pi run x` | `pi` 只放行 `--help`、`--version`(`src/readonly.ts:175-177`) |
| 11 | `node` | 裸解释器会进入交互式 REPL(`src/readonly.ts:264`) |
| 12 | `python` | 同上 |
| 13 | `python3` | 同上 |
| 14 | `py` | 同上 |
| 15 | `node -e 'x'` | 内联执行参数(`-e`、`--eval`、`-c`、`-`)(`src/readonly.ts:265-266`) |
| 16 | `python -c 'x'` | 同上 |
| 17 | `git config user.name x` | `git config` 只有读取形式是只读(`src/readonly.ts:327-330`) |
| 18 | `git remote add a b` | `git remote` 只有查询形式是只读(`src/readonly.ts:323-326`) |
| 19 | `git stash push` | `git stash` 只有 `list`、`show` 是只读(`src/readonly.ts:319-320`) |
| 20 | `git tag -d v1` | `git tag` 只有列举形式是只读(`src/readonly.ts:315-318`) |
| 21 | `git reflog delete` | `git reflog` 的 `delete`、`expire` 会改动引用(`src/readonly.ts:331-334`) |
| 22 | `git branch -D x` | `git branch` 只放行列举旗标(`src/readonly.ts:311-314`) |
| 23 | `npm config set x y` | 包管理器 `config`、`pkg` 只有读取形式是只读(`src/readonly.ts:343-347`) |
| 24 | `npm install` | 不在包管理器的只读子命令集合内(`src/readonly.ts:349`) |

**【规则】** 两层家族的读形态与写形态必须**成对**出现:放行的每一个子命令或旗标,都要有一条对应的写形态被拒(规则表见 `../01-写入门禁/02` §5)。

**【依据】** 参数级白名单与重定向豁免同属「最易放宽」的判定。把 `git stash` 整体放行会让 `push` 成为写入路径,把 `npm` 整体放行会让 `install` 执行任意脚本。成对的正反例使这类放宽立刻被捕获。

## 4. `src/intercept.test.ts` 必测清单

共 **2 个 test**,各覆盖一项设施。

### 4.1 `matchesGrant accepts the identical command only`(`:10`)

| # | 调用 | 期望 | 覆盖的规则 |
| --- | --- | --- | --- |
| 1 | `matchesGrant("rm -rf x", "rm -rf x")` | `true` | 逐字相同即放行 |
| 2 | `matchesGrant("rm -rf x", "  rm -rf x  ")` | `true` | 比较前去除首尾空白 |
| 3 | `matchesGrant("rm -rf x", "rm -rf x && ls")` | `false` | 更长的命令是另一条命令 |
| 4 | `matchesGrant("rm -rf x", "rm -rf X")` | `false` | 大小写不同即不是同一命令 |
| 5 | `matchesGrant(undefined, "rm -rf x")` | `false` | 无凭据时不放行任何命令 |

**【规则】** 第 3 条必须保留。该条是「放宽为前缀匹配」这一改动的回归用例(见 `../01-写入门禁/05` §3.3)。

**【依据】** 批准的范围等于用户在 UI 上看到的命令文本。前缀匹配或子串匹配会让「批准 `rm -rf x`」同时放行 `rm -rf x && rm -rf src`,用户看到的与被执行的不再是同一件事。

### 4.2 `recordBlocked appends one JSON line per refusal under .pi`(`:18`)

| # | 断言 | 覆盖的规则 |
| --- | --- | --- |
| 1 | `blockedLogFile(cwd)` 为 `<cwd>/.pi/deep-plan-blocked.log` | 记录位置 |
| 2 | 两次调用后文件有两行 | 追加,不覆盖 |
| 3 | 含换行的命令仍占一行 | 一行一条 |
| 4 | 首行解析结果等于传入的记录 | 五个字段原样写入 |

**【规则】** 测试用 `mkdtempSync` 建临时目录,结束时 `rmSync` 删除(`:19`、`:48`),不得写入仓库自身。

**【依据】** 记录文件按 cwd 定位。测试若使用仓库根目录,一次失败的断言会在仓库里留下调试文件,并可能被误读为真实记录。

| # | 未覆盖 | 风险 |

| 6 | `archive.ts` 的 frontmatter 往返 | 解析 / 渲染 / 写入的边界(引号、冒号、缺失文件)无测试 |

**【规则】** 新增或修改门禁判定时,**必须**在 `state.test.ts`、`readonly.test.ts` 或 `intercept.test.ts` 里加对应断言;仅改判定不加测试视为未完成。

**【依据】** 判定逻辑是本项目里唯一「出错将挡住正常开发、且不易凭肉眼发现」的部分。该逻辑现有测试,是这套代码里最可靠的一环;改动时绕过测试会使该保证失效。
